# Как идёт портирование Ennorath

Один документ про порядок работы. Указатель документов: [README.md](README.md). Правила проекта остаются в [../ENNORATH_FACTION_PLAN.md](../ENNORATH_FACTION_PLAN.md) и [../PLAN.md](../PLAN.md); здесь то, что нужно, чтобы начать смену, довести класс или запись до конца и не мешать другому исполнителю.

## 1. Цель

Ennorath 1.9.8.5 (база с 2026-11-21, до этого 1.9.8.4 с 2026-11-20, 1.9.8.3 с 2026-11-15, 1.9.8.2 с 2026-11-04 и 1.9.8.1 с 2026-11-03; см. [README.md](README.md)) на движке OpenBFME ведёт себя так же, как на RotWK 2.01. Порт читает файлы мода без изменений, мод не правится, игровые данные в Git не попадают. Чиним общий механизм движка, без списков конкретных объектов и фракций. Каждую правку подтверждаем адресом RW (ванильный бинарник 2.01, md5 `daed3668…`: `workspace/games-en/Vanilla_(2.01)/install/game.dat`; `RotWK/game.dat` Эннората пропатчен pySAGE (1.9.8.5: md5 `fc32e4c4…`) и эталоном не служит; оговорка S-001) или файлом декомпиляции BFME2 (`workspace/reference/open-bfme-2`). Вывод без такого подтверждения помечаем `INFERENCE`.

**Всё должно быть как в Ennorath (решение владельца 2026-11-02).** Агент не выбирает «улучшения» сам, даже если поведение оригинала кажется хуже. Если есть причина отойти от него, агент объясняет её владельцу простыми словами и ждёт ответа. Принятый отход записывается стопом и в этот список.

Принятые отходы от оригинала:

- Смена строя, когда кнопку жмёт логика (ИИ, улучшение): прямой вызов вместо сообщения 0x453 (RW 0x697204 / 0x77BE83), строй меняется примерно на кадр раньше. Стоп S-5307. Решение владельца 2026-11-02.
- Косметика и удобство: раздел «Not retail» в [../MODS.md](../MODS.md).
- Правки пропатченного `game.dat` Эннората 1.9.8.5 (pySAGE), только с профилем «Ennorath 1.9.8.5 game.dat» (`--mod-engine=fc32e4c4…`, lane MODS-3): `ennorath.stance-keeps-moving` — «Удерживать позицию» не останавливает идущий отряд; `ennorath.middle-click-camera` — щелчок средней кнопкой 350 мс по часам, сдвиг дальше 5 пикселей отменяет; `ennorath.evacuate-containers` — «Высадить все» из туннеля (туннели гномов, крипты Ангмара) выпускает и боевые повозки, и ангмарского Короля-чародея. Разбор — [ENNORATH_EXE.md](ENNORATH_EXE.md), стоп S-5304. Решение владельца 2026-11-21 (PR #792).

## 3. Кто что делает

- **Владелец**: ставит задачи, записывает найденное в игре в `PROBLEMS.md`, играет и подтверждает результат, решает спорное. Статус `ВЫПОЛНЕНО` для видимых вещей ставится только после его ответа.
- **Агенты**: работают параллельно, каждый в своей ветке и своём дереве (раздел 4). Колонка «состояние» в `MODULE_GAPS.md` называет, кто чем занят. Чужой класс не берём. Общие файлы (`STOPS.md`, `LogicModules.cpp`, `PROBLEMS.md`) правим короткими точечными правками, а не переписываем целиком. Числа в `README.md` и `test_module_coverage.cpp` руками не правим (раздел 5, шаг 8).
- **Порядок работы** (решение владельца 2026-11-02): прямое поручение владельца → поломка, из-за которой нельзя играть → P-31 → [проверка всех кнопок](BUTTON_SWEEP.md) → [подсистемы](SUBSYSTEMS.md) → классы, которые им нужны. Записи `PROBLEMS.md` без поручения не берутся отдельно: они привязываются к подсистеме и закрываются вместе с ней (раздел 6).

## 4. Ветка и дерево на агента

**Где работают агенты (решение владельца 2026-11-13 / 2026-11-14).** Сборки, тесты, замеры эталонов и разборы `game.dat` идут в Google Colab владельца (`colab-sandbox`, правила `.clinerules/colab.md`); компьютер владельца — только сборка игры под Windows (`build.bat`) и запуск игры, это делает Claude. Агент, запущенный на компьютере владельца (задачи «Local N», раздел 7в), выполняет всё через `ssh colab-sandbox`. Для работы на Colab в этом и следующих разделах вместо `build.bat` — `bash tools/colab/build_tests.sh`, вместо `engine\build\openbfme_tests.exe` — `engine/build/openbfme_tests`, деревья — `/content/sandbox/openbfme-godot/workspace/wt`; полный прогон тестов — только по слову владельца.

**Три песочницы и компьютер владельца (решение владельца 2026-11-14).** Песочниц три, по одной на аккаунт Colab Pro. У каждой на компьютере владельца свой SSH-конфиг (`C:/Users/apple/.ssh/colab-<N>.conf`), хост во всех называется `colab-sandbox`, поэтому команда — `ssh -F <конфиг> colab-sandbox`; `ssh colab-sandbox` без `-F` идёт в песочницу 1. Песочницу агенту выдаёт дашборд (страница «Локальные»: онлайн или нет, адрес туннеля, команда конфига) вместе со станцией; ветка станции живёт в `origin`, дерево станции в новой песочнице создаётся из неё. Бэкап (`openbfme-sandbox`) и ccache (`openbfme-ccache`) у каждой песочницы свои, на Диске своего аккаунта; архив игры и аудит — ярлыки на копии аккаунта 1. На компьютере владельца остаются только основное дерево (`main`) и станция Claude `station-0` (`workspace/wt/claude-station-0`); станции 1–3 и деревья агентов — только в Colab.

Решение владельца 2026-10-31. В основном дереве никто не работает и не оставляет незакоммиченных правок: там лежит только `main`, в него владелец играет.

- **Рабочие станции** (решение владельца 2026-11-04, вечер). Новую ветку под каждую задачу не создавать: у агента есть постоянные деревья-станции, ветки `agent/<агент>/station-<номер>` (у Claude `station-0` в `workspace/wt/claude-station-0` — проверка чужой работы и перенос в `main`; `station-1` в `workspace/wt/claude-hashwalk`, `station-2` в `claude-rule-long-tests`, `station-3` в `claude-main-red` отданы локальным агентам (решение владельца 2026-11-07: новых станций нет); имена папок старые, потому что сборка привязана к пути). Задача делается в свободной станции: `agent_worktree.py sync`, правка, коммиты, после «переноси» `land <станция>`: `main` перематывается, ветка и дерево станции остаются для следующей задачи. Номер проблемы TOP20 или тема — в сообщениях коммитов, не в имени ветки. `new` отказывает агенту, у которого есть свободная станция (влита в `main`, без незакоммиченных правок); новая станция создаётся только с согласия владельца: `new <агент> station-<номер>`.
- **Начать работу**: `python tools/agent_worktree.py new <агент> <тема>` создаёт ветку `agent/<агент>/<тема>` и дерево `workspace/wt/<агент>-<тема>` со своими `engine/build` и `godot/bin`. Если есть отложенное дерево (его оставили `land` или `remove`), команда берёт его: ветка переключается в нём, а `git` переписывает только отличающиеся файлы, поэтому сборка пересобирает лишь их, а это минуты. Путь и имя папки остаются от прошлой ветки, своё дерево смотреть по выводу `new` и `list`. Без отложенного дерева первая сборка полная, около 20 минут (раздел 7).
- **Коммитить** в свою ветку можно без просьбы и часто, минимум после каждого готового шага: если агент выбыл, его работа цела. Шлюз `tools/precommit.py` ставит та же команда.
- **Перед сдачей**: `python tools/agent_worktree.py sync --tests-exe engine\build\openbfme_tests.exe` вливает свежий `main` и пересчитывает числа.
- **Перед первой записью в файл** убедиться, что `git rev-parse --show-toplevel` показывает своё дерево, и писать только по путям внутри него. Запись в основное дерево или чужое дерево считается ошибкой, даже если правка верная: 2026-11-01 половина работы над Евой попала в основное дерево, половина осталась в дереве агента, и не собирались оба. Заметив такое, ничего не переносить и не удалять, а сообщить владельцу и хозяину правки.
- **В `main`** работа попадает только после одобрения владельца: `python tools/agent_worktree.py land <ветка>`. Исключение (решение владельца 2026-11-13): Claude переносит проверенную работу станций и принятые PR и задачи агентов сам, без «переноси»; узкие тесты зелёные, шлюз коммитов прошёл, каждый пункт помечен «проверить в игре» в [TOP20.md](TOP20.md) / [PROBLEMS.md](PROBLEMS.md). Выпуск, PR в upstream от имени владельца и полный прогон остаются за владельцем. Команда двигает `main` только перемоткой, а потом удаляет ветку (ветку рабочей станции не удаляет). Дерево она откладывает (`HEAD` отцеплен, сборка цела), пока отложенных меньше трёх; иначе удаляет. Незалитую или незакоммиченную работу она не удалит и не перезапишет.
- **Одобрение** должно прямо относиться к переносу этой ветки: «переноси», «land». Ответы вроде «+», «ок», «меняй» на сообщение с несколькими решениями одобрением не считаются: надо переспросить. Одобрение одной ветки не распространяется на другую и на следующий коммит.
- **Если `land` отказал**, потому что в основном дереве лежат незакоммиченные правки владельца, агент сообщает об этом. Обойти отказ можно только с одобрением этой ветки и только через `git merge --ff-only <ветка>`, а в отчёте об этом сказать. Чужие незакоммиченные правки не трогать.
- **Кто чем занят**: `python tools/agent_worktree.py list`.

Таблица «Что запущено» в [PROBLEMS.md](PROBLEMS.md) остаётся только для **игры, которую запускают для владельца, и нагрузки**. Собирать в своём дереве можно при открытой игре: библиотека у каждого дерева своя. Одновременно не больше двух сборок, у каждой стандартный лимит `build.bat` (треть ядер, пониженный приоритет); если владелец сказал, что компьютер лагает, `OPENBFME_BUILD_JOBS=2` и одна сборка за раз. Сборку и игру другого агента не останавливать.

## 5. Конвейер одного класса модуля

1. **Взять** класс, который нужен подсистеме или матрице (раздел 3). Если таких нет, сверху списка `python tools/mod/ennorath_queue.py priority`: он отсортирован по числу объектов мода, классы без достижимых объектов отложены. Охват считает объекты, а не заметность, поэтому владелец может поднять класс выше. Затем поставить в строке `MODULE_GAPS.md` «ЗАНЯТО — кто, дата».
2. **Досье**: `python tools/mod/class_dossier.py <Класс> --game-dat RotWK\game.dat` за один запуск даёт строку таблицы, состояние в upstream (`ennorath_unique.py`: если upstream уже сделал или делает, не переносим), адреса реестра, поля мода со значениями и объекты, файлы декомпиляции, ближайший перенесённый класс и ссылки на имя в бинарнике. Не хватает источника — досье так и пишет. Вывод содержит данные мода: в Git его не кладём.
3. **Что запускает класс** (кнопка, ИИ, другой модуль). Если не запускает ничто, это пишем честно (так было у `DeflectSpecialPower`).
4. **Бинарник и декомпиляция**: тело функций (`tools/mod/rw.py RotWK\game.dat dis|xref|str`), тело в BFME2. Что RW делает иначе, чем BFME2, берём по RW. Декомпиляция BFME2 (`workspace/reference/open-bfme-2`) — донор: по ней быстрее найти функцию, имена полей и структуру класса, но каждое поведение подтверждается адресом RW (раздел 15, правило 1). Вердикт «RotWK поле не читает» допустим только с цепочкой чтения в RW (парсер поля → смещение → все читатели смещения) и проверкой донора: если BFME2 поле читает, найти, куда это чтение делось в RW.
5. **Код**: данные, поля INI, рантайм, `xfer` и `crc`, привязка в `LogicModules.cpp` и файл подключён в лейн-файле `engine/cmake/Modgap*.cmake`. В заголовке: что прочитано (с адресами) и что не перенесено. Обязательно (каждый пункт уже ломал `main`):
   - **Имена полей INI** копировать из таблицы игры (`engine/data/rotwk-201/field-tables.json`) вместе с регистром, а не набирать по памяти. В таблице `Sweepfrequency`, а не `SweepFrequency`: эта ошибка остановила загрузку всех данных.
   - **`xfer` модуля** объявлять только через `OBFME_MODULE_XFER(Класс)`. Простой `void xfer(Xfer &x) override;` компилируется, но сохранение на таком объекте отказывает.
   - **Класс перестаёт быть заглушкой**: найти все места, которые его читают: `git grep -n "<Класс>" engine`, а также `dynamic_cast<const RawModuleData` и `className()`. Типизированные данные не читаются через `RawModuleData`, поэтому `AnimalAIUpdate` потерял `AfraidOfCastles`. Списки «не перенесено» и проверки `isUnported()` в тестах обновить в той же ветке.
   - **Правка общей функции** (`Object`, `Contain`, `AIUpdateInterface`, `ScriptConditions`): пройти все вызовы и все значения её флагов и прогнать наборы затронутых систем (раздел 7). Правка `HordeContain::removeMember` учла выход из отряда, но не `keepSlot=true`, и сломала вход в здания, шахты и транспорт.
6. **Два теста.** Тест, который падает без правки: данные синтетические, ожидаемые значения — из данных мода, а не считанные из самого кода, файл `engine/tests/test_modgap*_*.cpp`. И сценарий на настоящих данных мода, если у класса есть проверяемая логика: `TEST_CASE("ENNORATH scenario <Класс>: ...")` в `engine/tests/test_ennorath_scenarios.cpp` (раздел 8). Новый тест должен быть запущен и зелёным в ветке для обеих редакций, пока он красный, класс не готов. INI в тесте пишем синтаксисом RotWK (`DamageNugget`, а не `PrimaryDamage` из Zero Hour). Тест не обращается к объекту, который мог быть уничтожен: последний член отряда уничтожает свой отряд.
7. **Стоп** на всё, что не перенесено или выведено: строка в `STOPS.md`. Найденное по ходу сначала доделать (решение владельца 2026-11-14): непортированное поведение переносится в той же ветке со своим тестом, если (а) оно в том же классе или функции, что задача, (б) это не общий механизм и не чужая область, (в) правка не двигает пины и чужие тесты, (г) объём не больше трети задачи. Стоп пишется только на то, что не прошло хоть одно условие, и в строке сказано, какое. Правка, целиком закрывшая открытый стоп, удаляет его строку (или переписывает остаток). Остальные стопы закрываются отдельными задачами «Port N», пачками по механизму, текст задачи — колонка «как закрыть» стопа. **Новая строка стопа — отдельный файл** `docs/stops.d/S-<id>.md` (первая строка — строка таблицы, дальше по желанию раздел `## ...`), строка NIGHT_WATCH — файл `docs/ennorath/night_watch.d/<PORT-N|LOCAL-N>.md`: параллельные ветки не правят одну таблицу. Номера стопов выдаёт задача (`python tools/fragments.py reserve <issue> 3`, запись в `docs/stops.d/RESERVED.tsv`). В таблицы фрагменты сводит перенос в main (`tools/fragments.py collect`, его вызывает `tools/land.py`); `tools/precommit.py` проверяет их формат и номера. Перед выдачей задачи — `python tools/issue_check.py <черновик.md>`: адреса RW, уже процитированные в коде, и открытые issue / PR с теми же стопами, адресами и файлами.
8. **Числа** (`README.md`, `test_module_coverage.cpp`) в работе не трогаем, тест покрытия в ветке может падать только из-за них. Их выставляет `agent_worktree.py sync` перед сдачей (`tools/sync_counts.py`). Конфликт в этих строках решается так: взять любую сторону и запустить `sync_counts.py`.
9. **Собрать**, прогнать (раздел 7), обновить строку в `MODULE_GAPS.md` и запись в `PROBLEMS.md`. Статус `ported` ставим, только если класс реально работает в игре: его запускает кнопка, ИИ или другой модуль (шаг 3), а после появления матрицы ещё и строки матрицы с этим классом проходят без обрыва на нём. Если прочитаны только данные или механизм не даёт эффекта, статус `partial` с указанием, чего нет. Тест одного класса не доказывает работу цепочки.
10. **Сдать**: обновить чек-лист партии (раздел 8), написать отчёт по разделу 14 и попросить владельца принять ветку.

## 7. Сборка и тесты

- **На Colab** (раздел 4, «Где работают агенты»): сборка `bash tools/colab/build_tests.sh` из своего дерева; правила про `build.bat`, очередь сборок и `build_slot.ps1` ниже относятся к сборке игры под Windows на компьютере владельца, которую делает Claude.
- Собирать только `build.bat` (пониженный приоритет и лимит задач, см. «Нагрузка сборки» в плане). В своём дереве можно собирать, когда нужно проверить правку; вхолостую не собирать. Правило «пачками» больше не действует: оно защищало общую папку сборки.
- **Очередь сборок:** `build.bat` сам ждёт свободного места, одновременно идут не больше двух сборок на машине, из любых деревьев (`tools/build_slot.ps1`). Следить за этим вручную больше не надо. Если компьютер лагает, `OPENBFME_BUILD_SLOTS=1`.
- **Только тесты:** `OPENBFME_BUILD_TARGETS=openbfme_tests` не собирает библиотеку игры. Использовать, когда игра не нужна.
- Кэш компиляции не включать: `OPENBFME_COMPILER_CACHE` в `build.bat` есть, но в дереве по другому пути `sccache` дал 1 попадание из 2483 (замер 2026-11-01), а смена настройки пересобирает всё дерево. Папку сборки нельзя скопировать в дерево по другому пути: в ней полные пути CMake и ninja. Поэтому деревья не удаляются, а откладываются и переиспользуются (раздел 4, `agent_worktree.py`); одна сборка занимает 12–14 ГБ (замер 2026-11-03), отложенных держим не больше трёх.
- **Какие тесты**: в ветке `python tools/test_select.py --run engine\build\openbfme_tests.exe` гоняет только тесты, которых достигает правка. Если есть карта (`workspace/test-map/map.json` в главной копии), это файлы тестов, которые реально выполняли изменённый файл; иначе цепочка `#include`. Первая строка вывода говорит, какое правило сработало. Широкий выбор не `FULL`: он идёт несколькими запусками подряд, столько, сколько требует длина командной строки. Если проследить нельзя, команда скажет `FULL`: перед `--run` сначала запустить её без `--run` и посмотреть причину. Настоящий `FULL` обходить нельзя (раздел 15, правило 8): перед `land` нужен полный прогон на последнем коммите ветки, его можно поставить на ночь. Новое дерево показывает 4 PNG из `godot/assets` как изменённые (Git LFS), и это даёт ложный `FULL`. Такие файлы не коммитить, а скрыть один раз после создания дерева: `git update-index --assume-unchanged godot/assets/brand/poweredby_openbfme.png godot/assets/platform_icons/linux.png godot/assets/platform_icons/macos.png godot/assets/platform_icons/windows.png`.
- **Для работы по TOP20 действует раздел 7а**: исправление проверяется узким тестом и владельцем, без ожидания других тестов, последнее слово за ночным прогоном. Правила ниже остаются для остальной работы.
- **Правило пяти минут** (решение владельца 2026-11-04). Цель: маленькая правка, ошибку в которой владелец увидит в игре за секунды, не должна ждать получасового прогона. Правило касается только **видимого**: того, что владелец замечает в обычной игре (как выглядит, звучит, двигается, что делает кнопка, курсор, способность). Ошибка, которой в обычной игре не видно (состояние логики, хэши, сохранения, сетевая игра и рассинхрон, падение в редкой ветке кода, данные, которые читает другой модуль), проверяется только тестами: для неё длинный прогон остаётся обязательным до `land`, владелец его не заменяет.
  - **Исключение: правка самого движка** (решение владельца 2026-11-04). Правило пяти минут подходит для местной правки: одна кнопка, одна способность, один модуль или класс, одна панель интерфейса. Если правка меняет общий механизм, которым пользуются многие объекты и системы, длинный прогон обязателен до `land`, даже если всё изменённое видно в игре: владелец проверит свой случай, но не все остальные. Правка движка — это изменение общих систем: цикл кадра и порядок обновлений, поиск пути и движение, бой и урон, приказы и группы, ИИ, производство и строительство, ввод и поток сообщений, сохранения, сеть, загрузка данных (INI, архивы), отрисовка и камера в целом; а также код, через который идёт больше одного модуля или класса. Сомнение решается в пользу «движок». Агент и тогда не ждёт без дела, а работает над другими задачами, пока идёт прогон.
  - **Прогон до 5 минут** агент запускает и дожидается, как раньше.
  - **Прогон дольше 5 минут** агент не ждёт. Длительность берётся из прошлых прогонов или логов карты тестов (там время каждого теста); если она неизвестна, прогон запускается в фоне, и через 5 минут без результата он считается длинным. Длинный прогон агент запускает в фоне или ставит в ночной, а видимую часть правки отдаёт владельцу точной проверкой: кого заспавнить (Cheat Mode, `docs/CHEAT_MODE.md`), что сделать, что должно получиться по оригиналу. Проверки собираются в пачку не меньше пяти, по одной владельца не зовут.
  - **Агент сразу переходит к следующей задаче.** Если следующая зависит от результата длинного прогона или проверки владельца, она ставится на паузу с пометкой «ждёт: <прогон или проверка>», и агент берёт следующую независимую. Когда результат пришёл, агент возвращается к задачам на паузе. Список задач на паузе есть в каждом отчёте.
  - **Перенос в `main`.** Правка только видимого: ответа владельца «работает» и его «переноси» достаточно, длинный прогон для этого не ждут. Правка, в которой есть невидимая часть (логика, хэши, сохранения, сеть): тесты этой части из выбора `test_select` должны пройти до `land`. Агент их не ждёт, а работает дальше, и переносит ветку, когда они прошли и владелец ответил. Результат длинного прогона разбирается в любом случае: падение, которого нет в [TEST_BASELINE.md](TEST_BASELINE.md), становится первой задачей агента, чья ветка его внесла.
  - **Какая часть видима**, агент пишет в отчёте по каждому изменённому поведению: «видно в игре: что и где» или «не видно: какой тест это проверяет». Сомнение решается в пользу «не видно». Там же одна строка: правка местная или правка движка, и почему.
- **Перед `land`** (решение владельца 2026-11-01: полный прогон занимает около 5 часов, на каждую ветку его не гоняем), на сборке из последнего коммита, после `agent_worktree.py sync`, с правилом пяти минут выше:
  1. Сборка `build.bat`.
  2. `test_select.py --run`.
  3. Обязательный набор, с данными игры (окружение ниже), всегда, для любой правки кода:
     `openbfme_tests.exe "--test-case=ENNORATH scenario*,module coverage*,modgap2*,mapobj retail: the object world*,logic retail: the PlayerTemplate*,save4a retail T4*,save4b retail*,move retail*"`

     `move retail*` создаёт все шаблоны чистой игры. Он обязателен с 2026-11-02: `6117d165` прошёл без него и уронил `main` на создании объекта.
  4. Наборы затронутых систем. Правка входа, выхода и отрядов: `garrison*,tunnel*,transport retail*,ring delivery*,ship1*`. Правка ИИ и скриптов: `modcompat-ai*,script*,castlearea1*,move retail*`. Правка сохранений: `save*`.
- **Правило красного**: всё из перечисленного должно пройти. Падение допускается, только если этот тест записан в [TEST_BASELINE.md](TEST_BASELINE.md) с тем же сообщением. Если записи нет, падение относится к ветке и чинится до `land`, слова «падало и раньше» не считаются, нужен запуск этого теста на чистом `main` с выводом в отчёте. В `TEST_BASELINE.md` записи добавляются только по полному прогону на чистом `main`. Если исправлено, запись убирается в той же ветке. Тесты, которые не запускались из-за отсутствия `ROTWK_INSTALL` и других переменных (SKIP), не считаются пройденными.
- **Каждое падение, замеченное в прогоне, либо исправляется, либо записывается** (решение владельца 2026-11-04). Это касается и падений, которые внесла не своя ветка, и падений, которые зависят от порядка тестов. Маленькое падение исправляется сразу, в своей ветке или в отдельной: причина понятна, а правка небольшая и не уводит от задачи. Большое падение не исправляется сразу. Записываются оба: каждое падение получает в [PROBLEMS.md](PROBLEMS.md) отдельную запись P-<номер>. Исправленное записывается в той же ветке, что и исправление, со статусом **ВЫПОЛНЕНО**: в записи причина, правка (коммит) и тест, который теперь проходит. Неисправленное остаётся открытой записью. В любой записи указываются тест, файл и строка, сообщение, сборка и что уже проверено (падает ли без правки ветки, падает ли отдельно). Промолчать о падении нельзя. Слова «чужое» и «падало и раньше» не освобождают ни от исправления, ни от записи. Записи из `TEST_BASELINE.md` уже записаны, второй раз их не записывают.
- **`SIGSEGV`, `CRASHED`, зависание** в любом тесте — самая срочная ошибка: они обрывают прогон и прячут всё, что идёт после. Такой коммит в `main` не попадает, а уже попавший чинится первым.
- **Ночью** полный прогон `openbfme_tests.exe` на свежем `main` (с `ROTWK_INSTALL`, `BFME2_INSTALL`, `OPENBFME_ENNORATH_INSTALL`, иначе retail-тесты пропускаются). Утром его падения сравниваются с [TEST_BASELINE.md](TEST_BASELINE.md); отчёт содержит только разницу. До разбора прочитать [NIGHT_WATCH.md](NIGHT_WATCH.md): там правки, которые ждут ночи, и что в них может сломаться (раздел 7а). Упавший только после `land` относится к веткам, залитым за день. `test_select` не видит связей через данные, а без карты и через виртуальные вызовы, поэтому ночной прогон обязателен, пока такие связи есть. **Карта** пересобирается там же ночью: `build.bat` с `OPENBFME_TEST_COVERAGE=1` (своя папка `engine\build-cov`), затем `python tools\test_coverage_map.py`, с теми же переменными. Каждый файл тестов идёт своим процессом; после обрыва запись продолжается с того же места, а перед новой записью старую папку `workspace\test-map\records` надо удалить. Заодно в её логах остаётся время каждого теста. **Прогон считается полным**, только если в нём нет `CRASHED` и строка `skipped` равна числу тестов с `doctest::skip` (2026-11-02: 26). Смотреть надо на это число, а не на `Status`: после вылета все оставшиеся тесты тоже считаются skipped. Если прогон оборвался, продолжить с `--first=<номер упавшего + 1>` и сказать об этом в отчёте. Если большая группа тестов падает на одной ранней проверке (например, `errors.empty()` при загрузке), они не проверены: после исправления причины их надо запустить снова.
- **Изменение ожиданий теста** — самое опасное действие: оно может спрятать настоящую ошибку.
  - Ожидание меняем только с источником рядом в комментарии: адрес RW, файл декомпиляции или блок и поле INI мода. «Так сейчас считает код» источником не является.
  - Нельзя делать проверку слабее, не сказав об этом: удалять `CHECK`, заменять проверяемый объект другим, расширять исключение на целый класс, если причина в одном шаблоне. Если причина законная (например, разные слоты планировщика у двух объектов), остальное сравнить напрямую, а причину записать в комментарии.
  - **Эталонные хэши и числа** (`engine/tests/data/**/*.hashes`, закреплённые значения в тестах) обновляются только с названной причиной: какая правка их сдвинула и почему. Детерминизм между потоками и запусками не доказывает, что новые значения верны. Причину ищут самым дешёвым способом, который её доказывает (решение владельца 2026-11-06: не гонять железо зря):
    1. **Своя правка.** Сдвиг от правки своей ветки доказывается одним запуском упавшего теста с выключенной правкой (вернуть строку, флаг, вызов) на той же сборке. Совпало со старым эталоном — причина названа. Сборка родителя и прогон по истории не нужны.
    2. **Чужой сдвиг.** Если ночной разбор уже назвал коммит или слияние (сборка до и после), этого достаточно. Слияние upstream — причина целиком: коммит внутри слияния не ищется, если игра не сломана (сдвинулись числа теста, а не поведение, которое видно).
    3. **Причина не названа.** Поиск делением пополам по коммитам `main` с первым родителем, только упавший тест, не больше 5 сборок. Нашлась первая правка, а дальше значение сдвигалось ещё: записать первую правку и «позднейшие правки форка до `<коммит>`» и переснять.
    4. **Нельзя:** проходы по всей истории со сборкой на каждом коммите, полный прогон ради одного эталона, больше 5 сборок на один эталон без решения владельца. Перед работой, где сборок наберётся больше часа, — оценка времени владельцу.
    5. **Сначала чтение, потом одна сборка** (решение владельца 2026-11-21: партия Local 111–120 сдвинула `perf1` / `uber1`, причины искали выключением веток по одной — пять сборок, две из них впустую). Когда в сборке несколько правок (партия, слияние нескольких веток):
       - **Прочитать diff каждой ветки целиком, по всем файлам** (`git diff origin/main...<ветка> -- engine/src`), а не по описанию PR: описание называет одну правку, а ветка может нести три (Local 120: P-169 названа, P-168 — нет). Выписать каждый кусок кода и пометить: **меняет состояние симуляции** (логика `engine/src/GameLogic`, `engine/src/Common` — порядок обновлений, случайные числа логики, создание и гибель объектов, движение, бой, ИИ, скрипты, хэш) или **не меняет** (клиент, отрисовка, звук, интерфейс, `GodotDevice`, отчёты и журналы, только `xfer` без нового состояния, комментарии и цитаты). Сомнение — «меняет».
       - **Одна сборка, в которой выключено всё, что меняет состояние** (откат этих кусков `git apply -R`). Совпало со старым эталоном — список причин полон; дальше не выключать по одной, а назвать каждую правку из списка причиной. Не совпало — в списке «не меняет» ошибка: перечитать, а не выключать ветки наугад.
       - **Делить список дальше** только если нужно указать вклад каждой правки отдельно (например, одна из них неверна и не переносится): делением пополам по списку кусков, не по веткам.
       - **Агент в PR** перечисляет все куски своей ветки, меняющие состояние симуляции (файл, функция, адрес RW), и для каждого — двигает ли он эталоны (шаблоны Local и Port); Claude при приёмке сверяет этот список с diff.
       - **Платформа** (2026-11-21, партия Local 108–126 на sb5): векторы `perf1` / `uber1` совпадают на Colab GCC и Windows MSVC, а перепись классов `save4b retail T4` (партия четырёх ИИ на кадре 3000) на GCC иная уже в чистом `main`. Её перемеряют только на Windows MSVC; красный T4 на песочнице сначала сверить с чистым `main` там же, ожидание по замеру Colab не менять.
       - **Слияние нескольких веток на песочнице**: проверка фрагментов стопов берёт задачу из общего `git config openbfme.issue` агента станции и отказывает стопам других задач; сливать и коммитить через `git -c openbfme.issue= merge|commit`.
  - Эталоны, у которых причины названы, переснимаются **одной веткой сразу все** (запрет «нельзя обновлять при других красных тестах» относится только к красным тестам без названной причины: их причина могла сдвинуть эталон). В ветке: таблица «тест, было, стало, причина», в каждом тесте комментарий `// pin: <причина>`.
  - Каждое изменённое ожидание попадает в отчёт: было, стало, источник (раздел 14).
- Окружение для тестов с данными игры:

```powershell

$env:BFME2_INSTALL = 'C:\Program Files (x86)\BFME2'

$env:OPENBFME_ENNORATH_INSTALL = (Resolve-Path 'workspace\mods-en\Ennorath\install').Path
$env:RW_GAME_DAT = (Resolve-Path 'workspace\games-en\Vanilla_(2.01)\install\game.dat').Path   # ванильный daed3668; RotWK\game.dat пропатчен (1.9.8.5)
```

- Тесты гонять из копии (`Copy-Item engine\build\openbfme_tests.exe workspace\tests_xx.exe`), по одному набору: `-tc="modgap*"`, `module coverage*`, `save*`, `MOD-4*`, `MODS-1 mod corpus*`, `ENNORATH*`, `factb*`, `move*`, `combat*`, `proj*`, `horde*`, `hud6*`. Не запускать `*save*` и другие длинные наборы во время чужой сборки.
- Появилась новая сборка: идущий прогон тестов старой сборки можно остановить и начать заново на новой, его результат уже устарел. Прогресс не сохраняется, найденное в логе остаётся: падения из него перед перезапуском выписать, а в отчёте сказать, что прогон прерван. Прерванный полный прогон не считается пройденным. Правило касается только своих прогонов: чужой не останавливать (раздел 4).
- В отчёте всегда: что запущено, сколько случаев и проверок, что пропущено или упало, что не запускалось (подробнее раздел 14).

## 7а. Работа по TOP20 без ожидания тестов (решение владельца 2026-11-04, вечер)

Цель: исправление не ждёт тестов. Последнее слово за ночным полным прогоном. Для работы по [TOP20.md](TOP20.md) этот раздел заменяет из раздела 7 «Перед `land`» (`test_select`, обязательный набор, наборы систем), правило пяти минут с исключением для правки движка и правило 8 раздела 15.

1. **Задача.** Брать проблему из [TOP20.md](TOP20.md) сверху вниз, одну за раз, в своей рабочей станции (раздел 4). Номер проблемы — в сообщении коммита.
2. **Исправление.** Как всегда: по RW или файлам мода, с адресом (раздел 15, правила 1-4).
2а. **Сложную задачу не пропускать** (решение владельца 2026-11-04, ночь). «Большое», «много функций RW», «нужна новая подсистема» — не причина записать стоп и взять следующую проблему. Агент делает перенос до конца: разбивает его на шаги, каждый шаг — отдельный коммит со своим тестом, и не переходит к следующей проблеме, пока текущая не исправлена. Стоп вместо исправления допустим только когда без решения владельца дальше нельзя (в RW поведение не определяется, нужно выбрать архитектуру, нужны файлы или запись из оригинальной игры); тогда агент спрашивает владельца с тем, что уже найдено, а не уходит к следующей задаче молча. «RotWK тоже не использует» остаётся исходом, когда это доказано адресом.
3. **Тест против регрессии.** Тест максимально нацелен на изменение: проверяет именно то, что правка поменяла (по числам RW), падает без правки, проходит с ней. У большой правки на каждый шаг свой такой тест, плюс тест, который держит соседнее поведение, которое правка могла задеть (против регрессии), — тоже узкий. Запускать только его и тесты того же файла (`-tc=` по имени). Ничего широкого и «на всякий случай» не запускать: `test_select`, обязательный набор, `FULL`, наборы систем — это работа ночного прогона. Если правка трогает хэши, сохранения или сеть, узкий тест — это тест эталона именно этой системы (например, один `perf1*`, один `save4b*`), не весь набор.
4. **Проверка владельцем.** Если результат видно в игре, владелец проверяет: агент даёт точную проверку, составленную по данным мода (раздел 15, правило 11) (кого заспавнить в Cheat Mode, что сделать, что должно быть по оригиналу), проверки собираются в пачку не меньше пяти. Если в игре не видно, проверкой остаётся узкий тест.
5. **Аудит полей.** После теста и ответа владельца прогнать `tools/mod/field_audit.py` (команда в [audit/PROMPT-task1-field-check-2.md](audit/PROMPT-task1-field-check-2.md)) с `--manual <manual-check.tsv>` и найти строку поля. Нужен статус `used`, и `where` указывает на новое чтение. Старый ручной вердикт (`parsed-unused` до правки) перекрывает новый статус и выходит в `field-audit.md` списком конфликтов: после правки вердикт этого поля в `manual-check.tsv` меняется на `used` с новым `where` и коммитом правки в `note`.
6. **«Проверено».** Строка в [TOP20.md](TOP20.md) получает статус `проверено`, когда есть все три: узкий тест прошёл, владелец сказал «работает» (или в игре не видно и это записано), аудит показывает `used`. Без одного из трёх статус `исправлено, ждёт: <что>`.
7. **Журнал для ночного прогона.** Каждая перенесённая в `main` правка получает строку в [NIGHT_WATCH.md](NIGHT_WATCH.md): что изменено, местная правка или движка, что может сломаться и какие тесты ночью смотреть первыми. Строку пишет агент, который сделал правку, в той же ветке.
8. **Перенос в `main`** без ожидания других тестов: после «переноси» владельца, а у Claude — сам, с пометкой «проверить в игре» (раздел 4, «В `main`»). `agent_worktree.py sync` перед переносом остаётся.
9. **Ночь решает.** Ночной агент читает [NIGHT_WATCH.md](NIGHT_WATCH.md) до разбора прогона. Падение, которого нет в [TEST_BASELINE.md](TEST_BASELINE.md), сверяется со строками «ждёт ночи»: совпало с «что может сломаться» — строка получает `ночь: упало`, проблема в TOP20 снова `исправлено, ждёт: исправления падения`, запись P-<номер> в [PROBLEMS.md](PROBLEMS.md) и первая задача ветки, которая это внесла. Прогон прошёл — `ночь: прошло <дата>`, и `проверено` в TOP20 становится окончательным.

## 7в. Задачи локальных агентов (решение владельца 2026-11-07)

Принятый PR арены записывает Claude при приёмке (раздел 7б). Перед каждым слиянием upstream в форк строки сверяются с новыми коммитами upstream по порядку из этого документа.
- **Что считается ванильным** (решение владельца 2026-11-18). Цель: upstream — полный порт ванильного RotWK 2.01, форк — полный порт Эннората; форк со временем сжимается до того, чего в upstream быть не может. Поэтому в upstream идёт **любой код `game.dat` 2.01**, подтверждённый адресом RW и тестом на синтетическом INI, в том числе модули, поля и ветки, до которых доходят только данные Эннората (в ванильных INI у них нет пользователя). В форке остаются: поведение пропатченного exe Эннората (pySAGE), возможности форка, которых нет в upstream, визуальное без снимков «до/после», вердикты без кода, инструменты и документы Эннората. Шаблоны Port и Local (DashBoard `prompts/`) говорят то же.
- **PR в `Open-BFME` открывает только владелец или агент по его прямому выбору конкретной правки**: это публикация от его имени. Исключение (решение владельца 2026-11-17): цикл песочницы 4 (`tools/colab/upstream_loop.sh`, каждые 3 ч) сам открывает PR каждой ветки `up/*`, которую проверка `tools/upstream_pr.py check` признала готовой (`ready`) и у которой ещё нет PR в upstream (`upstream_pr.py open --ready`); ветки `visual` ждут снимков владельца, `fail` — доработки агента.
- **Как собирается PR в upstream** (2026-11-09, первая партия #274–#284). Дерево `workspace/wt/upstream-pr`, отцеплено на `upstream/main`; на правку ветка `up/<ключ>` от `upstream/main` с коммитами правки и её теста, пуш в `origin`, PR: `gh pr create -R Open-BFME/openbfme-godot --head Gleb302596555:up/<ключ>`. Правила upstream (их `CONTRIBUTING`/`REVIEW`): одна правка на PR; тест, который падает без правки; видимая правка — снимки до и после (такие ждут снимков владельца); сдвинутый эталон — комментарий `// pin:`; `tools/stops_count.py --write`; номера стопов уникальны (тест в CI); все редакции работают. Ловушки: `STOPS.md` не объединять со своим — брать файл upstream и добавлять только строку этой правки; в тексте PR и коммитов не писать `#N` (ссылается на issue upstream, писать «fork issue N»); заголовок и описание по-английски, по коду, а не по коммиту теста; `CMakeLists`/лейн-файлы не тянуть строки чужих портов. Не идут как есть: правки на API только форка, правки, двигающие эталоны upstream, правки с конфликтом исходников — их переносят руками. Следующую партию не начинать, пока владелец не скажет, что первая прошла.

- **Сравнивать с upstream по содержимому** (деревья и diff), а не по хэшам: синхронизация сжимает коммиты, и у совпадающего кода хэши разные.

## 14. Отчёт агента и проверка чужой работы

Отчёт проверяют по коду, поэтому всё в нём должно подтверждаться. Ошибочный отчёт считается незавершённой работой.

- **Только то, что проверено.** Хэш коммита проверить через `git cat-file -t`, имя теста скопировать из вывода, число взять из строки `[doctest]`. Вывод, сделанный только чтением кода, помечать `INFERENCE`, а не писать как факт.
- **Все порученные тесты по списку**, с результатом у каждого: прошёл, упал или не запускался. Сокращать фильтр из задания нельзя, а если тест исключён, сказать почему.
- **Изменённые ожидания и эталоны**: таблица «тест, было, стало, источник». Слова должны соответствовать diff: «заменено» и «удалено» нельзя называть «дополнено».
- **Причина**: коммит и механизм, с доказательством. Список возможных причин причиной не считается.
- **Осталось**: что не исправлено, что не проверено и что ждёт владельца. Строка с этим есть в отчёте всегда, даже если там «ничего».
- **Сборка**: на каком коммите собран `openbfme_tests.exe`. Прогон на сборке старше последнего коммита с кодом не считается.
- **Задание владельца или другого агента важнее догадки**: «не обновляй, пока не объяснено» нельзя выполнять частично. Если выполнить нельзя, остановиться и сообщить.
- **Матрица кнопок** (решение владельца 2026-11-16, после PR #587: отчёт умолчал о 54 кнопках, которые были PASS на `main` и стали красными). Кто меняет `docs/ennorath/MATRIX.tsv`, запускает `python3 tools/matrix_run.py diff` и даёт в отчёте его таблицу переходов. Каждая кнопка, которая была PASS и стала чем угодно другим, получает строку в `docs/ennorath/matrix_explain.d/<задача>.md`: `` `<объект> <кнопка>`: почему ``. Объяснять можно только настоящую причину: прежний PASS был ложным или новое правило нашло пробел, с названием модуля и доказательством. Ошибка своего теста не объясняется, а чинится. Проверяльщик PR запускает `diff` сам и ставит ❌ за необъяснённые строки. Новое правило зонда (`SweepEffectProbe`) ждёт эффекта нагета, только если у юнита выполнены `RequiredUpgradeNames` / `ForbiddenUpgradeNames` нагета и его снаряда, а цель проходит `SpecialObjectFilter` нагета (`+STRUCTURE`, `+MONSTER`, `+HERO`, `ENEMIES` / `ALLIES`). Если сцена такой цели не даёт, ей ставят свою цель под фильтр или снимают ожидание с пометкой в строке. Три ошибки #587 именно такие: дебафф Леголаса только с `Upgrade_GeschenkeLoriens`, паралич «Корней» только по строениям, ужас стрелы Дейла только на монстров.

При проверке чужой работы действует то же: прочитать код и сам перезапустить тесты, прежде чем подтверждать или обвинять. Причину падения или порчи файла не называть, пока она не проверена.

## 15. Жёсткие правила (решение владельца 2026-11-03)

Каждое правило закрывает ошибку, которая уже попала в `main`. Нарушение любого из них значит, что работа не готова, даже если тесты зелёные.

1. **Каждое изменённое поведение подтверждено инструкцией RW.** Адрес должен указывать на ту инструкцию или ветку, которая делает это поведение, и быть прочитан через `tools/mod/rw.py RotWK\game.dat dis`; в комментарии и в отчёте сказано, что там стоит. Адрес функции не подтверждает ветку внутри неё. Не нашёл — `INFERENCE` в комментарии кода и в отчёте, а `INFERENCE`, который меняет то, что игрок видит, слышит или чем управляет, переносится в `main` только после ответа владельца. *Было:* мигание стойки приписано общей функции SetStance (RW 0x96F53C), хотя его делает только клик по пункту (RW 0x96F85A); выбор крипа кликом и полоска здоровья у любого выделенного юнита добавлены без адреса.
2. **Одно действие игрока — одна реакция.** Прежде чем добавить обработчик клавиши, сообщения, события или хука модуля, найти существующий: `git grep` по типу сообщения (`MSG_*`, `CMSG_META_*`), клавише, имени события. Если путь уже есть, правится он, второй не добавляется. Тест проверяет число сообщений, звуков или вызовов на одно действие, а не только итог. *Было:* клавиши стоек зарегистрированы второй раз буквами поверх мета-команд CommandMap, одно нажатие давало два приказа и двойной голос.
3. **Причина, а не симптом** (правило владельца). В отчёте назван общий механизм, который был сломан, и почему он объясняет все похожие случаи. Особый случай для одного режима, объекта или кнопки допускается, только если в RW есть этот особый случай по адресу. Слой устройства (`engine/src/GodotDevice/`) не переопределяет решения ядра. **Чинится вся система сразу** (решение владельца 2026-11-04): найдя ошибку, агент ищет все места, где работает тот же механизм (те же данные, тот же разбор, то же допущение), и правит механизм так, чтобы одна правка закрыла все такие случаи; точечная заплатка на одно место, когда рядом остаются такие же, — недоделанная работа. В отчёте перечислено, какие ещё места проверены и что с ними. *Было (2026-11-04):* голос входа брал целью «первый ID объекта» в приказе; поправили только MSG_ENTER, а правильный путь — таблица «какой аргумент — цель» для всех приказов с голосом. *Было:* курсор при постройке чинили заплаткой в ядре и второй в Godot, а причина была общая: положение мыши уходило в поток только при движении (ZH `Mouse::createStreamMessages` шлёт его каждый кадр).
4. **Без молчаливых запасных путей.** Не найден файл, не разобрана строка, неизвестный ключ — ошибка в журнале, отчёте и тесте, а не значение по умолчанию. INI читается читателем движка и таблицами полей игры, свои разборщики не пишутся. Числа-маски и смещения — именованные константы с источником. *Было:* `DrawGroupInfo.ini` разбирался самодельным разборщиком, ошибка загрузки молча оставляла значения по умолчанию; маска `0x227` без имени.
5. **Новое состояние симуляции сохраняется в том же коммите**: `xfer`, блок в `GameLogic::registerSnapshotBlocks`, вклад в хэш, и `save4*` проходит, пока это состояние активно. *Было:* огонь попал в хэш без блока, любое сохранение во время пожара отказывало.
6. **Перенаправление существующего пути** (сообщение, приказ или событие теперь идёт в другую систему) сохраняет всё, что делал старый путь: счётчики, побочные действия, тесты старого пути. Каждый тест старого пути проходит или меняется с адресом RW рядом. *Было:* приказы атаки, строя и входа в здание ушли в очередь групповых приказов и перестали выполняться; 13 тестов упали в `main`.
7. **Ожидания теста — из RW и файлов мода, а не из нового кода.** Тест на своё новое поведение пишется так, чтобы падать без правки, и рядом стоит источник ожидания. Тест, изменённый в одном коммите с кодом, попадает в таблицу «было, стало, источник» (раздел 7). *Было:* тесты стоек проверяли мигание и лишние буквы, которые сам агент и добавил.
8. **Всё, что выбрал `test_select`, прогоняется** на сборке из последнего коммита. `FULL` значит полный прогон (можно ночью), обязательный набор его не заменяет. В отчёте первая строка `test_select` и список падений против `TEST_BASELINE.md`. Прогоны дольше 5 минут агент не ждёт; видимое владелец проверяет в игре, а невидимое (логика, хэши, сохранения, сеть) и любая правка самого движка переносятся только после своих тестов (раздел 7, «Правило пяти минут»); результат длинного прогона разбирается в любом случае. *Было:* очередь приказов и огонь ушли в `main` с прогоном одних своих тестов.
9. **Перед сдачей прочитать весь свой diff** (`git diff main...HEAD`) и в отчёте дать таблицу «изменённое поведение — адрес RW или файл мода — тест». Строка без адреса и без теста — недоделанная работа.
10. **Видимое и слышимое проверяет владелец**: в отчёте короткий список, что посмотреть в игре; `ВЫПОЛНЕНО` ставится после его ответа (разделы 6, 8).
11. **Данные сначала из мода, потом из ванили; последнее слово за Энноратом** (решение владельца 2026-11-05). Каждое утверждение о данных — кто использует механизм, какие значения у поля, какой список Lua-событий, какое тело или модуль у объекта — проверяется в таком порядке:
   1. **Мод**: архивы Эннората (`workspace/mods-en/Ennorath/install`). Объект, блок или файл мода целиком перекрывает ванильный с тем же именем. Закомментированное в моде поле (`;` / `//`) значит, что поле **отключено**, даже если в ванили оно задано.
   2. **Ваниль** RotWK 2.01 (`workspace/games-en/Vanilla_(2.01)/install`) — только для того, чего в моде нет, и с пометкой «из ванили, мод не перекрывает».
   3. **Вывод для владельца по Эннорату**: проверки в игре, ожидаемое поведение, список затронутых объектов. Ваниль в отчёте — отдельной строкой («в ванили иначе: …»), не вместо мода. Тест на ванильных данных (`ROTWK_INSTALL`) не подтверждает поведение в моде: нужен сценарий на данных мода (`ENNORATH scenario*`) или явная сверка объекта в архивах мода.

   Описание PR для основного репозитория (ваниль 2.01) — единственное исключение: там данные ванили, но и там мод упоминается, только если отличается. *Было (2026-11-05, буйство):* проверку «Mordor Attack Troll бесится при ранении» составили по ванильному `attacktroll.ini`. В Эннорате у тролля `AILuaEventsList = MountainTrollFunctions` (без `GoIntoRampage`), `RampageTime` закомментирован, тело `ActiveBody`: буйство в моде отключено.

12. **Видимое, что может тихо сломаться, записывается** (решение владельца 2026-11-09). Тесты не видят, что дошло до экрана (P-72: Лурц перестал краснеть под Fury, все тесты зелёные). Подтверждённое владельцем видимое или слышимое поведение — строка в `docs/ennorath/VISUAL_REGRESSIONS.md`; её добавляет тот, кто переносит правку в `main`. После партии, которая трогает отрисовку, материалы, тени, FX, звук или интерфейс, в список «проверить в игре» входят и строки этого файла по затронутым разделам.
13. **Не гадать, как правильно: смотреть в оригинальный мод и сверять** (решение владельца 2026-11-13). Прежде чем решить, как должно работать (курсор, кнопка, звук, эффект, приказ), агент находит, что делает оригинал: данные Эннората (INI, Mouse.ini, CommandButton, файлы в архивах и на диске установки) и код RotWK по адресу (`RotWK/game.dat`). Решение и отчёт строятся на этом сопоставлении «оригинал — порт» по каждой ситуации, а не на догадке или на том, что «выглядит логично». Если оригинал по коду расходится с тем, что владелец помнит по игре, агент не выбирает сам: даёт владельцу таблицу ситуаций с адресами и просит проверить спорные строки в оригинале. *Было (2026-11-12):* курсор P-15 правили по одной ситуации; владелец попросил сначала выписать все случаи курсоров по оригиналу, чтобы не исправлять второй раз.
14. **Карта механизма по оригиналу** (решение владельца 2026-11-13). Для механизма, где одно и то же решение принимается во многих ситуациях (курсоры, состояния кнопок, звуки событий, отсчёты, подсказки), агент один раз составляет карту: каждая ситуация — что ставит оригинал (адрес RW и строка данных мода), как это выглядит, что делает порт. Карта лежит в `docs/ennorath/<МЕХАНИЗМ>.md` (первая — `CURSORS.md`), правки механизма сверяются с ней и дополняют её; не прочитанные ещё строки помечены как непрочитанные, а не заполнены догадкой.

15. **«Кнопка ничего не делает» и «так задумано в моде» — только после проверки владельца в оригинале** (решение владельца 2026-11-18). Вердикт без кода по кнопке или эффекту, который виден в игре (нет эффекта, BY-DESIGN, «данные мода пусты»), не принимается по одним данным мода: агент пишет его в отчёт как кандидата, Claude заносит строку в TOP20 «проверить в оригинале» (кнопка, объект, что сделать, что ожидаем по разбору), кнопка матрицы остаётся красной, а объяснение в `matrix_explain.d/` появляется только после ответа владельца. Пустой список или пустой блок в данных ещё не значит «эффекта нет»: эффект может задавать код по другому полю или модулю. Вердикты «RotWK поле не читает» по невидимым полям остаются как были (цепочка чтения в RW, раздел 5, шаг 4). *Было (2026-11-18):* Port 278 объявил рог Боромира пустым (список модификаторов `BoromirGondorHornAntiCategory` без строк `Modifier`), Claude принял вердикт; владелец в оригинале: рог оглушает. Тот же пустой список «только для длительности» у 9 способностей (рог, Элендил, смех Короля мёртвых, Око Саурона).

16. **Правки exe мода (pySAGE) — сначала вид правки** (решение владельца 2026-11-22). Мод правит закрытый `game.dat` байтами, потому что иначе не может; у порта код открыт, поэтому переносится поведение, а не заплатка (`docs/ennorath/ENNORATH_EXE.md`, `tools/mod/pysage_dump.py`). Перед работой определить вид каждой правки и записать его в PR:
   - **Обход ограничения движка** (размер массива или маски, число игроков, слотов, улучшений, построек, кадров): проверить, есть ли такое ограничение в порте. Нет — записать с местом в коде («в порте ограничения нет: <файл:функция>») и ничего не переносить. Есть — снять его в общем виде; если это меняет симуляцию или сеть — за возможностью профиля.
   - **Исправление ошибки оригинального движка**: исправить по-настоящему, в общем механизме, но включать только возможностью профиля мода (`ennorath.*`): без профиля поведение ванильной 2.01 остаётся, иначе разойдёмся с оригиналом в сети и повторах.
   - **Новая возможность** (интерфейс, удобство, экран): строить нативно в порте по «контракту» экранов мода (что Apt вызывает и читает); чисто клиентское можно делать свободно, меняющее симуляцию — за возможностью профиля и в сетевой подписи (`MODS-3`).
   В режиме мода поведение совпадает с оригинальным модом (игрок порта играет с игроком оригинала, повторы сходятся). Улучшения сверх мода (больше кадров, игроков, удобства) — собственные настройки OpenBFME с явным включением, не возможности профиля мода.

## 16. Границы форка (решение владельца 2026-11-03)

Форк — это RotWK 2.01 с Ennorath, вместе с онлайн-игрой. Из основного репозитория приходят и исправления для BFME1, BFME2 и других модов: код остаётся, но работа форка их не касается.

1. **Порт только по RotWK.** Правка переносится и подтверждается по RotWK (`RotWK/game.dat`). Адрес BFME2 и перенос для BFME2 не требуются. Ветку кода BFME2 трогаем, только если её использует сама RotWK (RotWK стоит на данных и коде BFME2). Требование «обе редакции» в старых заданиях и стопах для работ форка больше не действует.
2. **Чужие тесты не гоняем и не чиним.** Тесты BFME1, кампаний BFME2 и других модов (Edain, Edain Unchained, Patch 2.02) перечислены в `tools/fork_scope.txt`. `test_select.py` добавляет эти исключения к каждому прогону, ночной полный прогон запускается с ними же: `openbfme_tests.exe` плюс строки файла. Их падения в `TEST_BASELINE.md` не записываются. Онлайн, кампания RotWK и Война Кольца остаются в наших прогонах.
3. **Слияние с основным репозиторием** берёт всё. Конфликт в чужой части (код и тесты BFME1, кампаний BFME2, других модов) решается в пользу основного репозитория, без разбора. Свои правки делаем только в общем коде и в том, что касается RotWK и Ennorath.

## 17. Карты, проверки и досье (решение владельца 2026-11-19)

1. **Карты** (все в `docs/ennorath/`, обновляются прогоном карт на песочнице 3 после переносов):
   - кнопки: `MATRIX.tsv` / `MATRIX_GAPS.tsv` (кнопка → модуль → функции без цитаты);
   - поля мода: `FIELD_GAPS.tsv` (поле без читателя → функции-кандидаты);
   - функции RotWK по модулям: `RW_FUNCTION_MAP.tsv` (статус `ported` / `partial` / `none`);
   - скрипты: `SCRIPT_MAP.md`;
   - карты игры (2026-11-20): `MAP_SWEEP.tsv` / `MAP_SWEEP.md` — каждая карта установки Эннората стартует скирмиш и играет 60 с, одна карта на процесс (`tools/maps/map_sweep.py`, тест `ENNORATH sweep maps`); ошибки сгруппированы по тексту, одна группа — один механизм; запускается руками (около часа на ПК);
   - модификаторы атрибутов: `MODIFIER_MAP.md`, `MODIFIER_READERS.tsv`, `MODIFIER_PORT_READS.tsv` (`tools/mod/modifier_map.py`: атрибут → списки мода → читатели RotWK → читает ли порт; таблица списков — на Drive, это данные мода).
   Связь: `MODIFIER_MATRIX.tsv` — красные кнопки матрицы со списками модификаторов их модулей и атрибутами, которые порт там не читает (кнопка «ничего не делает» из-за непортированного чтения); досье задачи сводит все карты по её классам.
2. **Свой тест до PR**: PR, который добавляет `TEST_CASE`, несёт в описании строку итога doctest каждого своего префикса (`PORT-N*: [doctest] test cases: N | N passed | 0 failed`). Нет строки — проверка GitHub Actions «Own test shown passing» и проверяльщик PR возвращают его сразу, без сборки (`tools/ci/own_test_check.py`).
3. **Одна функция — одна задача**: две открытые задачи не переносят одни и те же функции RotWK. Песочница 4 каждые 30 минут сверяет открытые задачи и PR (`tools/mod/task_overlap.py`: функции, которые задача переносит впервые); дашборд не выдаёт задачу, у которой с задачей в работе две и более общих функции, и помечает одну. Агент, чья работа уходит в функции другого открытого PR, ставит `status=stop`.
4. **Досье задачи**: карты — комментарий `<!-- dossier -->` к issue (GitHub Actions «Task dossier», `tools/ci/port_dossier.py`); дизассемблер функций задачи — с 2026-11-20 тоже GitHub Actions (решение владельца: песочница работает не всегда), `.github/workflows/dossier-disasm.yml` при правке issue и каждые 30 минут: `game.dat` и список функций расшифровываются на машине GitHub секретом `ARENA_KEY` из `refs/arena/files` и `refs/arena/inventory`, досье `tools/mod/dossier_disasm.py` шифруется тем же ключом в `refs/arena/dossier/<issue>`. Открытый текст досье, `game.dat` и список функций не попадают ни в лог, ни в артефакты, ни в ветки. Арена расшифровывает своё досье ключом из промта, локальные агенты — ключом `/content/sandbox/.arena_key` (есть на каждой песочнице). Бот досье на песочнице 3 снят.
6. **Сначала GitHub Actions, потом песочница** (решение владельца 2026-11-20). Каждый PR (не только из чужих форков) собирается в GitHub Actions, и там же идут его свои тесты `PORT-N*` / `LOCAL-N*` (`.github/workflows/fork-pr.yml`, задание «Fork PR: build and own tests», `tools/ci/fork_pr_check.py`). Проверщик в песочнице (`tools/colab/pr_checker.py`, `actions_check`) берёт PR этого репозитория, только когда это задание зелёное на голове PR: пока оно идёт — ждёт, красное — один комментарий в PR и PR не проверяется до нового push. Головы, запушенные до 2026-11-20 21:00 UTC (у них задания нет), проверяются как раньше. Песочница тратит время только на то, что требует файлов игры. Голову, запушенную до правила, можно проверить вручную: `gh workflow run fork-pr.yml -R Gleb302596555/openbfme-godot --ref main -f pr=<номер>` — отдельное задание без кода PR кладёт результат на голову PR под тем же именем (PR в конфликте с `main` тоже получает красный). Тяжёлые проверки upstream («Pull request checks», «Sanitizers»: сборки Linux, Windows, macOS, санитайзеры) в форке с 2026-11-21 не запускаются на PR, только на push в `main` и вручную (решение владельца: они занимали все 20 параллельных заданий GitHub, и сборка, которую ждёт песочница, стояла в очереди; форк их результаты не читает).
7. **Правила PR проверяет GitHub Actions** (решение владельца 2026-11-20): `.github/workflows/pr-rules.yml`, задание «PR rules: description, test sources, citations», `tools/ci/pr_rules.py` (берётся из `main`, не из PR) — за секунды, без сборки, при открытии PR, push и правке описания: (1) в описании Port PR есть «в игре», «местная правка или движка», «Осталось», «Карты», в Local PR — «в игре» и «Карты»; (2) у каждого нового `TEST_CASE` есть источник ожиданий (`RW 0x…`, файл INI мода или игры, `DONOR`, `INFERENCE`) в его строках, в комментарии над ним или в шапке нового файла тестов (правило 15.7); (3) блок нового кода в `engine/src` без адреса рядом — предупреждение; (4) ветка `up/*` без `#N` в коммитах и добавленных строках. Красное — проверщик в песочнице PR не берёт (как и красную сборку, п. 6), дашборд показывает причины. Холостой прогон по 21 открытому PR 2026-11-20: правилу (1) не отвечали 14, правилу (2) — 3 PR; текущие головы проверка заденет при следующем push или правке описания.
8. **Почтальон PR доверенных участников** (решение владельца 2026-11-21): агент доверенного лица на платформе с токеном, который видит только его форк (`gh pr create` → 403), пушит в свою ветку `trusted/*` или `arena/*` пустой коммит-сигнал `PR READY: <заголовок>` с описанием PR; `.github/workflows/trusted-pr-relay.yml` (раз в 15 минут, `tools/ci/trusted_pr_relay.py`, только API GitHub — код форка не запускается) открывает PR без права правки мейнтейнерами и вручную запускает сборку `fork-pr.yml` (PR, созданный токеном Actions, сам проверки не запускает).
