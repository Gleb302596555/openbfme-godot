# Port 272 / P-116: какая пара строк доходит до экрана

Ennorath 1.9.8.3: у `FactionMen` → `GondorTrebuchet` → `GondorTrebuchetCommandSet`, позиция 2 — `Command_ToggleTrebAutoAcquire`. Это **кнопка дуги палантира**, `TOGGLE_NO_AUTO_ACQUIRE` с `TOGGLE_IMAGE_ON_WEAPON`, двумя изображениями, двумя `TextLabel` и двумя `DescriptLabel`. Проверены объект, набор и кнопка в INI мода. `PASS` этой кнопки в `MATRIX.tsv` проверяет приказ, не текст на экране.

## От наведения до рисования в порте

1. `InGameHud::mouseMove` передаёт координаты в APT. В каждом `InGameHud::update` сначала обновляется `ControlBar`, затем `updateHud6` → `hoveredAptButton` берёт путь **текущей** кнопки APT, `AptPalantir::contentSlotAt` сопоставляет его со слотом, HUD читает запись слота этого кадра. Новое событие мыши для этого чтения не нужно. Штатный `_OnPress` в `AptPalantir::syncFrames` через `whenHeld` вызывает `dispatchPalantirButtonPress`: снятие провайдера, затем обычный приказ и прогноз индекса. Изображение и оба ключа в `ControlBarButton` обновляет Port 189.
2. Старые строки держал **`InGameHelpBox::showHelp`**: он решал, заменить ли `m_help`. Снятие провайдера не снимает уже нарисованную подсказку. В первом обновлении после клика новый провайдер лишь устанавливался, а `render` в состоянии 4 ещё рисовал **предыдущий измеренный** `CommandButtonHelp`. И после показа, если состояние кнопки менялось под тем же курсором, ветка `m_shownForProvider` возвращалась до `compose`: свежая запись слота сама по себе уже не могла изменить этот текст. Это два разных случая: ожидание после клика само по себе не объясняет бесконечную задержку.
3. `CommandButtonHelp::composeRetail` переводит ключи из записи слота; при показе `setWidthAndComputeHeight` разбивает строки на линии. `HudDevice::drawPlaceholder` → `Hud6Draw::drawHelp` → `InGameHud::helpBoxRender` → `InGameHelpBox::render` → `CommandButtonHelp::render` отдаёт эти линии как `HelpDrawOp::TEXT` в `Font::draw_string`. Godot не выбирает подпись по иконке. Даже при повторном использовании canvas item `redrawNativePlaceholders` очищает его и вызывает нативную отрисовку снова. `WindowManager::updateTooltip` выбирает другой текст — подсказку курсора меню, а не содержимое рамки палантира.

`PORT-189` напрямую предлагает провайдер по имени кнопки и после клика проверяет `help()->name()/longText()` **после двух** кадров. Функция измерения в этом тесте возвращает константу; тест не читает линии, которые в первом кадре получает Godot.

## Что действительно делает оригинал

Проверено дизассемблированием предоставленного RW 2.01 (`game.dat`, MD5 `daed3668006cd90f01c34e5a7da1901f`; оговорка о происхождении образа — S-001). Адреса RW — VA, адреса донора ниже — RVA, как в исходниках донора.

| Ситуация | Ветка RW |
|---|---|
| Допустимый клик | `RW 0x9D2814`: после проверки окна `0x9D282D` снимает провайдер **до** уведомления `0x4008`; справа аналогично `RW 0x9D288A`, `0x9D28A3`. `RW 0x8076CD` обнуляет `+0x21C`, освобождает `+0x2AC` и просит hide-soon. Отказ слева в `RW 0x9D285E` не идёт этим путём. |
| Индекс кнопки | `RW 0x940435`, case `0x941335..0x941367`: один `0x45B` с ID, затем `RW 0x75D366(id,1)` → `RW 0x75D22E`. При двух изображениях `0x75D2BB..0x75D2E1` (опция `0x800000`, команда `0x30`, статус `0x17`) → `0x75D319`: индекс `status == invert`. В `RW 0x941BA0`, `0x941C14..0x941C1D` обновляется изображение. |
| Провайдер | `RW 0x9D2D45` → `RW 0x807A00`: команда из окна. `RW 0x807848` → `RW 0x8075A3`, `RW 0x8075F5` сравнивает **окно и кнопку, не индекс**. Равный помечает кадр; `0x8078CA` уже использован → выход; иначе `0x8078ED` ждёт строго `now > start + delay`. Новый клон сбрасывает часы и признак показа (`0x807955..0x807960`). `0x807971..0x80798D` потребляет запрос до поздних запретов и вызывает `RW 0x807676` (vslot `+0xC`). |
| Новый текст | `RW 0x807A81` читает кнопку провайдера: `0x807D9C/0x807DBB` → `RW 0x75CECD` (описание), `0x807EB3` → `RW 0x75CE47` (имя). Индекс `+0xFC`; последний элемент за пределами списка, пустой для пустого списка. Отдельное непустое переопределение имени `+0x7C` — существующий S-7335. |
| Что видно | `RW 0x92E229` (3 → 4 на пять обновлений); `RW 0x92E2AC`, `0x92E2E3..0x92E2FA`: в 3 **и 4** рисовать сохранённый `+0x1C`. `RW 0x92E570` заменяет его через `RW 0x92E362`; `RW 0x92E462` в `0x92E49E..0x92E4FA` измеряет новую подсказку и вызывает `Show`. `RW 0x974795` рисует подготовленные строки, не выбирает другой индекс. |

Донор: DONOR BFME2 0x005C33DD (`Rva005C33DDWindowNotification.cpp`), 0x00405C04 (`Rva00405C04Show.cpp`), 0x00405E3D (`GUI/GUICallbacks/OldSchoolHelpBoxContentSource.cpp`), 0x0056CCE2 (`InGameCommandButtonHelpRender.cpp`). Источник порядка и условий — RW, не имя функции донора.

**Граница переноса.** Нужна актуализация *содержимого уже видимой той же кнопки*, не повторный клик, не новый hover, не безусловный перевод строк на каждом кадре и не изменение равенства провайдеров. INFERENCE для раздельных обновлений HUD/логики порта: если в рамке ещё рисуется эта команда, заменить подготовленный текст при изменении пары эффективных ключей уже в текущем обновлении. У RW нет отдельной проверки «индекс изменился» в сравнении провайдеров; обычный путь после клика заново выдерживает задержку. Первое наведение, другая кнопка, уход курсора и запреты показа не должны получить ускоренный первый показ. Проверка без файлов игры заканчивается на строках для отрисовки; это не захват пикселей и не установление порядка кадров в сеансе владельца.

## Проверка места отказа

Синтетическая карта с одним своим объектом; в памяти загружаются INI и фильм с кнопкой в `CommandButtons.Command2.content`. Нажатие проходит через сетку попадания APT, `_OnPress` и обработчик палантира; тест не подставляет провайдера и не вызывает `showHelp` вручную. Переводы придуманы для теста. Сняты `HelpDrawOp::TEXT` из `InGameHud::helpBoxRender` и имя нативного изображения из `AptPalantir::imageFor` в **одном** обновлении.

- Без трёх файлов исправления первый клик меняет изображение на `ToyStart`, но отдаёт на рисование **Cancel watch / Wait for orders.**, а не **Resume watch / Look for targets.** Обратный клик даёт обратное расхождение. Сам приказ ушёл один раз; следующий отложенный показ уже мог догнать картинку. При изменении состояния объекта после того, как провайдер был использован, старое содержимое держалось все четыре проверенных кадра. Это подтверждение двух ветвей отказа в клиенте, не утверждение о числе кадров в сеансе владельца.
- Отдельная мутация — вернуть только `updateHud6` к вызову без текущей записи слота, оставив остальной новый код и весь итоговый тест, — даёт те же **2 из 4 случаев, 14 из 164 проверок** красными. При возврате записи — **4/4, 164/164**. Независимые проверки: одинаковый заголовок или одинаковое описание, неподвижный курсор после подтверждения логикой, первое наведение на границе задержки, выход/вход во время скрытия, поглощение запроса при DisconnectMenu.

**Отдельное наблюдение, не диагноз P-116 — S-7457.** `AptPalantir::syncFrames` может переслать прежнее состояние при новом изображении. В `RW 0x9D2B49` вызовы независимы: `0x9D2B96` → установка картинки (`RW 0x9D7154`, равная пропускается в `0x9D7168`); `0x9D2C6E` → установка состояния (`RW 0x9D7109`, равное пропускается в `0x9D711A`, вызов фильма `0x9D7144`). DONOR BFME2 0x005C7B96 (`Common/AptImageKeySetters.cpp`). В синтетическом фильме цель APT сохраняется; для оригинального фильма мода влияние повторного `SetState` на его таймлайн не измерено. Общий контроллер фильма не менялся.
