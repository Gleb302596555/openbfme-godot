# Кандидаты в PR в основное репо (Open-BFME)

Здесь записаны правки форка, которые исправляют поведение **ванильного RotWK 2.01** (общий код движка, а не данные или привязку к Эннорату). Каждая такая правка может уйти в upstream отдельным PR. Документ нужен, чтобы быстро найти код, который нужно отправить, и не потерять его при слияниях. Порядок работы — раздел 12 [PROCESS.md](PROCESS.md).

## Что сюда попадает

- Правка движка или клиента, которая приближает поведение к RotWK 2.01 и не зависит от мода: перенос ветки RW, исправление ошибки порта, недостающий механизм, сборка на других платформах.
- **Не попадает**: данные и проверки только для Эннората, документы процесса (`docs/ennorath/*`), задачи арены по разбору полей без кода, отчёты ночных прогонов.
- Пересъёмка эталонов (`*.hashes`, закреплённые числа в тестах), сделанная из-за правки, записывается в той же строке: без неё PR в upstream красный.

## Как вести

- Строку добавляет тот, кто переносит правку в `main` (раздел 7а или 7б), **в той же ветке**, до переноса. Принятый PR арены записывает Claude при приёмке.
- **Решение**: короткое имя, по которому его найдут (TOP20 #N, P-N, PORT-N, S-N), и что исправлено.
- **Дата**: день переноса в `main`.
- **Автор**: кто сделал правку: `Claude (station-N)`, другой локальный агент (`agent/<имя>/...`), `арена` (облачный агент), владелец.
- **Где**: PR арены (`#N`), коммиты (короткие хэши) и ветка, из которой они пришли. Сопутствующая пересъёмка эталонов — отдельно, в той же ячейке.
- **Проверено**: тест-фильтр и проверка владельца в игре (`ждёт` / `проверено <дата>`).
- **Upstream**: `не предложено` → `PR #N <дата>` → `принят <дата>` / `отклонён <дата>: причина` / `уже есть в upstream <коммит>`.

## Проверка при слиянии upstream в форк

Когда владелец говорит перенести новые коммиты из основного репо в форк, до слияния:

1. `python tools/mod/upstream_sync.py status` — какие коммиты и конфликты придут.
2. Каждую строку со статусом `не предложено` или `PR #N` сверить с новыми коммитами upstream **по содержимому** (файлы и diff, не хэши: синхронизация сжимает коммиты):
   - то же исправление уже пришло из upstream → статус `уже есть в upstream <коммит>`; при конфликте берём версию upstream, если она ведёт себя так же, иначе разбор;
   - upstream изменил те же места по-другому → строка в отчёт владельцу: конфликт и чья версия ближе к RW;
   - не задето → остаётся кандидатом.
3. После слияния: правки, которые остались только у нас, перечислить владельцу списком «можно отправить» (решение об открытии PR — только его, раздел 12).
