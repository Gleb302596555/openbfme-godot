This is a declared route, not verified actual gameplay; RW generic delivery `0x8840FC`, upgrade dispatch `0x8B8E2E`, replacement `0x8B1690 -> 0x8B140D`, named timers `0x8B12BF -> 0x897368` are generic evidence. The base is explicitly excluded from the carrier-attachment filter (`_gamedata.inc:31`); that does not preclude delivery by another carrier.

Their effective inherited ring modules and other overrides require resolution; do not assume each stage has an identical active path. The base's `CreateObjectDie` names `OCL_TheOneRing` and lists two `UpgradeRequired` names (`:1540–1544`); `WildShelobRing` names the same OCL without that field (`:2919–2924`). This alone does not establish death gating semantics, duplicate prevention or respawn.

## Light-eating: a known writer, not an absent mechanic

The ring form's `SpecialPowerKankraLichtfresserin` applies `LichtfresserinSelfModifier` to itself (`:2598–2618`); that literal modifier has `Duration = 5000`, `AUTO_HEAL 250` and `Upgrade = Upgrade_TestBuilding Delay:100` (`includes/attributemodifier.inc:11301–11306`). The upgrade is OBJECT (`upgrade.ini:10–16`), and `ModelConditionUpgrade` sets `USER_2` in response (`wildkankra.ini:2619–2623`). Three buttons require `EnableOnModelCondition = USER_2`: web, blink and cocoon (`includes/commandbutton.inc:43201–43242`); blink additionally disables on `RIDER5`. Their own level, pause/recharge and targeting conditions remain independent.

This chain was already analyzed and ported upstream as **PORT-286** (`docs/re/rotwk/PORT-286.md`, branch main `adbccb1f`), so it must not be reimplemented here. Its generic RW evidence is self modifier `0x897987 -> 0x8977BF`, `Delay` parser `0x8050D3 / 0x805154`, pool schedule/grant `0x805A8E / 0x80585F`, model-condition upgrade `0x8BA668`, and HUD gate `0x942733 -> 0x942490`. The existing `PORT-286: self cast grants the model-condition upgrade only on the pool's delayed wake` test checks a synthetic self-cast, delayed OBJECT upgrade, `USER_2`, gated button, idle neighbor, and an immediate-grant contrast; it uses different delay/duration numbers and is **not** an actual Shelob INI or full three-button test. An initially sleeping pool can wake by the modifier duration rather than exactly at the nominal grant deadline; other pool wakeups can change the observed time. Do not assert `Delay:100` means an unconditional visible toggle at 100 ms.

The generated main `adbccb1f` matrix marks the three gated commands **DISABLED**, explicitly saying the sweep could not set `USER_2`; this is not proof the buttons are broken, and the existence of an upstream synthetic generic test does not by itself prove the full mod sequence works. The matrix sees the light-eating self modifier and a model condition on the caster, but the recorded condition is not a demonstration that all three gated buttons can subsequently be pressed and their effects verified. A future actual-data scene must cast light-eating, wait for its real upgrade/condition path and independently establish each command's level, recharge, target, dispatch and result; do not force the bit and call the producer tested.
