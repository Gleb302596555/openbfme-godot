# Port 5: ChargeAttackSpeedBoost — анализ RotWK 2.01

Рабочая запись по issue #57. Адреса ниже прочитаны через `tools/mod/rw.py dis` из RotWK 2.01 (`game.dat`, MD5 `daed3668006cd90f01c34e5a7da1901f`). Это не отметка о завершённом переносе.

## Флаг и включение

- RW `0x851A1E`: конструктор данных записывает 0 в `+0xB2`; таблица поля находится по `0xC56190`, парсер — `0x42E558`.
- RW `0x85406B–0x854074`: ветка `0x8547C5` выбирается для типа способности `0x2A` (`SPECIAL_CHARGE_ATTACK`), а не для всех способностей с этим полем.
- RW `0x8547C8–0x8547D3`: без AI ветка немедленно заканчивается. RW `0x8547D9–0x8547EB`: при выключенном поле или уже выставленном байте модуля `+0x82` установка пропускается. Иначе RW `0x8547F0` записывает 1 в байт модуля; RW `0x8547F3–0x854803` выставляет бит `0x10` объекта `+0x11C`, если он ещё не выставлен, и оповещает объект через `0x68B53C`. Это `CHARGING` (индекс модельного состояния `0x84`).
- RW `0x854808–0x85481A`: независимо от флага ускорения, но только при наличии цели и AI, вызывается RW `0x852DC5(target, 2)` и выставляется байт модуля `+0x83`. RW `0x852DD6–0x852E00` формирует AI-команду `0x48` с целью и указанным источником. Цель не требуется для установки `CHARGING`.

## Сброс и сохранение

- RW `0x8530D5` вызывает помощник `0x851BCF` в начале завершения способности. RW `0x852F04` вызывает его также при начале новой способности, после проверки шаблона. RW `0x851BD7–0x851C11` строит и очищает маску **из 14** модельных состояний; среди них RW `0x851BF0` добавляет `0x84` (`CHARGING`). RW `0x851C16–0x851C3D` дополнительно очищает настроенную `CustomAnimAndDuration` при нулевой длительности и обнуляет таймер модуля `+0x84`. Не заменять эту общую операцию одиночным сбросом флага ускорения.
- RW `0x5E3B79–0x5E3B9B` передаёт маску очистки и пустую маску установки в RW `0x68D607`; RW `0x671F99–0x671FA3` выполняет `(старые & ~очищаемые) | устанавливаемые`. Уведомление делается при изменении RW `0x68D632–0x68D63F`.
- RW `0x8533B2–0x8533D4`: если байт `+0x82` установлен, AI при его наличии получает idle с источником 2, а байт модуля затем обнуляется даже без AI. Очистка `CHARGING` уже произошла в начале завершения, до idle.
- RW `0x85288D–0x8528A7` сохраняет оба байта модуля `+0x82` и `+0x83` через Xfer slot `0x90`. В порте они уже в `xfer`, но отсутствуют в `crc`; изменение использования требует проверить сохранение и хэш при активной способности.

## Скорость и движение

- RW `0x5E3EF7–0x5E3F45`: при включённом `ChargeAvailable` статусы атакующего или ведомого разрешают заряд; иначе/дополнительно нужны **оба** `Object +0x251` и модельное состояние `0x84` (RW `0x5E3F26–0x5E3F3D`). RW `0x5E3F82–0x5E3FD5`: повреждённый объект без `ChargeIgnoresCondition` использует `MaxSpeedDamaged`; в другой ветке ускорение умножает скорость набора локомотора на `ChargeSpeed` и длительность кадра; затем применяется ограничение скорости.
- `Object +0x251` не является доказанным временным приказом: RW `0x699AC6` обнуляет байт при создании объекта, RW `0x69A536–0x69A549` выставляет его, если RW `0x68C461(object, 0x2A)` находит интерфейс обновления способности такого типа (тип читается через RW `0x851D10`). В порте `AIUpdate.cpp` сообщает `false` для `isChargeOrdered`, что не воспроизводит эту ветку.
- Для обычного AI конструктор RW `0x66ED41` записывает vtable `0xC10590`; после AICommand `0x48` диспетчер RW `0x66AAA9–0x66AAB1` вызывает слот `0x48` этой таблицы, RW `0x66434E`. При отказе из-за AI-dead или неподвижности приказ не меняет машину; иначе локомотор очищается, старая машина очищается, сохраняются цель и источник и запускается состояние `0x3F` (RW `0x66436B–0x6643AD`).
- При подходе к заданной позиции, а не объекту, RW `0x853B5D–0x853BDE` при ненулевой позиции и наличии AI посылает `0x852D59(position, 2)`, формирующий команду `0x47`, и только для типа `0x2A` выставляет байт `+0x83`. Путь к объекту RW `0x853B4B–0x853B58` тоже использует команду `0x48`; не считать вызов из эффекта единственной дорогой к движению.
- Определение состояния `0x3F`: RW `0x753823–0x75384E` → конструктор `0x741A7B` → vtable `0xC28560`. Вход — слот `0x10`, RW `0x74E259`, обновление — слот `0x18`, RW `0x74943C`, выход — слот `0x14`, RW `0x74933F` → `0x748D8A`. Это **не** обычное состояние движения 1: у него vtable `0xC28518` и другие вход/обновление.
- В состоянии `0x3F` RW `0x74943F–0x749475` при ненулевом байте `+0x50` сравнивает текущий кадр с сохранённым `+0x4C`: после срока возвращает -2, иначе условно очищает у объекта бит `0x20` по смещению `+0x113` и возвращает 0. При нулевом байте RW `0x749476–0x749492` обновляет позицию цели и передаёт управление общей функции движения `0x748E46`. RW `0x741A8C–0x741A96` инициализирует оба поля нулём; RW `0x741A5C–0x741A6F` передаёт их в Xfer. Общая функция движения вызывает виртуальный слот `0x44` RW `0x7491DC–0x7491E0`: для vtable `0xC28560` это RW `0x749344`. Там, если проверка RW `0x6FB754` и последующая RW `0x745C6C` обе ответили нет, RW `0x7493B5–0x7493CA` ставит `+0x50` и срок `+0x4C` равным текущему кадру плюс десять раз глобальное значение `0xD9F608`. Точный смысл и необходимые условия двух проверок ещё не прослежены.
- RW `0x854F20–0x854F8A`: для типа `0x2A`, если AI idle и цель мертва либо байт `+0x83` уже установлен, локальный признак окончания ставится даже при занятой упаковке. Полные переходы упаковки и движения ещё необходимо сверить перед реализацией.

## Незавершённое

Проследить и перенести все ветки состояния `0x3F`, включая ожидание и обновление цели, а также соответствующие пути GiantBirdAIUpdate; выяснить жизненный цикл Object `+0x251` при изменении модулей/загрузке. Сверить завершение `0x2A` после перехода AI в idle и все затронутые общие пути. Тесты на синтетических данных, код, NIGHT_WATCH и PR ещё не сделаны.
