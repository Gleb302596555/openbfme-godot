# PORT-238: Angmar Witch-king New (partial trace)

Sources are the local Ennorath 1.9.8.3 INI archive MD5 `c53b6dea885cab044f80e783565f41f3`, paths relative to `data/ini`, and vanilla RW 2.01 `game.dat` MD5 `daed3668006cd90f01c34e5a7da1901f`. Main `c6cbb9a7` reports the main mod INI archive unchanged through 1.9.8.5; that archive is not locally available for independent comparison. Literal names and synthetic tests are not proof of effective loading, gameplay or appearance. `AngmarWitchkingNew` / `AngmarWitchkingNewRing` in `object/evilfaction/units/angmar/new/angwk.ini` are **not** the separate `AngmarWitchking_mod`, `_modRing`, `_MountedRing` and `_mod_RingHero` in `angmarwitchking.ini`; those remain to audit.

## Delivery, marker and replacement

The base's contain (`angwk.ini:989–1003`) checks `HOLDING_THE_RING`, destroys `TheDroppedRing`, and grants the OBJECT upgrades `Upgrade_RingHero` and `Upgrade_FortressRingHero` (`upgrade.ini:181,198`). `Upgrade_RingHero` triggers `DoCommandUpgrade` and an `ObjectCreationUpgrade` with `Delay = 0`, `ThingToSpawn = AngmarWKRingBearerMarker` (`:1046–1057`). `Command_SpecialAbilityAngmarWKRingGain` names `SpecialAbilityWagonMounted` (`includes/commandbutton.inc:53136`); the unpaused starter and `ToggleMountedSpecialAbilityUpdate` target the separate `AngmarWitchkingNewRing`, unpack 2000 ms and synchronize `KampfschreiEffectWK`, `CurseEnemy`, `WkIceTomb`, `WordOfPower` (`angwk.ini:1026–1044`). Those names occur on both base and ring object, but real pause/identity/timer transfer has not been tested here. The ring object also declares a `DoCommandUpgrade` with the **same** trigger and a toggle whose `MountedTemplate` is itself (`:2884–2905`); whether it can be activated after replacement, re-trigger, or loop depends on actual upgrade propagation and is not established. S-7321, S-7446 and S-861 remain.

`AngmarWKRingBearerMarker` is a ChildObject of `Held1RespawnLevel` (`object/projectile.ini:7580–7611`). Its `GrantUpgradeCreate` overrides the parent's same tag to grant `Upgrade_AngmarWKRingBearer`, which is a PLAYER upgrade (`includes/upgrade.inc:704`); the parent declares zero lifetime and slow death. Four later `CommandSetUpgrade` modules on Angmar fortress (`object/evilfaction/structures/angmar/angmarfortress.ini:1092–1111`) select a ring set for no subfaction or one of three choices, the latter requiring both player upgrades. Each ring set puts `Command_SpecialAbilityAngmarGiftFortressPassive` in slot 7 (`commandset.ini:4219–4230,4264–4275,4300–4311,4336–4347`). This is not a claim that the icon, removal or gameplay has been verified.

ObjectCreationUpgrade's donor match is limited to constructor and removal (`ObjectCreationUpgrade.h`); RW `0x8B8221` identifies the class, `0x8B8281` queues its update and `0x8B8464` creates `ThingToSpawn`, runs its create modules and grants/removes named upgrades. `GrantUpgradeCreate` on-create `0x8BD15E` and on-build-complete `0x8BD1D4` select player/object delivery (`0x8BD1AE` / `0x8BD1FD`) and grant the player upgrade via `0x6AEE22`; `CommandSetUpgrade` applies its set at RW `0x8B7C68`. Existing engine paths are `ObjectCreationUpgrade.cpp`, `UpgradeModuleClasses.cpp` and `GarrisonContain.cpp`; this trace does not port an alternate ring-only mechanism.

`PORT-238 Witch-king-style delivery*` tests a synthetic carrier delivery, marker ChildObject overriding its parent's grant, and automatic base→ring replacement together. Its two fortresses have different owners. Seven subcases cover no choice and each of three choice upgrades before or after hand-over; the owner's command-set name changes to the corresponding ring set, the other player's does not, and the correct player upgrade remains after the synthetic marker and original hero are removed. The synthetic ring form also declares the self-targeting command and a second PLAYER HQ upgrade: after ordinary replacement the object lacks the OBJECT ring upgrade, the HQ upgrade belongs to the right player, and no spontaneous self-replacement is observed for 15 frames. Explicitly giving the OBJECT ring upgrade to that synthetic form causes one self-replacement; its successor lacks that upgrade and survives another 15 frames. This is not real reacquisition or proof of unbounded behavior. It passes **366/366** assertions; the whole isolated `PORT-238*` suite passes **26/26 tests, 1333/1333 assertions** on matching `3f0105c8` core/headers with only the upstream PORT-286 parser separately compiled. Substituting the parent marker in the earlier fixture fails seven required upgrade checks (220/227); removing only the synthetic ring form's self-targeting `DoCommandUpgrade` in the current fixture fails seven self-replacement checks (338/345). Both are fixture-sensitivity controls, not code-fix controls. The test uses simplified command sets and replacement and does not load the real mod, verify a visible slot-7 icon, test all choices simultaneously, or test revocation, another acquisition, save/load, HUD reachability, death/drop or an actual game.

The ring form declares a separate `GrantUpgradeCreate` for PLAYER `Upgrade_AngmarStructureHQBuild` with `GiveOnBuildComplete = Yes` (`angwk.ini:2570–2573`, `includes/upgrade.inc:1740–1742`). Other named Angmar heroes use that upgrade; it is **not** the `Upgrade_AngmarWKRingBearer` marker. The synthetic test checks only that a separate HQ PLAYER upgrade is granted on completion to the replacement owner, not its real name or downstream effects. Full cross-object effects, lifetime and removal of both upgrades have not been proven.
