# Port 287 · выбор отряда и натиск

Проверены RotWK 2.01, BFME2 1.06 (донор) и INI с включениями из архива Ennorath 1.9.8.3. У «Натиска» обнаружился **другой CommandButton у выбранного отряда**. Эта часть задачи #669 сдаётся отдельно. Остальное остаётся в S-7502; исходный разбор и диагностические пробы сохранены в черновой ревизии `c74ef879`.

## 1. На чьей панели находится кнопка (обе редакции)

В `SelectionTranslator::leftClick` (RW 0x83C340) вызов `iterateDrawablesInRegion` передаёт `addDrawableToList` (RW 0x7108F2). Это **один** callback и для точки (RW 0x485B80, вызов RW 0x485D6F), и для рамки (обход drawable в той же функции). DONOR BFME2 0x70F14C (`GameClient/Rva0030F14CSelect.cpp`); ветка сверена на обоих `game.dat`.

- RW 0x7108F9–0x71096B: список, битовые маски типа drawable, специальные запреты и `CanSelectDrawable`. RW 0x71097D–0x7109CC: проверка тумана и невидимого drawable, включая принадлежащий отряду (`getHordeObject(false)`, RW 0x693A1A). Это ещё не выбор представителя.
- RW 0x7109CE–0x710A09: поиск объекта по **`Object + 0x78` (producer ID)**, независимо от `ContainedBy`. Нет ID, объект по нему не найден либо не `HORDE` — продолжается обработка исходного drawable. Если найденный `HORDE` имеет `UNSELECTABLE` (статус 3), отвергается весь кандидат; иначе callback заменяет и объект, и drawable на отряд. BFME2: та же проверка в 0x70F228–0x70F263.
- RW 0x710A0C–0x710A4F: далее читается `SelectionPriority` уже представителя и в список заносится его drawable. Путь двойного щелчка (RW 0x81F791) и объект-цель приказа под этот callback не подпадают.
- До исправления `HudObjects::pickForSelection` подменял через `ContainedBy`, а рамка читала `ProducerID` только внутри проверки `ContainedBy`. Обычный сформированный отряд и до правки выбирал правильный набор. Связи могут разойтись: RW 0x872D0A пишет ID производителя через RW 0x68B6A1; выход на время перехода в гарнизон (RW 0x86EBF4, слот 0xA8 интерфейса отряда) снимает контейнер, сохраняя производителя. В порте это `HordeContain::releaseMemberForGarrison` → `removeMember(keepSlot)`. Теперь `HudObjects::selectionListObject` применяет правило производителя к точке и рамке, не меняя выбор цели приказа. Это исправление входа в панель, не перенаправление каста; оно не доказывает, что владелец нажимал старую кнопку отдельно стоящего бойца.

## 2. От доступности до исполнения

| Этап | Что читает и делает RotWK 2.01 |
|---|---|
| `getCommandAvailability`, RW 0x942733, ветка RW 0x943343 | `ShowButton`, шаблон и активный хозяин; перебирает науки до первой принадлежащей игроку, без подходящей скрывает, выключенная/скрытая наука запрещает. Проверяет `PreventActivationConditions` и `UnitCost` у интерфейса отряда (RW 0x94341F–0x943480). |
| Поиск в той же ветке | RW 0x943486 ищет свой модуль по шаблону через RW 0x68C26D. RW 0x94349A–0x9434F4 отдельно может сменить шаблон по команде цепочки `SpecialAbilityUpdate`, найденного по типу (RW 0x68C461 / RW 0x851371). Без модуля цикл `CommandTrigger` смотрит только кнопки `SPECIAL_POWER`; выходы из цикла ведут к доступности `1` (RW 0x9434F7–0x943564 → RW 0x942FF1). Это не исполнение. С модулем: требования, готовность, процент перезарядки, условия модели и ветка `BattlePlan` (RW 0x943569–0x943606). |
| `processCommandUI`, RW 0x940435 | Кнопка должна быть кликабельной. RW 0x94070F — проверка готовности специальной команды; RW 0x940877 — адресные `Options` переключают режим выбора цели. Для обычного левого нажатия без цели RW 0x94153C посылает `MSG_DO_SPECIAL_POWER` со своим ID силы и `Options`, оба ID объектов нулевые; цикл RW 0x94157D–0x941618 добавляет команды из `CommandTrigger` с типом `SPECIAL_POWER`. Правая кнопка для `AutoAbility` (RW 0x9414E7–0x941537) отправляет иной приказ, не каст. `TriggerWhenReady` — ветка уже установленного на объекте `AutoAbilityBehavior::update` (RW 0x85D9D1), не самостоятельный эффект кнопки. Исключение `AutoAbility` (RW 0x940642) для ранней проверки готовности не отменяет проверок симуляции. DONOR BFME2 0x539A65 (`ControlBarCommandProcessing.cpp`). |
| Симуляция | RW 0x77A42C с нулевым ID источника берёт выделение игрока; RW 0x76F5DB идёт по выбранной группе, а не её `InitialPayload`. Ветка `OK_FOR_MULTI_EXECUTE` пропускает выбор старшего героя; RW 0x82D5DA проверяет тип, местность, `UnitCost`, собственный модуль, готовность и требования; безадресный натиск проходит финальную таблицу. Адресный вариант RW 0x82D925 тоже требует модуль. RW 0x68E5A3 / RW 0x68E67A проверяют disabled, доступность RW 0x7B1D79 и ищут интерфейс; без него возврат, с ним — проверка формации RW 0x68CB85 и слот каста. RW 0x68C26D проходит только массив модулей объекта (`Object + 0x24C`, интерфейс в слоте 0x20) и принимает первый, чей интерфейс заявляет этот шаблон. Конструктор `SpecialPowerModule` (RW 0x8973EE) ставит таблицу интерфейса 0xC64FF0; её нулевой слот (RW 0x8969D1) сравнивает указатель `ModuleData + 8`, **не Enum**. У обеих сил натиска один Enum, но разные ID и указатели. DONOR BFME2 0x68BB9E (`Object_getSpecialPowerModule.cpp`), 0x68DF48 (`ObjectDoSpecialPowerCommands.cpp`) и 0x76D869 (`AIGroup.cpp`). |

## 3. Ангмар: «Натиск»

В `commandset.ini` кнопки с `SpecialAbilityAngmarCharge` принадлежат **старым наборам отдельных бойцов**. У фактически выбираемых `AngmarSnowTrollHorde` и `AngmarDarkDunedainHorde` в том же слоте — свои безадресные кнопки `SpecialAbilityChargeNoAim`. Набор тёмных дунэдайн, выдаваемый апгрейдом, также использует новую кнопку. Проверены `InitialPayload`, варианты `ChildObject`, объявления самих бойцов и активные включения: соответствующие `SpecialPowerModule` уже есть на обоих отрядах (и на бойцах, хотя меню бойца их не вызывает); старые блоки натиска в этих определениях закомментированы. Нет `CommandTrigger`, который связывал бы старую кнопку с новой.

- Стартёр разблокируется вторым уровнем: `UnpauseSpecialPowerUpgrade::upgradeImplementation` (RW 0x8B9676, перебор интерфейсов и сравнение шаблона через слот 0x18). `SpecialPowerModule::doSpecialPower` (RW 0x8980A3) проверяет паузу/disabled, инициирует действие (RW 0x897E87) и при `UpdateModuleStartsAttack = No` сразу запускает RW 0x897987. DONOR BFME2 0x89490F (`SpecialPowerModuleDo.cpp`).
- RW 0x897987 запускает перезарядку и ветку модификатора. Без `AttributeModifierAffectsSelf` берутся только прошедшие фильтры из запроса по радиусу; при `AffectsSelf` для не-отряда добавляется сам кастер, если его ещё нет, а для `HORDE` запрашивается интерфейс RW 0x68C866 и список бойцов (RW 0x897C5A–0x897CBB). Отсутствие этого интерфейса не превращает отряд в одиночную цель. RW 0x8977BF проверяет применимость к каждому кандидату, RW 0x89763B применяет список; в списках натиска есть `DAMAGE_MULT`. У дунэдайн есть и отдельный `WeaponModeSpecialPowerUpdate`; его модификатор движения — не источник увеличения урона.
- Основной каст и модификатор уже работают, когда выбран именно отряд (строки `PASS` в исходном `MATRIX.tsv`, без заявления о новом игровом прогоне). Задача порта здесь — довести выбор отряда до правила RW, а в матрице направить проверку к его реальной кнопке вместо старого ID силы отдельного бойца. Пустой старый модуль нельзя чинить поиском по похожим именам или типу силы.

## 4. Проверка

- Исходный прогон `c74ef879` на Linux Release (целевая линковка тестов с `openbfme_core`): `PORT-287*` 4/4, 245/245 проверок, в том числе отложенный контроль. Со старым `HudObjects.cpp` из `3f0105c8`: 2/4, 10 падений, на выборе отряда точкой/рамкой и запрете `UNSELECTABLE` у производителя. Соседи `PORT-101*,PORT-221*,combat weapons*`: 24/24, 916/916.
- В готовой части щелчок и рамка проверяются отдельными тестами. Оба проходят тот же путь через HUD после выхода бойца из контейнера: до разблокировки кнопка не готова, после нажатия один `MSG_DO_SPECIAL_POWER` с ID силы отряда. Попадание оставшегося бойца снимает 28 вместо 16 HP (`DAMAGE_MULT 175%`, RW 0x90E4D2–0x90E4F3), у вышедшего остаётся 16. Соседние тесты покрывают отсутствие производителя-отряда, совпадающий Enum без совпадающего модуля и `UNSELECTABLE`.
- `select1*`, `ENNORATH sweep units*` на установках игры/мода ранее не выполнялись. Матрица не переснята; сгенерированные таблицы и файлы `*.hashes` не изменены.
