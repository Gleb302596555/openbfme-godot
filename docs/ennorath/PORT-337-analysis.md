# Port 337: fire terrain data investigation

- The field table RW 0xC11750 maps the cap to `+0x90`, regeneration to `+0x94`, and the indexed subtable to RW 0x6866CE. That parser accepts indices 0–3; each record is 24 bytes, at `+0x10 + 24*index`. Its numeric fields have maxima 65535, 4095, 1023, 255 (RW 0x42ECB2 rejects values above the supplied maximum).
- RW 0x687748 seeds each cell by asking terrain vslot `+0x60`; index 0 and indices >=4 leave it zero, otherwise record offsets +8/+12/+16/+20 feed cell fuel/max rate/decay/resistance. RW 0x685EB0 restores the same values after object flammability, with zero clearing them. RW 0x6886E0 uses the terrain index again for fuel regeneration, compares the burning set size with `+0x90` at both admission sites, and uses the resulting cell values in decay and spread.
- The W3D terrain vslot is RW 0x462520 → RW 0x466AC3 → RW 0x4ADC78; it reads the map's per-cell flammability byte, with coordinate conversion and boundary clamping. The port already parses these bytes into `WorldHeightMap::m_flammability`, but FireLogicSystem hardcodes material 1 (and tests water instead).
- RW 0x5F32FF uses three times the cap for the terrain-fire particle capacity when nonzero, capped at 2048; otherwise it returns 128. The port already connects the live cap to the particle environment, but clamps positive values below 128 too.
- DONOR BFME2 0x00285FA9 (`Code/GameEngine/Source/GameLogic/Map/FireLogicSystem.cpp`), 0x00287015 (`Code/GameEngine/Source/GameLogic/System/FireLogicSystem_NewMap.cpp`), 0x00285778 (`Code/GameEngine/Source/GameLogic/Map/FireLogicSystemObjects.cpp`), and 0x00287FAD (`Code/GameEngine/Source/GameLogic/Map/FireLogicSystem.cpp`) provide corroborating layouts; RW instructions above are the behavioral source.
- The port's `FireLogicSystem::parseINI` has no production caller: `RetailObjectWorld::State` registers a recording stub instead, and the live logic is made after the world and map INIs. Wiring the actual block into that existing world INI pipeline and transferring its configuration into the new logic is required; a test-only registration would not fix the game.
- **Name / Color — no runtime reader in RW 2.01.** Table RW 0xDA07A8 (reached from RW 0x6866CE) uses RW 0x42EE5E for Name at record +4 and RW 0x42F13E for Color at +0. The records are `this+0x10+24*index` (constructor RW 0x6875FB -> element initializer RW 0x9CBA23). The binary xrefs to global `0xDE46A8` were inspected: apart from the parser, lifetime and generic snapshot-vtable plumbing RW 0x6DFBE9, users call fire methods or directly access the grid/burning set/cap (e.g. RW 0x6EE2A8, RW 0x7B13EB, RW 0x5F330A), not material Name/Color. A streaming decode of RW 0x685EB0..0x688DAF finds the stride-24 multiplications only at RW 0x685F02 (reset: offsets +8/+12/+16/+20), RW 0x6867BA (parser), RW 0x68786B (NewMap: four numeric offsets), and RW 0x688B53 (update: fuel +8). Vtable RW 0xC118EC points to destructor RW 0x688338, no-op/inherited functions, clear RW 0x687743, update RW 0x6886E0 and xfer RW 0x688384; none reads Name/Color. BFME2 donor's `FireLogicSystem*.cpp` / `FireLogicSystem_NewMap.cpp` likewise reference the corresponding `unknown00`/`unknown04` only in declarations and initialization/destruction. Name and Color are syntactically parsed/validated but deliberately not kept as new simulation state.
