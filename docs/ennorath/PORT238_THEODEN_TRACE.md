## Delivery, replacement and timers

`object/goodfaction/units/men/theoden.ini:7` defines `RohanTheoden_mod`; `:1653` defines a separate `Theoden_OneRing`. The former's `CitadelSlaughterHordeContain` (`:1368–1384`) requires a `HOLDING_THE_RING` carrier, destroys `TheDroppedRing`, and declares both OBJECT upgrades `Upgrade_RingHero Upgrade_FortressRingHero`. The attachment macro `_gamedata.inc:31` explicitly excludes `RohanTheoden_mod` and `RohanTheoden_mod_Summoned`; it does not follow that a separate carrier cannot deliver the ring. Variants, inheritance, effective filters and spawn paths remain to be resolved.

The base's `UnpauseSpecialPowerUpgrade` uses `Upgrade_RingHero`, but **both** the `DoCommandUpgrade` and `CommandSetUpgrade` require the two ring upgrades (`:1306–1342`). The switch button is `Command_SpecialAbilityGlorfindelRingSwitch` and the `ToggleMountedSpecialAbilityUpdate` replaces the object with `Theoden_OneRing`. Six timer names are listed: `SpecialAbilityTheodenGloriousCharge`, `SpecialAbilityKingsFavor`, `SpecialAbilityHornOfGondor02`, `SpecialAbilityAragornBladeMaster`, `SpecialAbilityBoromirErnennung`, `SpecialAbilityBoromirOsgiliath`. Both literal object blocks directly contain modules for the first two; the other four are not directly declared in either block. This is not proof of their effective absence after all includes/overrides. The ring form itself also has a same-template toggle (`:2558–2579`); reachability and self-replacement are not tested here.

The generic RW chain is ring delivery `0x8840FC`, upgrade command `0x8B8E2E`, toggle `0x8B1690 -> 0x8B140D`, and named timer loop `0x8B12BF -> 0x897368`. The BFME2 donor `ToggleMountedSpecialAbilityUpdate.cpp` also shows named timer synchronization and replacement. These are mechanism evidence, not an Ennorath playthrough; S-7321, S-7446 and S-861 remain.

`PORT-238 Theoden-style two upgrades gate replacement and two present timers survive` uses synthetic objects and direct grants or ring delivery. Each single upgrade alone leaves the base object and command-set name unchanged; delivery of both selects the synthetic ring set and replaces it, preserving the two named timer ready frames and team while not copying an unlisted timer. The other four globally defined synthetic timer templates have no corresponding modules on either object. It passes **115/115 assertions** in three subcases; the complete isolated `PORT-238*` suite passes **29/29 tests, 1817/1817 assertions** on matching `3f0105c8` core/headers plus the separately compiled upstream PORT-286 parser. A control changing only the synthetic `DoCommandUpgrade` to `RequiresAllTriggers = No` fails both single-upgrade subcases (107/109, with fatal assertions shortening the run). This is a fixture-sensitivity control, not a code-fix control. Test data do not load the mod or prove the four real modules absent, the UI purchase/selection, saved state, actual timers or gameplay.
