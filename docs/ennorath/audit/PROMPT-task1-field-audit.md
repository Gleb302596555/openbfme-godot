## Как устроено (проверено)

1. **Сторона мода**: архивы RotWK 2.01 и поверх архивы мода (`ennorath_graph.mount`, `expand` для `#include` и `#define`). Каждое определение (`Object`, `Weapon`, ...), поля модуля (`Behavior = <Класс> ModuleTag_x` .. `End`) относятся к классу, поля вложенных блоков к `<Класс>/<Ключ>`. Первый прогон: 22 600 различных полей.
2. **RotWK**: `engine/data/rotwk-201/field-tables.json` и `module-registry.json` — таблицы полей каждого из 329 классов модулей, вынутые из `game.dat`. Поле, которого там нет, — ошибка самого мода: RotWK его тоже не использует.
3. **Порт**:
   - Парсер движка (`INI::initFromINIMulti`) падает с ошибкой на неизвестном поле, поэтому «тихо не прочитанных» полей в типизированных модулях нет.
   - Модуль без своей таблицы «сырой» (`RawModuleData`): значения не разбираются вообще. Это главный источник будущих проблем.
   - Модуль без runtime-класса создаётся как `UnportedModule` и ничего не делает.
   - Таблицы полей в коде: `{ "Поле", парсер, user, OFF(m_member) }`. По имени `m_member` ищутся использования вне таблицы и парсера.

## Что не так в первой версии (исправить первым делом)

- **Статус модуля** берётся регулярными выражениями из `bindTypedData<T>("Класс")` и `bindModuleProc("Класс")`. Они пропускают регистрации через `bind<Runtime, Data>(modules, "Класс")` и `bindRuntime<...>`: нашлось 82 перенесённых класса вместо 222. Из-за этого 17 505 полей ложно попали в `missing-module`.
  - **Правильный источник** — таблица самого движка: `OPENBFME_MODULE_COVERAGE_OUT=<tsv> openbfme_tests.exe "-tc=module coverage: every registry class*"`. Колонки: `class type status typed ai drawkind`; `status` = ported / base-ai / parsed-only / missing; `typed` = 1/0. Уже выгружена в `field-audit/module-coverage.tsv` (сборка `main-red`, 2026-11-04). Сделай её входом инструмента (`--coverage`).
  - Связь «класс → структура данных» для типизированных классов: дополни разбор шаблонами `bind<..., Data>(modules, "Класс")` и `bindRuntime<..., Data>`, а если структура не нашлась, честно пометь `struct-unknown`. Не гадай по совпадению имени поля в чужих таблицах.
- **«Используется»** определяется по имени переменной, и это эвристика: у двух классов может быть член с одинаковым именем. В каждой строке «used» оставь первое место использования, чтобы его можно было проверить глазами. Подумай, можно ли сузить поиск файлами, которые включают заголовок структуры.
- **Собственные поля определений** (`Object`, `Weapon`, `Armor`, `CommandButton`, ...) сейчас сопоставляются по имени поля с любой таблицей в коде. Лучше привязать тип блока к его таблице (`ThingTemplate`, `WeaponTemplate`, ...) и для `Object` взять `objectTable` из `field-tables.json`.
- **Нет теста.** Добавь `tools/mod/test_field_audit.py` на маленьком искусственном наборе: модуль типизированный, сырой, отсутствующий; поле используется, не используется, неизвестно RotWK. Посмотри, как устроены соседние `test_*.py`.
