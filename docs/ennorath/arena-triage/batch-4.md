# Field triage 4/25 — что RotWK 2.01 делает с 30 полями Ennorath (issue #14)

Разбор 30 полей из issue #14 (аудит `tools/mod/field_audit.py`, статус `parsed-unused`). Для каждого поля: строка таблицы полей (`T`), функция-парсер (`P`), смещение члена (`+0x…`) и либо читатель с инструкцией, либо доказательство, что чтения в игре нет.

Источники и границы:

- Образ: `workspace/RotWK/game.dat`, RotWK 2.01, md5 `daed3668006cd90f01c34e5a7da1901f`. Оговорка **S-001**: образ сообщественно модифицирован, независимого подтверждения розничного оригинала нет. По note в `docs/ennorath/TOP20.md` (2026-11-04) у Ennorath `game.dat` — патч 2.02, а 2.01 и 2.02 различаются только фиксом задержки offhost, поэтому таблицы `engine/data/rotwk-201` и адреса RW 2.01 остаются действительны.
- Данные мода первичны (PROCESS.md 15.11): Ennorath 1.9.8.2 (INI распакованы вне репозитория, в отчёт попали только имена полей/блоков и количества, значений нет). Vanilla привлекалась только там, где мод её не переопределяет.
- Каждый адрес прочитан `python tools/mod/rw.py workspace/RotWK/game.dat dis <addr>`; для массового поиска по образу использованы те же capstone/pefile поверх того же файла (полный линейный проход `.text`, 2 701 800 инструкций, 424 недекодируемых байта) — то есть источник адресов один и тот же.
- `workspace/reference/open-bfme-2` (декомпиляция BFME2) привлечена один раз, в строке 3, и помечена `INFERENCE`.
- **Глобальная оговорка**: всё, что выведено из имён, из структуры таблиц, из декомпиляции BFME2 или по аналогии, а не из прочитанной инструкции, помечено `INFERENCE` в последней колонке. Ничего не портировано, код не менялся.

Обозначения: `T` — адрес строки таблицы полей, `P` — адрес функции-парсера, `+0x…` — смещение члена в классе-владельце. «Конструктор данных» — функция, пишущая значения по умолчанию в ModuleData/шаблон; «копия» — copy-конструктор/оператор присваивания; «xfer» — сериализация (save/load, CRC).

## Цепочки, которые разбирались отдельно

**A. Голосовые ключи `/UnitSpecificSounds` (строки 8, 9, 25).** Единственная функция в образе, которая ищет голос по имени, — `RW 0x8DDB2A` (её `call RW 0x825D3A` в `RW 0x8DDB6C` — единственный вызов этого «find по имени» во всём образе; у `RW 0x825C45` вызов тоже один — `RW 0x8DEFFE`). Все ключи-литералы (`VoicePrimaryWeaponMode` `RW 0xC77B14`, `VoiceSecondaryWeaponMode` `RW 0xC77B2C`, `VoiceTertiaryWeaponMode` `RW 0xC77B48`, `VoiceNoBuild` `RW 0xC77A64`) пушатся внутри диспетчера `RW 0x8DEDBB`, у которого 57 вызывающих; два из них проверены как живые: `RW 0x941242` (событие `0x43A`, режим берётся из `[esi+0x80]`) и `RW 0x83EAA0` (событие `0x7EB`). Незакрытым остался только вопрос, какой контейнер подаёт карту в `ctx+0x18`: диспетчер строит её через `CrowdResponseKey` (ThingTemplate+0x4AC, T `RW 0xDA4398`, P `RW 0x825DC2`, реестр `[RW 0xDE8B3C]`, приоритетный отбор `RW 0x8DEF8F`—`RW 0x8DF003`), тогда как блок `/UnitSpecificSounds` объекта — это ThingTemplate+0x388 (T `RW 0xDA4378`, P `RW 0x73F684`, на объект копируется в `RW 0x92738A`). На вердикт это не влияет: чтение имени и воспроизведение звука доказаны в обоих маршрутах.

**B. Локомотор (строки 3, 18, 22).** Таблица `RW 0xBF4478`…`RW 0xBF49E8` (88 строк, терминатор `RW 0xBF49F8`), ссылки на неё `RW 0x5E31B8` и `RW 0x5E83DC`. Все три поля читаются (или не читаются) в трёх обработчиках, на которые расходится `RW 0x67BE1D` по Appearance (LocomotorTemplate+0x74, имена enum `RW 0xD9DEEC`: 0 TWO_LEGS, 1 FOUR_WHEELS, 2 HOVER, 3 WINGS, 4 FOUR_LEGS_HUGE, 5 GIANT_BIRD, 6 HORDE, 7 HUGE_TWO_LEGS, 8 TREADS, 9 SHIP, 10 OTHER). Обработчики выделяют 0x58-байтный DrawableLocoInfo при `[this+0x13C] == 0` (`push 0x58; call RW 0x42F6E0; call RW 0x670392`), объект берут из `[this+0xFC]`, шаблон — из `mov eax,[ebp+8]; mov eax,[eax+4]`.

**C. Crate-классы (строки 19, 27, 28).** Базовая таблица crate-классов `RW 0xC71390` (поля +0x8…+0x58) общая для `HealCrateCollide`, `MoneyCrateCollide`, `SalvageCrateCollide`, `ShroudCrateCollide`, `UnitCrateCollide`, `VeterancyCrateCollide`; у каждой производного класса свои строки на тех же смещениях: Salvage — `RW 0xC05F80`…`RW 0xC06000` (+0x5C…+0x7C), Unit — `RW 0xC05E4C`/`RW 0xC05E5C` (+0x5C int, +0x60 строка), Veterancy — `RW 0xC05EB8`…`RW 0xC05EE8` (+0x5C, +0x60/+0x61 байты, +0x64), Money — `RW 0xC05E14` (+0x5C). Поэтому обращения к +0x60 в общем регионе crate-кода пришлось атрибутировать по типу доступа и по vtable конструкторов (`RW 0xC715C0` у Salvage, `RW 0xC71554` у Veterancy).
