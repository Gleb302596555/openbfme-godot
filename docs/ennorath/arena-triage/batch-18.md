# Field triage 18/25 — поля `GameData` (issue #28)

Изображение: RotWK 2.01 (`game.dat`, md5 `daed3668006cd90f01c34e5a7da1901f`). Все адреса — `RW 0x…`; каждая строка ниже подтверждена чтением инструкции через `rw.py dis` и полным перебором `.text` на `[reg+смещение]`; выводы из кода без запуска помечены `INFERENCE`.

## Как доказано, что поле читается (общая часть)

1. Таблица полей: `RW 0xBFF580`, 457 записей по 16 байт `{ +0: указатель на имя, +4: адрес парсера, +8: 0, +12: смещение члена }`, конец — `RW 0xC01210`. Найдена по строке `GroupSelectVolumeBase` (`RW 0xC0270C` → единственная 4-байтовая ссылка `RW 0xC005A0`). Те же две записи как аргументы — в инициализаторе, который загружает `[0xDE4364]` (`RW 0x6441A5`, `RW 0x64423A`).
2. Объект: `[0xDE4364]`, размер `0x1254` (`RW 0x64410D`), конструктор `RW 0x6429AD`, установка указателя `RW 0x64413A` (`mov dword ptr [0xDE4364], eax` внутри `RW 0x644102`); там же `RW 0x644131` `mov dword ptr [eax + 0x1250], ecx` — в новый объект кладётся прежний указатель. Инициализация по умолчанию внутри конструктора: `RW 0x643D01` `lea edi,[esi+0x954]` + `pop ecx`=8 + `RW 0x643D08` `rep stosd` (8 dword = `+0x954..+0x970`, включая `HumanSoloPlayerHealthBonus_*`/`AISoloPlayerHealthBonus_*`), `RW 0x643D33` `lea edi,[esi+0x10a4]` + `rep stosd` (20 dword = `+0x10A4..+0x10F0`, всё поле `HandicapBuildSpeed*`; значение — `edx`, в ветке `[0xDE437C] != 0` это `0x3F800000` из `RW 0x643D1F`), `RW 0x643D3C` ещё один такой блок на `+0x116C`, `RW 0x6437F9` `mov dword ptr [esi + 0xe84], 2`, `RW 0x642C57` `mov byte ptr [esi + 0x13d], bl`, `RW 0x643127`/`RW 0x64312F` — `+0xB48`/`+0xB4C`.
3. Парсеры: `RW 0x42E558` bool (`mov byte ptr [ecx], al`, `RW 0x42E571`), `RW 0x42EC5E` int (`mov dword ptr [ecx], eax`, `RW 0x42EC77`), `RW 0x42ED00` float (`fstp dword ptr [eax]`, `RW 0x42ED19`), `RW 0x42EEFA` проценты (`fstp dword ptr [eax]`, `RW 0x42EF18`), `RW 0x42EE5E` строка (`mov eax, 0xb70da6; call 0xa3cef0` — assert-пролог, `RW 0x42EE5E`/`RW 0x42EE63`, затем `call RW 0x42E757` — разбор токена, `call RW 0x436030` — присваивание строки по указателю из `[ebp+0x10]`, `RW 0x42EE7D`). `RW 0x40618C` — `call RW 0x4050E6; ret`, то есть **запись** значения по указателю.
4. Чтение ищется двумя способами: (а) прямое обращение `[reg+смещение]` по всему `.text` (все 30 смещений, включая индексированные формы), (б) поток данных от `[0xDE4364]`: 1292 инструкции загружают этот глобал; обход функций, достижимых от GameData-указателя, в двух реализациях — 780 функций (указатель только в регистре) и 230 состояний (указатель на член, переданный аргументом в вызываемую функцию, тоже прослеживается). Итог по 30 полям — **три** обращения, все в строках 27, 29, 30.

Две ловушки, которые пришлось снять:

- **`[0xDE4938]` — другой класс, не GameData.** Оба глобала привязываются к объектам одним и тем же регистратором `RW 0x636404` (`mov dword ptr [esi], edi` в `RW 0x63641C`, `[ebp+8]` = адрес глобала, `[ebp+0x10]` = объект). Для GameData это `RW 0x63AF9F` `push 0xde4364` при объекте из `RW 0x63AF65` `push 0x1254` → `RW 0x6429AD`; для `[0xDE4938]` — `RW 0x63C3D3` `push 0xde4938` при объекте из `RW 0x63C399` `push 0xa78` → `RW 0x6AA15C` (свои таблицы `0xC13DFC`/`0xC13DEC`, `+0x2FC`, поля `+0x954/+0x958/+0x95C` внутри размера `0xA78`). **Размеры разные — `0x1254` против `0xA78`**, поэтому `+0x10A4..+0x10F0` (гандикап) и `+0xE84` (`InitialMaxRingLevel`) в объекте `[0xDE4938]` вообще не существуют, а совпадение номеров у `+0x954/+0x958/+0x95C` — совпадение раскладки. Дополнительно `[0xDE4938]` никто не пишет через `mod=00/rm=101` (`A3`, `C7 05`, `89 05` — ноль совпадений во всём образе), а `[0xDE4364]` пишется в `RW 0x64413A`; статически `[0xDE4938]` = 0, то есть объект связывается с глобалом не кодом `.text`, а загрузкой/сценарием.
- Одинаковые смещения у несвязанных классов: `+0x11C` встречается 666 раз, `+0x120` — 500, `+0x124` — 404 (например `RW 0x49A6A1` `fld dword ptr [ecx + 0x11c]`, `RW 0x4A0A3A` `mov eax, dword ptr [esi + 0x120]`, `RW 0x9B2028` `cmp eax, dword ptr [esi + 0x95c]`). Все они отброшены: либо база не из GameData, либо смещение читается как другой тип.

## Что осталось непокрытым и почему

- **`HandicapBuildSpeed5..100`**: отсутствие чтений доказано по всему `.text` (прямые обращения, `lea`, индексированные формы) и по потоку данных от `[0xDE4364]`. Не доказано обратное — что игра применяет гандикап из другого места (возможно, значения передаются в сетевое сообщение/UI как данные объекта; обращений к `+0x10A4` за пределами инициализации в образе нет, но объект может уходить в скриптовый/сетевой слой по указателю). Дальше: искать, кто читает объект этого класса (`RW 0x7D7A7A`) по `+0x10A4`, через таблицы `RW 0xC491F8`, `RW 0xBD343C`, `RW 0xC49224`, `RW 0xC491E4` — эти адреса могут быть именами полей для отладочного дампа.
- **`HumanSoloPlayerHealthBonus_*`**: чтений из GameData нет; косвенная проверка (соседние `AI*`-поля читаются) проведена, но объект `[0xDE4938]` — другого класса (размер `0xA78`, конструктор `RW 0x6AA15C`, см. «Ловушки»), и в области `+0x954..+0x970` он читает байтовые флаги, а не проценты; совпадение смещений ничего не значит. Дальше: найти, кто пишет `[0xDE4938]` (статически ноль; вероятно, указатель ставится в сценарии/загрузке карты, поэтому в `.text` записи нет — все 129 записей в `.data`-области образа нулевые).
- **`HideGarrisonFlags`**: владельцы всех 6 обращений установлены (лог bumpmap в `RW 0x52AE50`, конструктор `RW 0x86B425`, UI-предикат `RW 0x86A002` с таблицей `0xC5A728`, геттер `RW 0x8B81E6` с таблицей `0xC6E288`, конструктор GameData `RW 0x642C57`). Осталось бы проверить `RW 0x86A002` на предмет «а вдруг это UI-предикат для флагов гарнизона» — но его объект (`RW 0x86B425`) не GameData и загружает свои данные из модуля `[ebx+4]`; проверка `[0xDE4364]` в этой функции даёт ноль.
- **`LevelGainAnimationName`** (единственное `не определено`): остановился на `RW 0x6D8583` (обход `std::map`: `mov esi,[ecx+0xC]`, `call RW 0x4065AA`, `ret 4`), результат которого в ветке не используется — `RW 0x695938` сразу читает `[esi+0x38]`. Чтобы закрыть поле, нужно найти, кто наполняет эту `std::map` (её владелец — объект `[0xDE4AB0]`) и читает ли найденный по имени клип кто-то ещё; в пределах функций, достижимых от GameData-указателя, таких чтений нет. Второе найденное обращение к `+0x11C` (`RW 0x5001E1`) относится к другому классу (`RW 0x500137`: `lea esi,[ecx+0x128]` в `RW 0x500299`, поля `+0x108`/`+0x12C`/`+0x130`).
