# Field triage 8/25 — issue #18

## Область и метод

Только анализ, без изменения порта. База: `da6cbfdf822247c0ff373522cda4125eb291ff99` (совпадала со свежим `origin/main` при начале). Бинарник с Диска: MD5 `daed3668006cd90f01c34e5a7da1901f`, оговорка S-001 (community-modified image). Объединённый архив `ennorath-ini-1.9.8.2.zip` распакован в `/tmp/ennorath-ini`; наличие полей и контексты проверены там, не в ванильных INI. Значения/тела INI сюда не скопированы. Отдельная сверка количества определений с аудитом не является результатом этой работы.

Адрес **таблицы** в строке ниже — адрес 16-байтовой записи PE: string, parser, userData, member offset. Это данные, не исполняемые инструкции. Таблицы проверены непосредственно в PE, включая отсутствующие в JSON Locomotor/OCL/CommandButton. Все приведённые адреса **инструкций** прочитаны `tools/mod/rw.py … dis`; перечисление операндов всей `.text` сделано Capstone, включая смещения с большим количеством ложных совпадений. Отсутствие прямых `call` не принималось за отсутствие использования; виртуальные таблицы искались как DWORD-адреса в PE.

**INFERENCE (раздел 14 PROCESS):** это статический анализ, не наблюдение запущенной игры. Названия восстановленных операций и ожидаемый визуальный эффект — интерпретация проверенных инструкций; отдельно отмечены в таблице. Вердикт «читает» означает найденный игровой/клиентский путь, а не гарантию, что каждый объект мода достигает его в каждом матче. Статус `RotWK не использует` требует доказательства всех чтений; в этой пачке такой статус не присвоен.

Общие парсеры: RW 0x42E571 пишет bool, RW 0x42ED19 пишет float, RW 0x73A450–0x73A46B преобразует время в кадры и пишет DWORD. Особый геометрический парсер RW 0xAD2B4A пишет во вложенный +4. Для словаря звуков нет отдельного фиксированного члена на каждое имя.

## Замкнутые цепочки и проверка принадлежности

### A. AODHordeContain: данные, оба виртуальных читателя, координаты

- Регистрация таблицы: RW 0x87D62E вызывает базовую регистрацию, RW 0x87D63E передаёт таблицу RW 0xC5CE50. Конструктор ModuleData RW 0x87D55F сначала вызывает базовый RW 0x878EE5, затем инициализирует именно диапазон +0x284..+0x2C8; RW 0x87D5FA ставит его vtable. Это не случайное совпадение смещений объекта орды.
- Конструктор модуля RW 0x87E647: RW 0x87E673 ставит основную vtable RW 0xC5D3F0, RW 0x87E6BB — интерфейсную RW 0xC5CFA8 на module+0x11C. В PE адрес читателя RW 0x87DEFB лежит по RW 0xC5CFC4, **слот +0x1C** интерфейса. Адрес RW 0x87E8FC лежит по RW 0xC5D474, **слот +0x84** основной таблицы.
- Замыкание обоих слотов одним вызывающим: в RW 0x872D55 `ebx=esi-0x20` (полный module). RW 0x872DA7 вызывает `[vtable(module)+0x84]`: для AOD это RW 0x87E8FC. Затем RW 0x872DBE получает `ecx=esi+0xFC`, т.е. module+0x11C; RW 0x872DD3 вызывает `[vtable(interface)+0x1C]`: для AOD это RW 0x87DEFB. Таким образом найден не просто похожий `vcall` другого класса.
- Инициализатор RW 0x87E8FC берёт **ModuleData из [module+4]** в RW 0x87E90D. Четыре поля Randomness читаются там, формируя шесть выборок RNG RW 0x6D332C на запись; RW 0x87EA9A добавляет запись в вектор module+0x30C. RNG не назначен по одному имени: RW 0x6D334C вызывает генератор и RW 0x6D336E–0x6D3371 масштабирует результат в переданные границы.
- Расчёт координат RW 0x87DEFB получает интерфейс module+0x11C; **RW 0x87DFC0 читает [interface-0x118]**, то есть тот же module+4, в ESI. Все перечисленные в строках 16–17, 20–28, 30 чтения — именно из этих данных. Случайные коэффициенты из предыдущего пункта используются в RW 0x87E09A / RW 0x87E0C9 и RW 0x87E19A / RW 0x87E1A8. Итоговые XYZ записываются в выходной аргумент RW 0x87E4D7–0x87E50A. Вызывающий после RW 0x872DD3 передаёт полученные координаты дальше в RW 0x872DFA (`RW 0x871897`). Это расчёт положения участников, не copy/xfer и не случайное чтение ModuleData в конструкторе.
- INFERENCE: названия «положение участника», «движение/покой», «рассеивание» восстановлены из этого пути и имён полей; факт достижимого чтения, случайных коэффициентов и возврата координат не зависит от BFME2-доноров.

### B. TransportContain: два bool и две длительности → Drawable

- RW 0x86BB13 регистрирует таблицу RW 0xC5ABD8 после базовой. RW 0x86B6C8 ставит на module+0x20 vtable RW 0xC5A690. PE-слоты RW 0xC5A6E8 и RW 0xC5A6EC содержат RW 0x86A943 / RW 0x86ABDC, т.е. слоты +0x58/+0x5C интерфейса.
- Это методы интерфейса module+0x20: на входе RW 0x86A961 берёт данные `[esi-0x1C]`, а RW 0x86AC1A — `[esi-0x1C]` в EDI. Оба адреса равны `[module+4]`. Следовательно, +0x16C/+0x16D/+0x170/+0x174 принадлежат нужному TransportContainModuleData.
- Есть также прямые вызовы, не только vtable: RW 0x87A5FC вызывает RW 0x86A943 с `ecx=module+0x20`; RW 0x87A61C вызывает RW 0x86ABDC. Поэтому отсутствие прямого вызова не используется как аргумент.
- Вход: RW 0x86AAC2 → RW 0x86AAD9 → фильтр RW 0x86AAFB → длительность RW 0x86AB69 либо RW 0x86ABA7 → Drawable fade RW 0x670A50 / RW 0x670AA2. Выход: RW 0x86ADBD → RW 0x86ADD5 → фильтр RW 0x86ADF6 → RW 0x86AE5F либо RW 0x86AE8D → RW 0x670AA2. Эти две конечные функции пишут режим fade, текущую непрозрачность +0xB0 и длительность +0x130 (RW 0x670A6E–0x670A87 / RW 0x670AC0–0x670AD9). Классификация клиентская, хотя запускает её contain-логика.

### C. EnterSound: общий OpenContain-путь у TransportContain

RW 0x8658A3 — реальный читатель, не getter: RW 0x8658D0 загружает ModuleData, RW 0x8658D9 прибавляет +0x38, RW 0x8658E3 создаёт аудиособытие, RW 0x8658F8 назначает ID и RW 0x86590C отправляет его Audio через +0x64. PE-слот RW 0xC5A85C содержит RW 0x8658A3, т.е. +0x54 основной таблицы TransportContain RW 0xC5A808 (установлена RW 0x86B6B4). Вход в контейнер вызывает этот слот в RW 0x86754C, предварительно восстановив полный module в RW 0x867534. Есть кадровая защита RW 0x8658C8; это не чтение для сериализации.

### D. DieOnMap: RunOffMap update → выбор AI-команды

RW 0x86527E регистрирует таблицу RW 0xC59698. Конструктор RW 0x8652AD ставит интерфейс на module+0x10: таблица RW 0xC59644 содержит RW 0x86540A (слот 0). В update RW 0x865427 `[ecx-0xC]` — module+4. Поле читается RW 0x865519. Ветви RW 0x865528 / RW 0x86552F ведут в RW 0x86539E / RW 0x865332: они создают разные AICommandParms и отправляют их виртуальным вызовом RW 0x8653DE / RW 0x865372. INFERENCE: восстановленное название update и значения команд; их различие и логическое использование bool подтверждены, а не выведены только из названия DieOnMap.

### E. RequiresValidContainer: активный обход кнопок

Не остановлено на геттере RW 0x9422F3 (его DWORD-адрес не найден в образе, прямые ссылки тоже не найдены). Есть независимый активный читатель: RW 0x943F37 получает CommandButton через RW 0x80C837 и сохраняет в ESI. Источник содержимого контейнера берётся с Object+0x258 в RW 0x943EB6, сохраняется в локальную переменную; RW 0x943F75 проверяет ESI+0x107. При заданном флаге RW 0x943F83 получает ModuleData контейнера, RW 0x943F8A проверяет byte +0xDE, RW 0x943F91 уходит к следующей кнопке. Это ветвь UI-обхода, не использование флага в copy-конструкторе.

### F. UnitSpecificSounds: прямой ключ и динамический словарь

Object-template имеет словарь на +0x388 (запись PE RW 0xDA4378 → RW 0x73F684). Парсер RW 0x73F691–0x73F69A передаёт таблицу обработки вложенных ключей. Клиент RW 0x8DFD0D явно запрашивает `VoiceStartCharging`, через RW 0x8DDB2A. RW 0x8DDB7D вызывает поиск по имени RW 0x674FFE; RW 0x67505B обращается к шаблону, RW 0x73EDEF–0x73EE0E ищет ключ в словаре +0x388 и возвращает запись. RW 0x8DDB89 передаёт результат в запись звуков RW 0x8DDA33. Этот конкретный литеральный путь подтверждает №13, но не №3. Для №3 активные определения INI сами по себе не доказывают наличия активного запроса.

### G. ShowPips: восстановление класса через интерфейс и рисующий caller

В AOD-конструкторе RW 0x87E687 установлен interface module+0x20 → RW 0xC5D268. DWORD по RW 0xC5D3B8 — RW 0x866411, слот +0x150. RW 0x86642B берёт ModuleData `[interface-0x1C]`, RW 0x86642E проверяет именно его +0x80, а не другой одноимённый член. При false RW 0x866497–0x8664A1 возвращает нулевые количества и false. Клиент RW 0x677994 получает Object из Drawable+0xFC, затем contain из Object+0x258 в RW 0x6779A5; RW 0x677A47 вызывает ровно слот +0x150 с шестью выходными аргументами. RW 0x677A4F пропускает рисование при false; при true — проекция RW 0x677AE2, цикл и вызовы рисования прямоугольников RW 0x677BBE. Это замкнутая клиентская цепочка у AODHordeContain, хотя реализация унаследована от OpenContain.

## Сводка и дальнейшие задачи

| Вердикт | Полей |
|---|---:|
| RotWK читает (логика) | 17 |
| RotWK читает (клиент) | 9 |
| RotWK не использует | 0 |

Кандидаты в TOP20, **не изменения самого TOP20 и не заявление, что порт уже исправлен**:

1. AODHordeContain: все 16 полей строк 14–28 и 30 — единый механизм координат, случайных коэффициентов, высоты и scatter.
2. TransportContain: EnterFadeTime, ExitFadeTime, FadePassengerOnEnter, FadePassengerOnExit — единый клиентский fade-путь.
3. Общий OpenContain: EnterSound и ShowPips (последний также нужен AOD).
4. RunOffMapBehavior/DieOnMap — выбор AI-команды.
5. OCL/InheritAttributesFromSource — передача атрибутов Drawable.
6. CommandButton/RequiresValidContainer — UI-фильтр пригодности контейнера.
7. UnitSpecificSounds/VoiceStartCharging — именованный запрос в клиентском выборе ответа.

Осталось: №1–2 — атрибуция всех возможных чтений шаблона, включая сдвинутые указатели; №3 — активный производитель динамического запроса конкретного ключа; №4 — конечный потребитель small внутри переданной GeometryInfo. Ничего из этого не объявлено неиспользуемым. BFME2-декомпиляция просмотрена только как навигация, её адреса не подменяют RW и не являются доказательствами вердиктов.

| Изменённое поведение | Источник | Проверка |
|---|---|---|
| Нет; только новый аналитический документ | RW-цепочки A–G и таблица выше | Ручное чтение `rw.py dis`, PE-таблиц и модовых контекстов; commit gate |

Сборка, unit-тесты и игра **не запускались**: по заданию только анализ, установленной игры в песочнице нет.
