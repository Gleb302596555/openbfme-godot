# Field triage 12/25 — issue #22

## Источники и границы

- Анализ только 30 полей `AIData` из issue #22, в его порядке. Движок и `TOP20.md` не изменялись.
- Проверен предоставленный RotWK 2.01 `game.dat`: MD5 `daed3668006cd90f01c34e5a7da1901f`. Оговорка S-001 сохраняется: это предоставленный образ, не независимая аттестация retail.
- Данные мода проверены первыми (PROCESS.md 15.11): все 30 имён имеют активные присваивания в `data/ini/default/aidata.ini` распакованного `ennorath-ini-1.9.8.2`; в `data/ini/aidata.ini` ни одного. Значения и выдержки INI не публикуются. Это проверка наличия ключей, не пересчёт определений по owner.
- Таблица полей `AIData` — 74 строки по 16 байт от RW 0xC1CB20 (S-152); **адреса строк — данные, не инструкции**. Каждая строка перечитана в PE: имя, парсер, `userData`, offset. Все приведённые ниже инструкции и все читатели прочитаны через `tools/mod/rw.py ... dis`.
- Смещения — от базы `TAiData` (`AI + 0x18`). `TAiData` создаётся только из `AI`: `sizeof 0x114` (RW 0x7002AC в конструкторе `AI`, RW 0x701610 в `AI::newOverride`), vtable RW 0xC1D6D8.
- **Метод доказательства неиспользования.** Указатель `TAiData*` (`[TheAI+0x18]`) не покидает пределы охватывающей функции: он только сохраняется в стековые слоты охватывающей функции (например, RW 0x668F84 `mov [ebp-8], eax` и RW 0x94CB5D `mov [ebp-0x10], eax` сразу после `mov eax,[TheAI+0x18]`) и перечитывается оттуда; наружу уходят лишь адреса трёх `AsciiString` (+0xDC / +0xE0 / +0xE4, RW 0x62DD05 / 0x62DD25 / 0x62DD4A, передаются в поиск шаблона RW 0x6D1305), `push [ecx+0x18]` в разбор INI (RW 0x7017CF → RW 0x42DB80) и собственные методы `TAiData` (конструктор RW 0x6FFBEF, копия RW 0x6FEEF7, `xfer` RW 0x6FF49C — слот vtable RW 0xC1D6D8+0xC, деструктор RW 0x6FF9E9 через RW 0x6FFAB8). Поэтому каждое чтение члена — либо в расширенном окне после одной из 670 загрузок `[0xDE4B40]` (рег. `TheAI`), либо в этих методах. Проверены оба. Обход всех 670 загрузок идёт от `mov reg,[TheAI+0x18]` вперёд и учитывает: продвижение базы через `lea` (в том числе на +0xDC / +0xE0 / +0xE4), сохранение базы в стековый слот и её перечитывание после `call`, сброс регистров при `call`, а также **остановку окна на любом `ret`/`jmp`**, чтобы оно не переходило в соседнюю функцию, — иначе возникают ложные попадания: единственный кандидат на чтение +0x4, `lea ebx,[ecx+4]` на RW 0x8F82B1, стоит сразу за `ret 8` на RW 0x8F82AE, относится уже к другой функции и берёт базу `ecx` из чужого объекта. Итог: ни одного доступа к +0x4 / +0x18 / +0x20 / +0x2C / +0x30 / +0x34 / +0x38 / +0x74 / +0x78 / +0x80 / +0xCC / +0x104 / +0x108 / +0x10C / +0x110. Сплошной проход по всему `.text` с ресинхронизацией не нашёл ни одного `[reg+disp]` с disp `0xCC`, `0x104`, `0x108`, `0x10C`, `0x110` (совпадения только в чужом коде 0xB55xxx). Методы `TAiData` для этих смещений содержат только инициализацию/копию/`xfer` (см. строки таблицы).
- «Мёртвый код» устанавливается полным перебором ссылок внутри `.text`: rel32 (`E8`/`E9`), rel8 (`EB`), условные rel32 (`0F 8x`) и все 4-байтные указатели; дополнительно — сырой побайтовый поиск четырёхбайтного значения адреса по всему файлу. Образ собран без таблицы релокаций (Characteristics `0x12F`, бит `RELOCS_STRIPPED`), виртуальные адреса секций совпадают с их смещениями в файле, поэтому побайтовый поиск по файлу эквивалентен поиску по образу. Для контроля метод проверен на заведомо живых функциях: RW 0x8F7F2B (вызовы RW 0x6AA4C5 / 0x8F3DFC), RW 0x8F805D (указатель RW 0xC79DF0 и слот 0x58 thunk RW 0x8F3EB2), RW 0x8F417A (слот 0x64 таблицы RW 0xC79788, единственная ссылка RW 0xC797EC), RW 0x8F3DF3 (RW 0x6AA4E4). Ограничение метода: адрес, вычисляемый в рантайме из константы, перебором не находится.
- **INFERENCE (для всей таблицы):** имена классов, назначение ветвей и смысл флагов — статическая интерпретация дизассемблированного кода, не результат запуска игры. Парсер, конструктор, копия и `xfer` не считаются игровым использованием. Отрицательный вердикт дан только там, где перечислены все чтения члена.

## Проверенные цепочки положительных вердиктов

### A. `AttackMoveUsesFormations` (#1) и `ForceSkirmishAI` (#7) — решения ИИ

#1: загрузка RW 0x774E63 (`mov eax,[0xde4b40]`), переход `+0x18` RW 0x774E68, чтение RW 0x774E6B. Гейт по числу членов группы (0x774E3E–0x774E61, сравнение с 1.0 через x87) и вторая проверка `+0xBD` на RW 0x774E79; при обоих ненулевых и отсутствии явной цели (0x774E74) — вызов менеджера строёв RW 0x7747DE на 0x774E8D, чей результат (`test al`) на 0x774E92 уводит на общий путь. Ничего не утверждается о поведении самого менеджера: он уже описан в S-895 / BACKLOG-8.

#7: порядок ветвей проверен по инструкциям, а не по имени: сравнение аргумента 0x6AA49A, затем поле 0x6AA4A7; выделение 0x7C + RW 0x8F7F2B на 0x6AA4AC–0x6AA4C5 против 0xA4 + RW 0x8F3DF3 на 0x6AA4CC–0x6AA4E4; указатель ставится в `[esi+0x2FC]` на 0x6AA4ED. Конструктор RW 0x8F7F2B читает `TeamSeconds` (RW 0x8F7FFC) — то есть два поля связаны: реализация, выбираемая при нулевом `ForceSkirmishAI`, берёт базовое время отряда из того же `TAiData`.

### B. `ForceHordesToLowLOD` (#6) — бит детализации

Все четыре читателя реагируют одинаково: в 16-байтном наборе флагов на стеке (`lea` база `[ebp-0x10]` на 0x86A10C, обнуление RW 0xA3CF28) выставляется байт 6, бит 7 (`[ebp-0xa] | 0x80` на 0x86A15A, `[ebp-0x2a] | 0x80` на 0x86B28B, `[ebp-0x8a] | 0x80` на 0x8A25ED). Исключением является RW 0x86A688, где значение становится bool-аргументом RW 0x73E909 (0x86A70A) и выбирает блок +0x3C4 / +0x3C8 по 0x73E918–0x73E925. Набор флагов из 16 байт передаётся в RW 0x6D165E (создание объекта, 0x86A178 / 0x86B2D0 / 0x8A2615) — INFERENCE: это `ObjectStatusFlags`, а бит 55 в таблице RW 0xD8AFF0 — `CREATE_DRAWABLE_WITH_LOW_DETAIL`; прямо проверено только соответствие индекса 55 байту 6 / биту 7 и имя записи 55.

### C. Низкодетальные деревья (#13–#16) — клиентская ветвь старта карты

RW 0x62DCE4 — цикл объектов старта карты (описан в `GameClient/MapObjectDrawables.h`); ветвь клиентская (деревья, кусты, приметы). Ветка деревьев: три адреса строк 0x62DD05 / 0x62DD25 / 0x62DD4A → поиск шаблона RW 0x6D1305; при `UseLowLODTrees` `+0xD8` (RW 0x62DD8B) и `GameData +0x1774 <= 0` (RW 0x62DD99) найденные указатели нормализуются через RW 0x73C040 (`mov esi,ecx` → RW 0x688D3C, пустой результат → исходный указатель) и пишутся в стековые слоты 0x62DDAC–0x62DDC1, откуда берутся при создании записи дерева; выбор одного из трёх по флагам шаблона +0x5FB / +0x5FC — 0x62E3F3–0x62E41B; масштаб — `+0xE8` (RW 0x62E426), он же аргумент RW 0x683D89 / 0x6808ED / 0x647939 (0x62E44F / 0x62E470 / 0x62E489). Отрицательных утверждений о самой ветви нет: читаются ровно эти четыре смещения.

### D. Пары «бедный / богатый» (#20, #30 против #25, #26)

Функция RW 0x8F805D (слот 0x58 таблицы RW 0xC79788) считает темп отряда: сравнивает деньги игрока `[obj+0x94]` (0x8F8236) с `Poor` `+0x10` (0x8F823C) и с `resourcesWealthy` `+0xC` (0x8F824C); ниже — деление на `TeamsPoorRate` `+0x24` (0x8F8245), выше — на `+0x1C` (0x8F8255). Парные поля зданий — `StructuresPoorRate` `+0x20` и `StructuresWealthyRate` `+0x18`, а также `StructureSeconds` `+0x4` в этой и любой другой функции не читаются: ближайший аналог, `TeamResourcesToStart` `+0x28`, читается в другой функции (RW 0x8F55CA, #28). INFERENCE: ветвь темпа строительства зданий в 2.01 не реализована или реализована без этих полей.
