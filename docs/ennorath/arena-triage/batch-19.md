# Field triage 19/25 — результаты проверки 30 полей Ennorath 1.9.8.2 в RotWK 2.01 (game.dat)

Источник: issue #29 (`Field triage 19/25`). Бинарник: `workspace/RotWK/game.dat` (md5 `daed3668006cd90f01c34e5a7da1901f`, оговорка S-001 — community-modified image). Все адреса прочитаны через `python tools/mod/rw.py workspace/RotWK/game.dat dis|xref|str <addr>`.

Данные мода — из `ennorath-ini-1.9.8.2.zip` (все 30 полей заданы в `data/ini/gamedata.ini`, кроме #8/#9 — они в `data/ini/gamedatadebug.ini`).

Общие факты, на которых построены вердикты:

- Таблица полей блока `GameData` (gamedata): начало `0xBFF580` (рядом — `0xC01200`, последняя найденная строка `WaitToForceMemberToEnterDelay`). Строка таблицы = 16 байт `{name_ptr, parseFn, userData, offset}`; offset — смещение члена в объекте GameData. Парсер вызывается как `push 0xBFF580; push ecx; call 0x42DB80` при `ecx = [0xDE4364]` (RW 0x6441A5 и 0x64423A, функция разбора gamedata.ini 0x644152).
- Глобальный указатель на GameData: `0xDE4364` (запись при создании: RW 0x64234 `mov [0xDE4364], ecx`; очистка в деструкторе RW 0x643DA0/0x643DA7). GameData выделяется размером `0x1254` (RW 0x64420A `push 0x1254`).
- Конструктор GameData с умолчаниями — область RW 0x642A00–0x6448xx (например, `mov [esi+0x13C], bl` RW 0x642C51); деструктор — RW 0x643D63+.
- Сохранение (xfer) GameData: RW 0x540800 (вызывается виртуально, `jmp [edx+0x6C]` RW 0x5407FC), блочные помощники в области RW 0xA28B00+ (шаблон `mov ecx,[esi]; mov eax,[ecx]; call [eax+0x28]` — Xfer).
- Парсеры-строки таблицы: `0x42E558` parseBool (пишет байт), `0x42EC5E` parseInt (пишет dword), `0x42ED00` parseReal (пишет float), `0x42EE5E` parseAsciiString, `0x42ECB2` parseInt-вариант с доп. аргументом, `0x73A396` пара float (min/max).
- Поиск чтений: полный проход capstone по `.text` (2 701 800 инструкций) с восстановлением базового регистра до `mov reg, [0xDE4364]` в пределах функции (скрипт сессии, не коммитится).

Обозначения вердиктов: `RotWK читает (логика)` / `RotWK читает (клиент)` — чтение симуляцией / клиентом (отрисовка, звук, UI); `RotWK не использует` — парсер пишет поле, но чтения нет или оно только у деструктора/копии/save; `не определено` — цепочка не замкнута (детали по полю).

## Уточнение по #18 `MaxUnitSelectSounds` (2026-11-16)

- **Чтение и владелец — разные выводы.** В `0xABEE30` шестой аргумент (`[esp+0x1c]` после сохранения `EBP`) копируется в `ESI` (`0xABEEE9`), затем вызывается `0xABEAD0`; в `0xABEB58` функция читает `[ESI+0xB50]` и передаёт значение в `0xAB39C0`. Последний получает тот же указатель первым аргументом и читает от него `+0x17C4` и `+0x1814` (`0xAB39C8`, `0xAB39E9`). Самостоятельный GameData выделяется размером `0x1254` (`0x64420A`), поэтому эти дальние обращения — сильное основание не приписывать `ESI` GameData по одним соседним offsets; это не устанавливает точный класс указателя.
- Второе чтение, `[ESI+0xB50]` в `0xABA020` (`0xABA025`), тоже не имеет доказанного GameData-владельца. В подтверждённом expiry-dispatch handler `AB4A00` получает event record пятым аргументом (`item+0xC`); он читает `[eventRecord]` и при ненулевом `[eventRecord+0x38]` передаёт этот первый DWORD в `ABA020`. Это прослеживает вызов до переданного runtime-указателя, но не устанавливает его класс или связь с GameData. Другой прямой caller — `0xAB9012`; его база до аллокации не прослежена. Отдельная registration path `0xAB9460` передаёт `0xAB9340` в `0xAB4A90` и пишет `[ESI+0xB50]` (`0xAB94F3`); в caller `0xAB99B5` тот же входной объект используется с `+0x18D4` (`0xAB9980`), поэтому эта запись не доказывает GameData-доступ и не атрибутирует базы чтений `ABEB58`/`ABA025`. `AB9340` не является таблицей `ABF410`. Getter `0xAAD000` не имеет найденного xref или указателя в образе.
- **Связь timer-list с event queue доказана; вызов entry таблицы — нет.** `0xABF410` заполняет 12-DWORD таблицу (entry 0 = `0xABEE30`); её первый аргумент записывается в `table+0x2C`, второй аргумент — указатель на таблицу. Call sites: `0xAB48E2` и `0xAB4B0C`. В пути `0xAB4A90` таблица передаётся в `0xAB59C0` (call `0xAB4B2F`); `0xAB59C0` передаёт её в `0xABFEF0` (`0xAB5A07`), который копирует `0x30` байт в wrapper размером `0x54` и передаёт его в `0xABFDA0`. `0xABFDA0` создаёт type-1 timer node в списке owner `+0x814/+0x818`, сохраняет wrapper в node `+0x1C` (`0xABFF3E`, `0xABFE0A`) и задаёт срок `+0xEA60` мс; node `+0x10` — отдельный handler, `+0x18` — event data, `+0x20` — ID. Затем `0xAB59C0` вызывает `0xAB5290` и опрашивает ID через `0xABFD40`/`0xAC5020`. В `0xAB5290` сначала обрабатывается timer-list `owner+0x814` через `0xABFCD0`, затем вызывается `0xAC4EE0` для event queue того же owner `+0x820`. На type-1 expiry `0xABFAC0` вызывает `0xABF5F0`; ветка типа 1 (`0xABF670`–`0xABF690`) не читает wrapper `node+0x1C`, а передаёт отдельный handler `node+0x10` в type-`0xF` item через `0xAC3D40` с payload размером `0xC`; item добавляется в owner `+0x820`. `0xAC4EE0` dispatch-ит type 15 через `0xAC4CE0`; его case `0xAC4DA8` вызывает указатель функции `item+4` с пятью аргументами: queue owner, три payload DWORD и `item+0xC`. Так могут вызываться handlers вроде `0xAB4A00`/`0xAB4700`. Это доказывает переход `+0x814` → `+0x820`, но не вызов table entry `0xABEE30`: проверенная expiry-ветка использует отдельный `+0x10` handler и пропускает wrapper `+0x1C`. Другие возможные пути вызова таблицы и фактическая runtime-достижимость entry остаются открытыми; владение аргумента 6 (`ESI` в `0xABEE30`) и его связь с GameData не установлены.
- **Не смешивать с callback-table entry:** `0xAB4700` — отдельный timer handler, установленный в пути `0xAB48xx`; в собственной ветке он передаёт callback `0xAB4590` в `0xAB61D0`. Это не вызов entry `0xABEE30` из таблицы `0xABF410` и не устанавливает её аргумент/владельца. Отдельно, `0xAB47A0` пишет `[EBX+0xB48]`, но caller `0xAAE382` передаёт туда свой `ESI`, который в той же функции используется с `+0x18D4`; это не GameData-размерный путь и не база чтений `+0xB50`.
- **Итог:** оставляем `не определено`: чтения по числовому offset и связь expiry-пути `+0x814` → `+0x820` доказаны, но не доказано чтение именно `GameData+0xB50`; type-1 expiry не вызывает entry `0xABEE30`, а её invocation из других путей и владение аргумента 6 остаются открытыми. Не использовать для этого вывода совпадение offsets `0xB40/0xB44/0xB50`.
