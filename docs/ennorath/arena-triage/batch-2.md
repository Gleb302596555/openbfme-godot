- Таблицы взяты из `engine/data/rotwk-201/field-tables.json`, пропущенные в JSON таблицы найдены по указателю на строку в самом PE. Строка таблицы — четыре DWORD: имя, парсер, userData, offset. **Адреса строк таблиц — данные, не инструкции.** Их содержимое проверено в PE; инструкции парсеров и все приведённые ниже читатели прочитаны через `tools/mod/rw.py ... dis`.

## Проверенные цепочки положительных вердиктов

### A. ForceLuaRegistration

RW 0x735941 — функция регистрации; RW 0x735950 проверяет Object+0x260. Если указателя нет, RW 0x73595C берёт Object+4, RW 0x73595F проверяет byte +0x640 (ровно offset поля ThingTemplate), RW 0x735966 выходит при нуле. При допуске выполняются вызовы Lua API, в том числе RW 0x7359DF и RW 0x7359F9. Вызывающий: RW 0x667C6E передаёт объект в эту функцию. Дополнительные геттеры RW 0x734471 и RW 0x73491A сами по себе не использованы как доказательство runtime-поведения. Совпадение типа поддерживается таблицей ThingTemplate и парой соседних байтов в копировании: RW 0x6D26CA / RW 0x6D26D6.

INFERENCE: смысл +0x260 как AI и назначения Lua-записи согласуется с существующим `LuaHost.h` / `LuaScriptEngine.cpp`; непосредственно доказано, что bool управляет допуском в выполняемую функцию, а не только копируется.

### B. ShadowOverrideLODVisibility в DefaultModelConditionState

RW 0x4B26B3 читает state+0xDC; RW 0x4B26C1 / RW 0x4B26C3 перенаправляют store и RW 0x4B26CE вызывает bool-парсер. Offset +0x24 относится к отдельным ShadowParameters. RW 0x4C4ED8 получает тот же state+0xDC, RW 0x4C4F1E передаёт его в RW 0x49A2EB. Для decal-ветвей RW 0x49A3F9 передаёт тот же указатель, RW 0x49A3FD вызывает RW 0x50BF6A. Там RW 0x50BF71 получает второй аргумент в ESI; RW 0x50BF80 проверяет глобальный флаг, а RW 0x50BF86 проверяет именно byte [ESI+0x24]; RW 0x50BF8A пропускает к созданию вместо возврата нуля. Это доказанное клиентское чтение, не редактор/копия. Для другого, одноимённого поля ThingTemplate такой вывод **не** сделан.

INFERENCE: имена ShadowParameters, decal и общего флага — интерпретация этой цепочки и существующих комментариев shadow-кода; условный обход отказа виден непосредственно.

### C. BannerCarrierDestroyHordeOnDeath / BannerCarrierHordeDeathType

Тип данных прослежен отдельно от голых смещений: фабрика RW 0x64B610 вызывает конструктор RW 0x878EE5 (call RW 0x64B634), RW 0x878F0C ставит vtable RW 0xC5BE10. Фабрика передаёт построитель полей RW 0x878B63 (RW 0x64B64A); тот добавляет таблицу RW 0xC5BB50 (RW 0x878B73). Конструктор инициализирует соответствующие члены на RW 0x879023 / RW 0x879029.

RW 0x871915 сравнивает ID удаляемого объекта с сохранёнными ID (+0x264, +0x26C); только во второй ветви RW 0x871949 получает ModuleData из +4. RW 0x871950 проверяет bool +0x224. При true получает список через interface +0x11C (RW 0x871969), идёт по нему и RW 0x871993 передаёт ModuleData +0x228, затем RW 0x87199B вызывает RW 0x698EC3. В последней RW 0x698EE4 / RW 0x698EE7 копируют второй аргумент в структуру запроса; запрос передаётся дальше на RW 0x698EFC. Вызывающие RW 0x8738CC и RW 0x8739F6 прочитаны вместе с начала́ми RW 0x87370B / RW 0x87393E, а не угаданы по соседству.

INFERENCE: это уничтожение членов при потере знаменосца с выбранным типом смерти; непосредственно видны проверка флага, обход членов и передача маски в запрос. Семантика урона согласуется с существующим `HordeBanner.cpp` и S-587, но вывод сделан по заново прочитанным инструкциям. Ничего не утверждается об эффекте на конкретные объекты мода или об их численности.

### D. VisionRearOverride

RW 0x872B9E читает указатель данных через interface-0x118 и RW 0x872BA4 возвращает float +0x274. Это согласуется с interface на module+0x11C: -0x118 даёт module+4, а не обращение к случайному другому классу. В таблице interface RW 0xC5B1F8 слот +0x258 (RW 0xC5B450) содержит RW 0x872B9E; эта таблица ставится на module+0x11C в RW 0x872C1E. Расчёт обзора RW 0x694A45 получает interface через RW 0x68C866 (call RW 0x694B6A). RW 0x694B9B вызывает слот +0x258. RW 0x694BB2 принимает override только при значении >0; иначе RW 0x694BB4 оставляет коэффициент шаблона. RW 0x694BCA умножает радиус на выбранный коэффициент. Это не только невызываемый геттер.

INFERENCE: названия «обзор» и «задний радиус» — интерпретация механизма и имени поля, согласующаяся с `ShroudManager.h`; условие >0 и умножение проверены непосредственно. Соседний slot +0x25C относится к другому коэффициенту, не к этому полю.

## Сводка и сдача

- `RotWK читает (логика)`: **4** — ForceLuaRegistration, BannerCarrierDestroyHordeOnDeath, BannerCarrierHordeDeathType, VisionRearOverride.
- `RotWK читает (клиент)`: **1** — ShadowOverrideLODVisibility в состоянии модели.
- `RotWK не использует`: **0**. Полного доказательства отсутствия runtime-чтений ни для одного поля не получено.
- `не определено`: **25**. Парсер не равен читателю.
