## Закрытые цепочки

### A. Раскачка самолёта — поля 7, 8, 9, 10 (`RotWK читает (логика)`)

Функция `RW 0x673114` (вызывается из `RW 0x675F8C`, тело вызывающего начинается в `RW 0x675996`).
Аргумент `[ebp+8]` — объект `Locomotor`, `[ebp+8]→[eax+4]` — `LocomotorTemplate`:

```
RW 0x673841  mov eax,[ebp+8]      ; Locomotor
RW 0x673844  mov eax,[eax+4]      ; LocomotorTemplate*
RW 0x673847  mov ecx,[eax+0x11C]  ; aeleronCorrectionDegree   (#7)
RW 0x67384D  movss xmm0,[eax+0x118]; elevatorCorrectionRate  (#10)
RW 0x673858  mov ecx,[eax+0x114]  ; elevatorCorrectionDegree  (#9)
RW 0x67386C  movss xmm0,[eax+0x120]; aeleronCorrectionRate    (#8)
RW 0x673874  addss xmm0,[ecx+0x34]   ; крен += rate(0x120)
RW 0x67388C  call 0xA3CF90           ; sin(крен)
RW 0x673891  fmul [ebp+8]            ; * degree(0x11C)
RW 0x673897  movss [esi+4],xmm0      ; боковое смещение объекта
RW 0x6738A5  addss xmm0,[ebp+0xC]    ; тангаж += rate(0x118)
RW 0x6738BB  call 0xA3CF84           ; cos(тангаж)
RW 0x6738C0  fmul [ebp-0x40]         ; * degree(0x114)
RW 0x6738CD  movss [esi],xmm0        ; продольное смещение
```

Вывод: пара `rate` задаёт скорость накопления крена/тангажа, пара `degree` — амплитуду махового смещения
модели самолёта. Это логика (GameLogic/физика), не отрисовка: значения уходят в позицию объекта.

### B. Предел поворота паруса — поле 15 (`RotWK читает (клиент)`)

1. Данные модуля: `createData RW 0x4647CA` → `push 0x194; call 0x42F6E0` → ctor `RW 0x4CFF2A`,
   который пишет vtable `RW 0xBE3A78` (`RW 0x4CFF55`), обнуляет `+0x188` (`RW 0x4CFF35`) и
   инициализирует разбор полей таблицей `RW 0xBE3B30` (`RW 0x4CFF77`).
2. Строка поля: `RW 0xBE3B30`, смещение `0x188`, парсер `RW 0x42EE15`.
3. Модуль отрисовки: `create RW 0x46478F` → `push 0x2F0` → ctor `RW 0x4CFF82`, который пишет
   vtable `RW 0xBE3C40` (`RW 0x4CFF95`) и заводит свои поля `+0x2E8`, `+0x2EC`.
4. Слот `+0x104` vtable `RW 0xBE3C40` = `RW 0x4D00CD`; на всю vtable в образе ровно одна ссылка —
   `RW 0x4CFF97`.
5. Чтение: `RW 0x4D013E` `mov ebx,[edi+4]` (moduleData) → `RW 0x4D01D4` `lea eax,[ebx+0x188]`,
   `RW 0x4D01DA` `fld`, `RW 0x4D01E0` `fcompi`, и при превышении `RW 0x4D01E6` подставляет
   `MaxRotationDegrees` вместо вычисленного угла. Ниже `RW 0x4D0228` сравнивает `sin(угла)` с `+0x190`.

Вывод: поле — верхний предел угла поворота паруса, применяется в клиентском коде отрисовки.

### C. Колёса — поля 1, 2 (`не определено`, что именно найдено)

* `+0xE0` (`MaximumWheelExtension`) читается в `RW 0x6770D2` внутри `RW 0x676ED4`, где из шаблона
  собирается весь блок подвески; у `RW 0x676ED4` нет ни вызывающих, ни указателя в образе
  (полный поиск dword по всем секциям, включая сообщественные). Геттер `RW 0x6701DA` тоже мёртв.
* `+0xE4` (`MaximumWheelCompression`) как float шаблона локомотора в образе не читается вообще;
  все 13 сайтов `[reg+4]+0xE4` — `int`/`byte` чужих структур.
* Банк геттеров локомотора `RW 0x670022`…`RW 0x67022E` (`+0x88`, `+0x8C`, `+0xB8`, `+0xDC`, `+0xE0`,
  `+0x114`, `+0x118`, `+0x11C`, `+0x120`, `+0x2FC`, `+0x308`, `+0x590`) в образе не адресуется:
  вызовы инлайнились, а неинлайновые копии остались без ссылок.

Значит, отсутствие ссылок на `RW 0x676ED4` — не артефакт поиска, а обычная для этого образа картина
(ср. банк геттеров). Вердикт «не использует» всё равно не ставлю: код физики колёс на месте и
`hasSuspension (+0xDC)` в нём проверяется, то есть путь в принципе живой, а вход в него через
косвенную диспетчеризацию я не доказал и не опроверг.

### D. Армейский AI — поля 19–30 (`не определено`)

Закрыто со стороны данных:

* `ArmyDefinition`: размер `0xEC`, ctor `RW 0x82FF49` (пишет значения по умолчанию во все смещения,
  включая `+0x2C` = 0.0f, `+0x40` = 2, `+0x44` = 0x12C, `+0x48` = 0x46, `+0x74` = 1),
  create `RW 0x83027B` (`push 0xEC; call 0x42F6E0` → ctor `RW 0x82FF49`), dtor `RW 0x830149`,
  удаляющий dtor `RW 0x83025F`, инициализация разбора `RW 0x8302A0` (`push 0xC52B40` → `RW 0x42DB80`),
  регистрация строкой `RW 0xDADAAC` в таблице имён (`RW 0xDADAA8` — `ArmyDefinition`).
  Значения по умолчанию из ctor: `RW 0x82FF84` (`+0x2C`), `RW 0x82FFA8` (`+0x40` = 2),
  `RW 0x82FFAF` (`+0x44` = 0x12C), `RW 0x82FFB6` (`+0x48` = 0x46), `RW 0x82FFF7` (`+0x74` = 1).
* Единственный известный кэш указателя на `ArmyDefinition` в AI-объекте — `RW 0x9BCF43`
  (`mov [esi+0x10], eax`).

Со стороны чтения: ни одна функция образа не читает ≥3 из 12 смещений `0x2C`–`0x98` через указатель,
положенный в `[объект+0x10]`; функции-кандидаты, отобранные по такому признаку, при проверке
оказывались чужими (например `RW 0x9BE28D`, `RW 0x9BE3FC` читают `+0x70`/`+0x74`/`+0x7C` отладочной
HUD-структуры, а не `ArmyDefinition`). В BFME2-декомпиляции имена всех 12 членов встречаются **только**
в `ArmyDefinitionManager.cpp` — таблица полей, ctor и копия; на этом основании вероятный вердикт —
`RotWK не использует`, но подтвердить его на уровне образа (исключить инлайновые чтения с другой
цепочкой провенанса) не удалось.

### E. Модульные поля 4, 5, 11, 12, 13, 14 (`не определено`)

Для каждого поля восстановлена цепочка «строка таблицы → парсер → create модуля → ctor → vtable»
(адреса в таблице выше) и просмотрены все виртуальные методы модуля: чтения `[moduleData+смещение]`
не найдено ни в одном случае. Ограничение метода: не виртуальные хелперы модуля и чтения через
локальную копию указателя на данные не покрыты, поэтому вердикт `RotWK не использует` не ставлю.

### F. `playertemplate` — поля 6, 16, 17, 18 (`не определено`)

Все четыре поля привязаны к таблице `RW 0xBF81A8` (61 строка) с точными адресами строк и парсеров.
`PlayerTemplate` не входит в `module-registry.json` (это не модуль), поэтому ctor/vtable класса
автоматически не выводятся, а смещения `0x14C`, `0x1A4`, `0x1C0`, `0x1C4` в образе горячие —
провенанс до шаблона игрока в 1–2 инструкции не разрешается.

## Итог

* `RotWK читает (логика)` — **4**: #7, #8, #9, #10 (раскачка самолёта, `RW 0x673114`).
* `RotWK читает (клиент)` — **1**: #15 (`MaxRotationDegrees` паруса, `RW 0x4D00CD` / `RW 0x4D01D4`).
* `RotWK не использует` — **0**.
* `не определено` — **25**: #1–#6, #11–#14, #16–#30.

Кандидаты в TOP20 (поля, которые RotWK читает, — порту их надо реализовать, а не игнорировать):

1. `W3DSailModelDraw/MaxRotationDegrees` (#15) — клиентский предел угла поворота паруса.
2. `AeleronCorrectionDegree` / `AeleronCorrectionRate` (#7, #8) — амплитуда и скорость раскачки по крену.
3. `ElevatorCorrectionDegree` / `ElevatorCorrectionRate` (#9, #10) — то же по тангажу; все четыре — одна
   функция `RW 0x673114`, реализовывать одной задачей.

Отдельным TOP20-кандидатом стоит завести неудобный вывод по армии: если армейский AI в RotWK 2.01
поля `ArmyDefinition` не читает (см. D и `INFERENCE`), то порту не нужно тащить их в логику — но это
надо подтвердить отдельным заходом, пока статус `не определено`.

## Чего не хватило (чтобы следующий заход не повторял)

1. **Провенанс на этом образе не масштабируется.** Атрибуция «чей это член» по ближайшей записи в
   базовый регистр даёт ложные срабатывания на горячих смещениях (`0x18`, `0x24`, `0x34`, `0x38`,
   `0x3C`, `0x44`, `0x48`, `0x74`, `0x7C`–`0x98`, `0x14C`, `0x1A4`, `0x1C0`, `0x1C4`): в образе
   десятки тысяч обращений к ним, и большинство — чужие классы.
2. **Границы методов без RTTI не восстанавливаются.** `vtable_fns` даёт корректный список слотов
   (`RW 0xBE3C40` — 161), но длина тела метода вычислялась по ближайшей точке вызова; для классов,
   чьи методы не вызываются напрямую, это ломается (пример: `RW 0xBE1CA8` у `FlammableUpdate` дал
   68 «методов», среди них чужие сеттеры). Для `W3DSailModelDraw` метод сработал, потому что нужный
   метод — слот vtable, а поле читается через `[this+4]`.
3. **`PushTo`/косвенная диспетчеризация.** `RW 0x676ED4` (колёса) и весь банк геттеров
   `RW 0x670022`…`RW 0x67022E` не адресуются ни `call`, ни `jmp`, ни указателем — на этом образе это
   норма (инлайн + мёртвые неинлайновые копии), поэтому «нет ссылок» не равно «мёртвый код». Проверено по геттерам `RW 0x6701DA`, `RW 0x6701E4`, `RW 0x6701EE`, `RW 0x6701F8`, `RW 0x670202`, `RW 0x67020C`, `RW 0x6700BE`, `RW 0x6700C8`, `RW 0x670122`: у всех списки вызывающих и указателей пусты.
4. **`ctr`-эвристика модулей иногда промахивается:** для `ArrowStormUpdate` (`RW 0x894063`) ctor не
   пишет vtable в первых 12 инструкциях, для `FlammableUpdate` vtable уходит в чужой класс.
   Нужен разбор пролога целиком, а не окно в 12 инструкций.
