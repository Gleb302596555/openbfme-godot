# Field triage 22/25 — issue #32

## Источники, границы и владелец данных

- Проверены только 30 полей issue #32, в порядке issue. Движок, общие документы и `TOP20.md` не изменялись.
- Предоставленный RotWK 2.01 `game.dat`: MD5 `daed3668006cd90f01c34e5a7da1901f`. Действует оговорка S-001: это предоставленный образ, а не независимая аттестация retail.
- Сначала проверен мод Ennorath 1.9.8.2: у каждого из 30 имён ровно одно активное присваивание в `gamedata.ini` (проверка наличия ключа, не запуск игры). Значения и выдержки INI не публикуются.
- В `engine/data/rotwk-201/field-tables.json` таблицы `gamedata` нет, поэтому строки найдены в PE по указателям на имена. Формат строки — 16 байт: `{имя, парсер, userData, смещение}`. `T` — адрес **строки таблицы (данные, не инструкция)**, `P` — начало парсера, `+` — смещение в `GameData`.
- Владелец доказан отдельно от совпадения смещений. `RW 0x644102` выделяет `0x1254` байта (`RW 0x64410D push 0x1254`, `RW 0x644112 call 0x42F6E0`), `RW 0x644126` вызывает конструктор `RW 0x6429AD`, и `RW 0x64413A` записывает объект в глобальный указатель `RW 0xDE4364`; `RW 0x643D5D` возвращает таблицу полей `RW 0xBFF580`. Строка `TheWritableGlobalData` по `RW 0xBFF288` используется при инициализации. Ниже `RW 0xDE4364` — единственный объект `GameData`.
- Парсеры: `P RW 0x42E558` — bool (`RW 0x42E55E` берёт токен, `RW 0x42E568` разбирает его); `P RW 0x42EC5E` — integer DWORD; `P RW 0x42ED00` — real DWORD; `P RW 0x42E956` — integer через userData `RW 0xDA3A68` (нумерованный выбор времени суток); `P RW 0x42EF99` — три компонента цвета (токен × константа `RW 0xBD1920` = 1/255); `P RW 0x42F247` — три float-координаты; `P RW 0x42EE9A`/`P RW 0x76392F` — строковое поле.
- Все инструкции, обозначенные ниже как RW, прочитаны через `python tools/mod/rw.py workspace/RotWK/game.dat dis <addr>`. BFME2/decomp использован только для навигации; ни один вердикт не перенесён оттуда по аналогии.
- **INFERENCE для всей таблицы:** функциональные имена классов и игровой смысл ветвей — статическая интерпретация дизассемблированного кода, не запуск игры. Совпадение числа смещения с членом другого класса чтением `GameData` не считалось.
- Во всех полях этого выпуска перебор вёлся двумя способами, чтобы не потерять чтения: (а) трассировка `[0xDE4364]` через копии регистров и `lea/add` по всему `.text`; (б) сплошной перебор всех операндов `[reg(+reg)*+disp]` с проверкой, что объемлющая функция действительно трогает `RW 0xDE4364`. Оба прохода независимы и дают одни и те же адреса.

Обозначения цепочек: **A** — массивы освещения объектов (`TerrainObjectsLighting*`); **B** — `TimeOfDay`; **C** — `TintUnitIfPathingForMoreThan`; **D** — `TreeFadeObjectFilter`; **E** — отрицательные цепочки (`UseCloudPlane`, `UseHalfHeightMap`, `UserDataLeafName`, `VideoOn`, `UseCameraConstraints`, `VTune`). ## Проверенные цепочки

### A. Массивы освещения объектов — читаются клиентским рендерером

1. **Раскладка.** Строки таблицы задают смещения: `MorningAmbient +0x434`, `MorningDiffuse +0x440`, `MorningLightPos +0x44C` (T RW `0xBFFC00`/`0xBFFC10`/`0xBFFC20`), `Evening* +0x50C/+0x518/+0x524` (T RW `0xBFFC60`/`0xBFFC70`/`0xBFFC80`), `Night* +0x578/+0x584/+0x590` (T RW `0xBFFC90`/`0xBFFCA0`/`0xBFFCB0`), `AfternoonLightPos3 +0x500` (T RW `0xBFFF50`). Шаг между блоками одного источника — `0xC`, между блоками источников — `0x24`, между временами суток — `0x6C`. База `+0x3C8`, как и в BFME2 `m_terrainObjectsLighting[6][3]`. Арифметика проверяется на самих числах: `0x434 = 0x3C8 + 0x6C`, `0x50C = 0x3C8 + 3*0x6C`, `0x578 = 0x3C8 + 4*0x6C`, `0x500 = 0x3C8 + 2*0x6C + 2*0x24 + 0x18`.
2. **Индексный читатель.** Функция RW `0x442E56`: RW `0x442EEC mov ecx,[eax+0x134]` (время суток), RW `0x442EFD imul ecx,ecx,0x6C`, RW `0x442F02 lea ecx,[eax+0x140]`, RW `0x442F08 lea edx,[eax+0x3C8]`, RW `0x442F0E add eax,0x650` — три массива одновременно. Цикл RW `0x442F3F`–`0x44308A` идёт по трём источникам (счётчик `+0xC`, предел `0x24`, RW `0x443068`, RW `0x443086`) и для каждого берёт ambient `[esi+0x14]`, diffuse `[esi+0xC]`, lightPos `[esi+0x10]` (RW `0x442F55`, `0x442F7B`, `0x442F84`), смешивает с текущими значениями и отдаёт в слоты `+0xC4`/`+0xC8` объекта `RW 0xDE4418` (RW `0x443032`, RW `0x44305A`), а результат пишет в активные слоты `+0x8FC` (RW `0x44306F`). Вызовов по `call` у RW `0x442E56` нет: в неё входит переход `RW 0x4430B6 jmp RW 0x442E56` из функции RW `0x4430A7`, а сам RW `0x4430A7` лежит в слоте `+0x28` таблицы RW `0xBD9C28` (слот-указатель в `.rdata` по `RW 0xBD9C50`).
3. **Слот-читатели.** Таблица RW `0xBD9C28`: `+0x28 → RW 0x4430A7`, `+0xB4 → RW 0x44406D`, `+0xB8 → RW 0x443FA9`, `+0xBC → RW 0x443B5D`, `+0xC4 → RW 0x443E2F`, `+0xC8 → RW 0x443E66`; `+0xC0` (вариант `RW 0x443FA9`) и `+0xB8`/`+0xB4` берут фиксированные `+0x434`/`+0x6BC` (`RW 0x443FC4`, `RW 0x443FCA`) либо `+0x3C8`/`+0x650` с `imul 0x6C` (`RW 0x44408D`, `RW 0x444093`); `+0xBC` = RW `0x443D5F` делает то же по `[gc+0x134]` (RW `0x443D6D`, RW `0x443D82`, RW `0x443D88`). Все они передают цвет в слот `+0x18` устройства (RW `0x443FF5`, RW `0x4440C3`, RW `0x443DC2`) и заполняют источники света объектов через `RW 0x443E9D` (цикл по четырём указателям `+0x148`, `RW 0x443EAC`–`0x443F9C`). Владелец объекта — глобальный `RW 0xDC7574`, инициализируется в RW `0x4496CA` (`[esi]=RW 0xBD9C28`) и RW `0x449875`.
4. **Вторая ветка.** Функция RW `0x4AC284` (вызывающие RW `0x4AD882`, `RW 0x4AE8AE`) читает и перезаписывает `+0x434`, `+0x440`, `+0x44C`, `+0x500`-области блока (`RW 0x4AC54C`, `0x4AC63F`, `0x4AC678`, `0x4ACC0C`, `0x4ACC51`, `0x4ACC96`) и отдаёт цвета в `RW 0x7084EB`.
5. **Почему вердикт «клиент».** Все читатели передают значения в слоты устройств/источников света и в параметры отрисовки, ни один не влияет на игровую логику. Отдельно проверено, что записи в конструкторе RW `0x643B9D`–RW `0x643BDB` (далее `add eax,0x6C` в RW `0x643BE5`, то есть обход всех блоков времени суток) — зануление при инициализации, а не чтение.

**INFERENCE:** названия «устройство», «источник света», «активные слоты» даны по семейству кода и по BFME2-навигации. Доказаны: `GameData`-база, индекс `[gc+0x134]*0x6C`, три базы `+0x140/+0x3C8/+0x650`, три итерации по `0x24`, передача в слоты таблицы `RW 0xBD9C28`.

### B. TimeOfDay — значение, по которому ветвится и логика, и клиент

1. Разбор: T RW `0xBFFA80`, P RW `0x42E956`, userData RW `0xDA3A68`, смещение `+0x134`.
2. Ветка «ночь/не ночь» в объектном коде: RW `0x68D8B3` загружает `GameData`, RW `0x68D8B8 cmp [eax+0x134],4`; при равенстве вызывается RW `0x68B71F`, иначе RW `0x68B6F5`; обе возвращают указатель на вариант ресурса (`+0x2A4` против `+0x2A0`), который уходит в `RW 0x674504` (RW `0x68D8D0`). Вокруг — работа с `[ecx+0x84]` и `RW 0x79FD6F` (получение шаблона).
3. Те же проверки независимо в RW `0x674592`, RW `0x6AEC9B`, RW `0x869B06` (там выбор `[eax+0x2A4]`/`[eax+0x2A0]` виден прямо), RW `0x4C49BC` (сравнение с сохранённым значением и ветвление), RW `0x4FC087` (запись значения в дескриптор и вызов RW `0x64193F` с аргументом 4).
4. Индексация массивов освещения — цепочка A. То есть значение одновременно и логическое (выбор варианта поведения/ресурса), и клиентское (освещение); по правилу выпуска выбран более сильный вердикт `логика`.

**INFERENCE:** семантика «ночь» при значении 4 опирается и на сравнение, и на имя строки `TerrainObjectsLightingNightAmbient` (`+0x578 = 0x3C8+4*0x6C`); конкретная игровая сцена не запускалась.

### C. TintUnitIfPathingForMoreThan — замкнутая логическая цепочка

### D. TreeFadeObjectFilter — читается клиентским обходом деревьев

1. Разбор: T RW `0xC00C20`, P RW `0x76392F`, смещение `+0xEB0`.

**INFERENCE:** «затухание деревьев» — по BFME2 `W3DTreeBufferUpdate.cpp:227`; доказаны чтение `GameData+0xEB0`, дескриптор и обход.

**Кандидаты в TOP20 (RotWK действительно читает, все 24):**

- `TimeOfDay` (#11) — значение выбирает варианты поведения объектов и одновременно индексирует освещение; самое сильное поле выпуска.
- `TintUnitIfPathingForMoreThan` (#12) — единственное поле выпуска с полностью замкнутой логической цепочкой «порог → время → бит состояния объекта», портировать стоит первым.
- `UseShadowMapping` / `UseShadowVolumes` / `UseShadowDecals` (#24, #25, #23) — взаимоисключающие переключатели подсистемы теней (`RW 0x6BFFA9`–`RW 0x6BFFB8`); в порте уже есть `GameLODManager` с этими смещениями, но нет наблюдаемого эффекта.
- `UseFPSLimit` (#19), `UseCloudMap` (#17), `UseLightMap` (#22), `UseHelpTextSystem` (#21), `UseCameraInReplay` (#16, порт уже разбирает), `Use3WayTerrainBlends` (#14), `TreeFadeObjectFilter` (#13), `WaterExtentX`/`WaterExtentY` (#29, #30) — клиентские ветки с прямыми чтениями.
- `TerrainObjectsLightingMorning*/Evening*/AfternoonLightPos3/Night*` (#1–10) — десять полей одного читателя (цепочка A); в TOP20 логично вести их одной позицией «освещение объектов по времени суток», иначе список распухнет дублями.

**Что помечено `INFERENCE`:** имена классов и игровой смысл ветвей (устройство/рендерер `RW 0xDC7574`, фильтр деревьев, ветка теней, расширение воды), отнесение индексов времени суток к названиям полей (арифметика адресов доказана, «Morning = 1» следует из строк таблицы), а также семантика «подсветка юнита» для `TintUnitIfPathingForMoreThan`. Ни одно чтение, ни один вызывающий и ни один адрес не выведены из имени.

**Что не разрешено и почему:** ничего не осталось в `не определено`. Все 30 полей закрыты доказанными чтениями либо отсутствием читателя при полном переборе. Ограничение формулировки: вердикт «не использует» — это утверждение о статическом переборе закрытого PE (два независимых прохода + проверка принадлежности охватывающей функции владельцу `RW 0xDE4364`), а не результат запуска игры.
