# Field triage 17/25 — предварительный результат

Источник: предоставленный `game.dat`, MD5 `daed3668006cd90f01c34e5a7da1901f`, оговорка S-001. Строки таблиц — **данные PE**, не инструкции; их расположение и четыре слова строк проверены поиском указателей в образе PE. Адреса кода ниже просмотрены `tools/mod/rw.py dis`. Это не доказательство чтения поля в игре.

Архив объединённых INI мода проверен первым: активные определения 1–13 и 23 обнаружены в `data/ini/gamedatadebug.ini`, остальные — в `data/ini/gamedata.ini`. Значения не воспроизводятся. ## Узкая сверка прямых FX-helper callsites (не исчерпывающий поиск)

Стриминговый Capstone-проход по `.text` искал прямые вызовы `0x4B1B5A` (`doFXObj`) / `0x494615` (`doFXPos`), перед которыми в окне 24 инструкций было чтение `[reg + 0x48]` (не stack-relative). Полученные совпадения сопоставлены с владельцами и раскладками:

| RW: чтение `+0x48` → helper | Владелец / назначение данных | Отношение к полю |
|---|---|---|
| `0x79A340` → `0x79A34D` | `CastleBehavior::releaseCrew`; `CastleBehaviorModuleData::CrewReleaseFX` (`+0x48`) | отдельный класс данных |
| `0x897AAE` → `0x897AC8` (`doFXPos`) / `0x897AD7` (`doFXObj`) | `SpecialPowerModule`, другая раскладка `+0x48` | отдельный класс данных |
| `0x8C06E2` → `0x8C06ED` | `CrateCollide::onCollide`; `ExecuteFX` (`+0x48`) | отдельный класс данных |
| `0x8C30FA` → `0x8C3113` | `ActiveBody::attemptHealing`; `StructureBody` data `+0x48` из `GlobalData+0x9E0` | условный generic-healing consumer, описанный выше |
| `0x8C5444` → `0x8C5450` | `SymbioticStructuresBody`; его data ctor использует `GlobalData+0x9DC` | отдельный healing-FX путь, не это поле |

Это помогает отсеять ложные совпадения по одному смещению и отделить реальную точку generic healing от других FX-полей. Но проверка ограничена прямыми вызовами этих двух helper-ов и близким чтением `+0x48`; она не исключает дальний/косвенный dataflow, indirect calls или иной playback helper и потому **не является доказательством отсутствия других readers**.

### Проверка оставшихся caller/indirect-call кандидатов

- Xref `Object::attemptHealingFromSoleBenefactor` (`0x690584`) at `0x884DBA` находится в method `0x884CF1`: vtable cell `0xC5FA54` (`0xC5FA04 + 0x50`) указывает на него, а name getter `0x884A84` возвращает строку `PropagandaTowerBehavior` (`0xC0BAB4`). Метод проверяет optional upgrade, получает Body interface цели и вызывает generic sole-benefactor healing с владельцем behavior как источником. Это ещё один generic-healing caller, не repair-specific путь; сам caller не вызывает FX helper.
- `0x7E97B5` и `0x75D2B3` — не вызовы getter `ActiveBody` `0x8C3A7B` (slot `+0xEC` в таблице `0xC720F0`). В обоих случаях receiver получен через вызов `0x68C866`, который берёт `Object+0x258` и вызывает contain slot `+0x7C`, возвращающий `HordeContainInterface*`; в HordeContain interface tables `0xC5B1F8`, `0xC5BE98`, `0xC5CFA8` slot `+0xEC` содержит `0x872B69` (`HordeContainInterface::isMainFormation`). `0x75D2B3` находится в formation-image ветке `CommandButton::updateToggleImage`; `0x7E97B5` проверяет main-formation у кандидата в обходе команды/объектов. Эти два кандидата не являются читателями `StructureBody` data.
- Для обычного Dozer repair disassembly `0x88DB61`/`0x88DC46..0x88DC6A` показывает расчёт heal amount и единственный вызов `0x690584`; при успехе ветка идёт к возврату `0x88DE32`, без локального FX-helper вызова. Объект `STRUCTURE` затем попадает в уже описанный generic-healing gate `ActiveBody::attemptHealing`, который пропускает default-FX playback для `STRUCTURE`.

Это сужает перечисленные кандидаты, но не доказывает отсутствие иных косвенных readers/playback helpers. Ennorath-configured non-`STRUCTURE` `StructureBody` healing event и отдельный repair-specific runtime route по-прежнему не установлены; статус остаётся unresolved, не no-reader.

## Сводка и остаток

- RotWK читает (логика): **2** — `DefaultStructureRubbleHeight` и `DefaultStructureRepairBuffFxList` (условный generic-healing playback consumer; обычный structure-repair playback не доказан).
- RotWK читает (клиент): **2** — `GetHealedAnimationTime` и `GetHealedAnimationZRise` (условный вызов из `AutoHealBehavior::update`, RW 0x8558C0); RotWK не использует: **0**; не определено: **26**. Для `DefaultStructureRepairBuffFxList` доказаны resolution при инициализации и conditional generic-healing playback site: `StructureBody` data `+0x48` передаётся FX helper `0x4B1B5A` после роста health, но только для non-`STRUCTURE`, non-`AIRBORNE_TARGET`; это кодовый runtime consumer, но не playback при реальном ремонте структуры.
- Кандидат TOP20: `DefaultStructureRubbleHeight`, с учётом уже зарегистрированного S-342; сначала проверить, не покрывает ли существующая задача нужный объём. `DefaultStructureRepairBuffFxList` имеет подтверждённый conditional generic-healing runtime consumer, поэтому это не no-reader поле; однако обычный Dozer repair передаёт `STRUCTURE` и обходит чтение/helper. Фактический Ennorath healing event для non-`STRUCTURE` `StructureBody` и отдельный repair-specific route не установлены, поэтому playback при обычном ремонте структуры остаётся открытым. Для пары `GetHealedAnimationTime/ZRise` доказан условный клиентский путь; Ennorath закомментировал `GetHealedAnimationName`, так что healed Anim2D для этой конфигурации не активируется. `DrawEntireTerrain` и `FramesPerSecondLimit` по-прежнему имеют чтения с открытыми классификацией и вызывающей цепочкой.
- **INFERENCE**: семантическая интерпретация пути rubble через описание `ActiveBody.cpp`; в оригинальной игре не проверялась. Остальные открытые совпадения не объявлены готовыми вердиктами.
- Осталось: доказать пути остальных 26 полей; для `DefaultStructureRepairBuffFxList` — достигает ли Ennorath-configured non-`STRUCTURE` `StructureBody` generic healing path либо существует иной repair-specific route; поиск таблиц/иной обработки 14 имён без точной строки, полное перечисление обращений к смещениям, доказательство классов и виртуальных вызовов.
