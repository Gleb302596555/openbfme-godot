# Port 266: tree-buffer fade investigation

RotWK 2.01: `W3DTreeBuffer::update` RW 0x4ED508, vertex update RW 0x4EB992; donor BFME2 0x000EDB47 `W3DTreeBufferUpdate.cpp` (comparison only).

* RW 0x4ED508 first handles buffer rebuild, skips under client/game-state gates, builds the persistent partition filter from GlobalData +0xEB0, then iterates buffer records; invalid or currently excluded records are skipped. It updates sinking and toppling before fade. Only records with visible byte +0x44 participate in the query.
* When GlobalData +0x40 is enabled, the partition service exists and RW 0x63252F permits this frame, the query uses the type's +0x60 radius and RW mode 1, the 2D bounding-circle edge distance (RW 0xDBDAF8 entry 1 -> 0xA3AE50). This corresponds to the port enum `FROM_BOUNDINGSPHERE_2D`, not `FROM_CENTER_3D`: RW and port enum values 1 and 2 are swapped. A candidate can qualify when its centre lies outside the fade distance but its bounding circle reaches inside; height is not part of this distance. An earlier version of this analysis incorrectly called the mode 3D. Candidates must have a controlling player and not be effectively dead. A candidate without the invisibility model conditions is accepted unless status 0xF is set and status 0x11 is clear; otherwise only an allied candidate relative to the local client player is accepted. The first accepted object chooses type +0x5C; no candidate chooses 255. When enabled, differing current +0xE0 and target +0xE4 mark the vertex buffer dirty.
* RW 0x4EB992 checks buffer readiness, then processes records in each mesh batch. Valid records with topple, unequal alpha or other vertex dirtiness are processed; if GlobalData +0x40 is enabled, current opacity moves toward target by type +0x58, clamped at the target. The rest of the function transforms vertices, handles morph, and writes vertex data. It is a client render update, not a simulation frame.
* Switch-off decision (user, 2026-11-17): preserve retail behavior. Disabling AllowTreeFading does **not** set target to 255 in these routines: RW 0x4ED692 skips the query without writing the target, and RW 0x4EBA5E skips the alpha step. Only an enabled query finding no eligible object writes 255 (RW 0x4ED780). The future switch-off test must start from a partially faded record and verify that both words stay unchanged, not force an opaque result.
* `TerrainTrees` is synchronized map/logic state; it does not own the tree-buffer visible byte, local-client player, client frame scheduling or vertex-buffer update. Putting this local-view-dependent state in its per-logic-frame update would change multiplayer simulation based on each client's view and would advance at a different cadence. The existing Godot opacity setter also participates in morphs and sub-object fade. A correct integration needs a client-owned tree-buffer update boundary, including visibility and timing; no competing simulated path is introduced here.

## Port integration boundary

`LiveGame.h` (`NewGameOptions::logicThread`, `logic()`, `presentedSnapshot()`) documents a single simulation owner and immutable presented snapshots. `GameWorld::_process` (`GodotGameWorld.cpp`, RENDERWAIT-1 around `heldClientWork` / `advance`) calls `updateTreeTopple` after the worker may have resumed, and then calls `updateMorphs`, which also writes the same instance opacity. Directly querying `GameLogic::partition()` from that render update either waits for the worker or reads mutable simulation data unsafely. `ObjectSnapshot` currently supplies position, owner index, effective-dead and presentation stealth look, but not the complete retail predicate inputs (status 0xF / 0x11, the actual filter decision, and local alliance at query time); adding general snapshot data needs the owner-thread publisher and its serial/parallel equivalence tests. `W3DInstancer::instance_outside` exists, but its camera-frustum result is not by itself proof of the RW tree-buffer visibility byte. This is a cross-client snapshot and visibility mechanism, not a missing shader.

`GameWorld::heldClientWork` is an existing safe owner window for querying the live partition: it is invoked before `LiveGame::advance` in threaded mode and after it in single-threaded mode, and returns immediately without work when `logicHeld()` is false. It is therefore a candidate integration point; the absence of a safe query window is **not** established as a blocker. However, a busy worker skips that window entirely, and the exact RW per-client frame gate / visible byte and opacity-versus-morph interactions still need to be preserved rather than assuming every frame or every tree is eligible. The existing `TreeTopple` client record and `advance()` already provide a candidate client-owned home for alpha stepping. Any continuation should investigate this path before changing the shared snapshot mechanism.

## Visibility and candidate bits

RW 0x4EABDE refreshes each tree record’s visible byte at +0x44 from the negated result of RW 0x4E41B5, passing its scaled/transformed sphere at record +0x48. RW 0x4E41B5 walks a list of objects and calls virtual slot +0x204 on each, returning true only if all return true; the list and its view implementations must be traced before equating this to Godot’s `instance_outside`. DONOR BFME2 0x000E488F (`W3DFloorBuffer.cpp`, comparison only) describes the same all-predicate and inverted use, but does not establish every list member. RW 0x68FC06 checks model-condition bits 0x222 and 0x223 through RW 0x46E918, not KindOf bits; the status tests use RW 0x44DDEC. The existing `Object::testModelCondition` is the relevant port accessor.

The list is copied into the tree buffer by RW 0x4ED8E4, called from RW 0x469503 after a nonempty-list check; RW 0x4E3614 forwards the list and compares positions via RW 0x53B370 before refreshing it. The DONOR BFME2 0x00071245 (`RTS3DSceneVisibilityCheck.cpp`) uses the same slot +0x204 for `CameraClass::Cull_Sphere`; the source supports a camera interpretation but the full RotWK producer/type chain has not been confirmed. RW 0x4EC93A initializes visible false and both alpha words to 255. The tested record bounds are the transformed type sphere (RW 0x4EC93A, region beginning at 0x4ECB43), not simply the tree position.

`GodotW3DInstancer::instance_outside` cannot be substituted unchanged for RW’s tree sphere: it tests the instance origin and `cull_radius`, which deliberately adds a non-retail animation margin (stop S-1730), whereas RW 0x4EC93A uses the scaled type sphere including its local centre, translated by tree position. Thus the two visibility predicates can differ near the edge even when both use frustum planes. The donor identifies the passed list as cameras (DONOR BFME2 0x000E3CE1, `FlatHeightMapUpdateCenter.cpp`), and the existing port identifies RW 0x470CC5 as camera Cull_Sphere, but the exact RW producer/type path remains to be established. Fixing the shared instancer bound for every user would exceed this port; do not replace it with an unrelated local approximation.

## Query cadence gate

RW 0x63252F computes signed integer `q = [0xD9F60C] / [0xECA400]`; if `q < 6` it permits only client counter +0x34 equal to `6 / q`, otherwise only counter 1. The image initial values at those addresses are 30 and 8, yielding counter 2 (not every render call), assuming they have not been changed at runtime. RW 0x6325A0 increments +0x34 and handles the six-phase cycle; `LiveGame::advance` instead normally runs each whole logic frame together (S-151), and its optional six-tick path can process multiple ticks in one call. `heldClientWork` runs once per call and may be skipped when the worker is busy. Consequently neither blindly querying on each held window nor deriving the retail phase from the number of `heldClientWork` calls preserves this gate. Runtime writes to the two globals and the client counter at the actual call site still need confirmation before treating the image values as an invariant.

## Morph and fade are separate retail draw paths

RW 0x4ED508 skips a record with nonzero morph state +0xC8 before updating its fade target (0x4ED5E9); its previous target is retained. RW 0x4EB992 steps current alpha before its visibility and morph checks (0x4EBA54–0x4EBAAF), provided its batch is processed, but does not write the tree-buffer vertices for a morphing record. RW 0x4EC40E creates separate morph render objects with opacity 1 and 0; RW 0x4EACB0 changes those opacities to complementary morph fractions independently of the tree-buffer alpha. Thus multiplying the morph fractions by fade alpha is not supported by these branches. The current `GameWorld` reuses the regular instance as a morph object and `morphTreeEnd` sets its opacity to 1, so any future fade integration must restore the stored tree alpha after morph, rather than having competing writers or applying a guessed product. This characterizes these branches, not the unresolved scheduling of buffer updates or all failure cases.

## Filter reference player and unset filter

The static filter wrapper initialized by RW 0x4ED508 at 0x4ED578–0x4ED5B2 holds GlobalData +0xEB0 as its filter, a null reference player and match flag 1. Its vtable 0xBE4CC8 calls RW 0x66122D, which forwards that null player to RW 0x7640C1; relationship-constrained ObjectFilters cannot match without the reference player (RW 0x763543 at 0x7635E5–0x7635F6). This is distinct from the later visibility/alliance check, which uses the local client player. Do not pass that local player to `ObjectFilterMatch::allows` for this filter. For an unset handle, RW 0x763543 constructs the default filter via RW 0x762BDF: rule ALL, empty lists/masks, flag 1, no side or relationships. `GameLogicSettings` keeps the omitted field as null, so a future query must represent that retail default rather than treating null as reject-all.

## Client alpha save / load

RW 0x4ED7F6 installs tree-buffer vtable 0xBE4E80, whose +0xC slot is RW 0x4ECE3E. That routine transfers the two per-record alpha words (RW 0x4ED1F0–0x4ED201) and, after recreating the record, restores them to +0xE0 / +0xE4 (RW 0x4ED3F8–0x4ED404). DONOR BFME2 `W3DTreeBufferXfer.cpp` identifies the corresponding entry as `xfer` and its early-return mode as light CRC. Consequently client ownership does not mean retail drops opacity on save/load: a complete implementation needs a client tree-buffer persistence path, without putting per-view values in synchronized `TerrainTrees` or the logic hash. The current `TreeTopple` client records have no xfer method; the appropriate client save integration and compatibility need separate verification, and adding just an alpha field without that path would lose state.

## Save block registration and native container v3

RW 0x6DF73E registers the normal save list; the `CHUNK_GameClient` registration starts at RW 0x6DF95C (label pushed at 0x6DF974, registration call 0x6DF980). The immediately preceding chunk is `CHUNK_TacticalView` and the next is `CHUNK_InGameUI`. `CHUNK_TerrainVisual` is registered separately later (label at 0x6DFA5F, call 0x6DFA6B), after `Partition`, `Shroud`, `Collision` and `ParticleSystem`. Thus the RW registration evidence supports *separate* client and terrain-visual chunks, not a claim that the latter is nested inside `CHUNK_GameClient`; the tree-buffer xfer at RW 0x4ECE3E belongs to the terrain visual path. DONOR BFME2 `GameStateInit.cpp` agrees on this registration order. The complete normal-save order is documented in `docs/SAVES.md` section 1; RW 0x6DDF2F is its save-stream writer.

The OpenBFME container is not a retail save stream: v3 adds an optional, SHA-256 checked and bounded `CLNT` part after `LWLD` to carry a versioned client snapshot, without changing the existing simulation `SNAP`. v1/v2 remain readable and produce an empty client payload; v3 omits `CLNT` when it has no client data. A missing payload is not yet wired to tree alpha defaults because tree client serialization and its lifecycle are still unimplemented. The new envelope test exercises opaque sample bytes only and is not evidence that a live tree survives a save/load.
