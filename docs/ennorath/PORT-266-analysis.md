# Port 266: tree-buffer fade investigation

RotWK 2.01: `W3DTreeBuffer::update` RW 0x4ED508, vertex update RW 0x4EB992; donor BFME2 0x000EDB47 `W3DTreeBufferUpdate.cpp` (comparison only).

* RW 0x4ED508 first handles buffer rebuild, skips under client/game-state gates, builds the persistent partition filter from GlobalData +0xEB0, then iterates buffer records; invalid or currently excluded records are skipped. It updates sinking and toppling before fade. Only records with visible byte +0x44 participate in the query.
* When GlobalData +0x40 is enabled, the partition service exists and RW 0x63252F permits this frame, the query uses the type's +0x60 radius and mode 1 (3D). Candidates must have a controlling player and not be effectively dead. A candidate without the invisibility KindOf states is accepted unless status 0xF is set and status 0x11 is clear; otherwise only an allied candidate relative to the local client player is accepted. The first accepted object chooses type +0x5C; no candidate chooses 255. When enabled, differing current +0xE0 and target +0xE4 mark the vertex buffer dirty.
* RW 0x4EB992 checks buffer readiness, then processes records in each mesh batch. Valid records with topple, unequal alpha or other vertex dirtiness are processed; if GlobalData +0x40 is enabled, current opacity moves toward target by type +0x58, clamped at the target. The rest of the function transforms vertices, handles morph, and writes vertex data. It is a client render update, not a simulation frame.
* Important mismatch with the requested test: disabling AllowTreeFading does **not** set target to 255 in these routines. RW 0x4ED692 skips the query without writing the target, and RW 0x4EBA5E skips the alpha step. Only an enabled query finding no eligible object writes 255 (RW 0x4ED780).
* `TerrainTrees` is synchronized map/logic state; it does not own the tree-buffer visible byte, local-client player, client frame scheduling or vertex-buffer update. Putting this local-view-dependent state in its per-logic-frame update would change multiplayer simulation based on each client's view and would advance at a different cadence. The existing Godot opacity setter also participates in morphs and sub-object fade. A correct integration needs a client-owned tree-buffer update boundary, including visibility and timing; no competing simulated path is introduced here.

## Port integration boundary

`LiveGame.h` (`NewGameOptions::logicThread`, `logic()`, `presentedSnapshot()`) documents a single simulation owner and immutable presented snapshots. `GameWorld::_process` (`GodotGameWorld.cpp`, RENDERWAIT-1 around `heldClientWork` / `advance`) calls `updateTreeTopple` after the worker may have resumed, and then calls `updateMorphs`, which also writes the same instance opacity. Directly querying `GameLogic::partition()` from that render update either waits for the worker or reads mutable simulation data unsafely. `ObjectSnapshot` currently supplies position, owner index, effective-dead and presentation stealth look, but not the complete retail predicate inputs (status 0xF / 0x11, the actual filter decision, and local alliance at query time); adding general snapshot data needs the owner-thread publisher and its serial/parallel equivalence tests. `W3DInstancer::instance_outside` exists, but its camera-frustum result is not by itself proof of the RW tree-buffer visibility byte. This is a cross-client snapshot and visibility mechanism, not a missing shader.
