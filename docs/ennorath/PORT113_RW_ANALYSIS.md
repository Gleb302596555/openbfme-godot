# Port 113: система light points «Войны Кольца» — анализ RotWK 2.01

Рабочая запись по issue #280. Адреса прочитаны через `tools/mod/rw.py dis|xref` из RotWK 2.01 (`game.dat`, MD5 `daed3668006cd90f01c34e5a7da1901f`, оговорка S-001). Донор — Open-BFME-2 (декомпиляция BFME2 1.06). Значения и выдержки INI мода здесь не приводятся. Предыдущая запись по этой же системе — `PORT99_RW_ANALYSIS.md` (поле `LightPointsUpSound`).

Итог коротко:

- Трекер — отдельный объект внутри `Player` по смещению `+0x338` (vtable RW `0xC13FD4`): очки (`+4`, то есть `Player + 0x33C`) и список индексов уровней (`+8`, вектор `int`).
- `TheLightPointSystem` (RW `0xDE8C04`) создаётся при старте движка **безусловно** (RW `0x63BB7B` .. RW `0x63BBB9`) и больше нигде не обнуляется: во время любой игры, в том числе скирмиша, он не null. Комментарии порта «no manager in a skirmish» неверны.
- Система хранит уровни (`LightPointLevel`, блок INI с полями `Name` и `SpecialAbilities`) и отвечает на три вопроса: в каком уровне названа спецсила, хватает ли игроку очков на неё, какой индекс у уровня с данным именем.
- Скрипты: пять действий (351–354, 405) и одно условие (124); номера подтверждены таблицами переходов диспетчеров.
- Спецсилы: проверка в `SpecialPowerStore::canUseSpecialPower` (RW `0x7B1E07`) и две траты `LightPointCost` (RW `0x853FCB`, RW `0x897A5E`).
- Звук `LightPointsUpSound` играет только тело `PLAYER_GIVE_LIGHT_POINTS` (RW `0x6AB148`), и только при положительной сумме.
- Сохранение RotWK пишет список уровней, но **не пишет очки** (раздел 8).

## 1. Трекер игрока: `Player + 0x338`

Класс без имени в образе; дальше «трекер». Размер `0x14`.

| Смещение | Что | Источник |
|---|---|---|
| `+0` | vtable RW `0xC13FD4` | конструктор RW `0x6ACE1F` |
| `+4` | очки, `int` | RW `0x6ACE13` (`and [esi+4], 0`) |
| `+8` .. `+0x10` | вектор `int` (begin, end, cap): индексы уровней | RW `0x6ACE1C` .. RW `0x6ACE25` (helper RW `0x478CBE`) |

Цепочка «создание → конструктор → vtable → слот»:

- Конструктор `Player` (функция RW `0x6B1A79`): RW `0x6B1BCA` `lea ecx, [esi+0x338]`, RW `0x6B1BD0` `call 0x6ACE0F`.
- Деструктор `Player` (функция RW `0x6B1CE4`): RW `0x6B1E56` `lea ecx, [esi+0x338]`, RW `0x6B1E60` `call 0x6ACE35`.
- vtable RW `0xC13FD4`, четыре слота, за ними строка RW `0xC13FE4`:
  - слот 0 RW `0x6ACE71` — удаляющий деструктор (зовёт RW `0x6ACE35`);
  - слот 1 RW `0x63F3BF` — один `ret`;
  - слот 2 RW `0x6ACE2F` — возвращает строку RW `0xC13FE4` `LightPointSystem` (имя блока для помеченных файлов);
  - слот 3 RW `0x830D3F` — xfer. Это единственная ссылка на RW `0x830D3F` во всём образе (поиск dword по всем секциям: только RW `0xC13FE0`).
- Слот 3 зовётся через `Xfer::operator==(Snapshot&)`: базовая реализация RW `0xA1F5A6` делает `call [eax+0xC]` по vtable снимка. Обёртки XferSave RW `0xA205DA` и XferLoad RW `0xA20229` в режиме помеченного файла дополнительно зовут слот 2 (`call [eax+8]`) и BeginBlock / EndBlock (слоты Xfer `+0x14` / `+0x18`).

Методы трекера (`thiscall`, `ecx` = трекер):

| Адрес | Что делает |
|---|---|
| RW `0x8309E3` | `add [ecx+4], arg` (RW `0x8309E7`); если результат отрицательный (RW `0x8309EA` `jns`), `and [ecx+4], 0` (RW `0x8309EC`). Прибавляет любую сумму, в том числе отрицательную, и не даёт уйти ниже нуля. |
| RW `0x8309F3` | Есть ли индекс в списке: линейный перебор, `al = 1` на RW `0x830A0F`, иначе `al = 0` на RW `0x830A0A`. |
| RW `0x830D1E` | Добавить индекс: если RW `0x8309F3` вернул 0 (RW `0x830D2C`), `push_back` (RW `0x830D36` → RW `0x90BE00`). Повтор не добавляется. |
| RW `0x830AB9` | Убрать индекс: первый равный элемент (RW `0x830AC8`) стирается одним `erase` (RW `0x830ADA` → RW `0x5FF944`). Нет такого — ничего. |
| RW `0x830D3F` | xfer, раздел 8. |

Сброс при инициализации игрока (функция RW `0x6B0239`, `esi = 0` с RW `0x6B026B`):

- RW `0x6B033A` `lea ecx, [ebx+0x340]`, RW `0x6B034E` .. RW `0x6B0355` `call 0x5FF9D3` с парой (begin, end): список уровней опустошается.
- RW `0x6B0362` `mov [ebx+0x33C], esi`: очки = 0.

## 2. Функции `Player`

| Адрес | Что делает | Кто зовёт |
|---|---|---|
| RW `0x6AA8F4` | `mov eax, [ecx+0x33C]; ret` — очки. | RW `0x7C36F3` (действие 405), RW `0x7E5B86` (условие 124) |
| RW `0x6AA8FB` | Проверка спецсилы. `[0xDE8C04]` null (RW `0x6AA902`) → `al = 1` (RW `0x6AA918`). Иначе RW `0x6AA911` `call 0x830AE3(трекер, шаблон)`. | RW `0x7B1E07` |
| RW `0x6AA91D` | Трата: `sub [ecx+0x33C], arg` (RW `0x6AA927`); отрицательный результат (RW `0x6AA929` `jns`) → 0 (RW `0x6AA92B`). Систему не проверяет. | RW `0x853FCB`, RW `0x897A5E` |
| RW `0x6AA931` | `and [ecx+0x33C], 0` — очки = 0. Список уровней не трогает. | RW `0x7BD340` |
| RW `0x6AA939` | Дать уровень по имени: только если `[0xDE8C04]` не null (RW `0x6AA940`) → RW `0x6AA94F` `call 0x830E63(трекер, имя)`. | RW `0x7BD381` |
| RW `0x6AA957` | Забрать уровень по имени: только если система не null (RW `0x6AA95E`) → RW `0x6AA96D` `call 0x830BD5(трекер, имя)`. | RW `0x7BD3C2` |
| RW `0x6AB148` | Дать очки и сыграть звук, ниже. | RW `0x7BD302` (единственный вызов) |

RW `0x6AB148(amount)`, `ret 4`:

1. RW `0x6AB15F` .. RW `0x6AB165`: `call 0x8309E3` на трекере с `amount`. Выполняется всегда, до любых проверок.
2. RW `0x6AB16A` .. RW `0x6AB171`: шаблон игрока `[esi+0x34]` null → выход.
3. RW `0x6AB173` .. RW `0x6AB176`: `amount <= 0` (`jle`) → выход. Звук только при положительной сумме.
4. RW `0x6AB178` .. RW `0x6AB17F`: указатель звука `[шаблон+0x1A4]` null → выход.
5. RW `0x6AB181` .. RW `0x6AB187`: `TheAudio` `[0xDE42FC]` null → выход.
6. RW `0x6AB189` .. RW `0x6AB191`: копия события (RW `0x6DA95E`); RW `0x6AB196` .. RW `0x6AB1A2`: индекс игрока `[esi+0x54]` в событие (RW `0x66ECE1`); RW `0x6AB1A7` .. RW `0x6AB1B6`: `TheAudio->vtbl[+0x64]` (addAudioEvent); RW `0x6AB1C3`: деструктор копии (RW `0x6DABCB`).

Событие без позиции и без объекта, с индексом игрока: кому оно слышно, решает общий фильтр addAudioEvent по типу события (в порте `AudioManager::shouldPlayLocally`, RW `0x4533A9`).

Сеттер без вызовов: RW `0x6B2EC4` (`mov [ecx+0x33C], arg; ret 4`) и соседние аксессоры RW `0x6B2E8F` .. RW `0x6B2EC1` не имеют ни вызова, ни ссылки из данных (xref по `.text` и поиск dword по образу пусты). Недостижимый код; не портируется.

Прочие обращения по смещению `0x33C` в образе (64 совпадения с базовым регистром) принадлежат другим классам: `Object` (RW `0x6980B4` в `Object::xfer`, RW `0x886849` после поиска объекта по id), шаблоны оружия и прочие (RW `0x6D1F8F`, RW `0x73D612`, RW `0x73F888`, RW `0x785224`, плавающие `fld`/`fstp`). У `Player` это только RW `0x6AA8F4`, RW `0x6AA91D`, RW `0x6AA931`, RW `0x6B0362`.

## 3. `TheLightPointSystem`

Создание: RW `0x63BB7B` .. RW `0x63BB8F` (`operator new`, конструктор RW `0x830B85`), RW `0x63BBA6` имя RW `0xBFEE70` `TheLightPointSystem`, RW `0x63BBB4` `push 0xDE8C04`, RW `0x63BBB9` `call 0x6376C1` (initSubsystem). Условий вокруг нет: это линейный список подсистем старта движка (перед ним подсистема с глобалом RW `0xDE7860`, после — объект размером `0x34`).

Все ссылки на RW `0xDE8C04` (`rw.py xref`): RW `0x63BBB5` (адрес для initSubsystem), RW `0x6AA8FC`, RW `0x6AA93A`, RW `0x6AA958`, RW `0x830EC4`, RW `0x830EF6`, RW `0x830FBA`, RW `0x853FA7`. Кроме старта все — чтения. Значит, между стартом и остановкой движка указатель не null.

Класс: базовый конструктор RW `0x5B4679` (SubsystemInterface), vtable RW `0xC5324C` (RW `0x830B96`), вектор указателей на уровни по `+0xC` (RW `0x830B93` .. RW `0x830B9C`).

Слоты vtable RW `0xC5324C` (0–13): RW `0x830DEA` (удаляющий деструктор → RW `0x830C55`), RW `0x5FFC33`, RW `0x5B4B9A`, RW `0x63F3BF`, RW `0x7FEAC1`, RW `0x9188EB`, RW `0x851E97`, RW `0x9F3A3C`, RW `0x63F3BF`, RW `0x830A13`, RW `0x63F3BF`, RW `0x7FEAC1`, RW `0x63F3BF`, RW `0x9F3A3C`. Свои тела у системы только в слотах 0, 1 и 9:

- слот 1 RW `0x5FFC33` (init): `erase(begin, end)` вектора `+0xC` (RW `0x5FFC3B` → RW `0x5FF9D3`);
- слот 9 RW `0x830A13` (reset): для каждого ненулевого уровня `call 0x5E2E2E` (RW `0x830A22`). RW `0x5E2E2E` — удаление цепочки переопределений: объект с флагом `+8` удаляет себя и возвращает 0 (RW `0x5E2E31` .. RW `0x5E2E46`), иначе рекурсивно чистит `+4` (RW `0x5E2E48` .. RW `0x5E2E54`). Сами уровни остаются.
- слот 10 RW `0x63F3BF` (update): `ret`.

Имена слотов 1, 9, 10 (init, reset, update) — DONOR BFME2 (`Libraries/Source/subsystem/SubsystemInterface.h`); тела прочитаны в RW.

Деструктор RW `0x830C55`: удаляет каждый уровень (RW `0x830C81` .. RW `0x830C8E`), чистит вектор, зовёт базовый деструктор RW `0x5B468A`.

Методы системы (`thiscall`, `ecx` = система):

| Адрес | Что делает |
|---|---|
| RW `0x830A3B(шаблон)` | Индекс уровня, в котором названа спецсила. Для уровня `i` (вектор `+0xC`) перебирает четырёхбайтные элементы `[уровень+0x18]` .. `[уровень+0x1C]`; совпадение с `[финальное переопределение шаблона + 0x14]` (id спецсилы; RW `0x830A75` `call 0x688D3C`, RW `0x830A7C` `cmp`) → возвращает `i` (RW `0x830AB4`). Нет совпадений → `-1` (RW `0x830AAA`). Сам уровень берётся из вектора как есть, без перехода к его переопределению. |
| RW `0x830AE3(трекер, шаблон)` | `0x830A3B`; индекс `< 0` (RW `0x830AEE`) → `al = 1` (RW `0x830AF0`). Иначе `al = (трекер.очки >= [финальное переопределение + 0x30])` (RW `0x830AF8` .. RW `0x830B07`, `setge`): хватает ли очков на `LightPointCost`. Список уровней трекера **не читается**. |
| RW `0x830BA6(вектор, имя)` | Поиск уровня по имени: сравнение `[уровень+0x10]` через RW `0x4065AA` (0 = равны). RW `0x4065AA` → RW `0x406307` → RW `0x4052F9`: `memcmp` (импорт RW `0xBD0698` через RW `0xA3D01A`) по меньшей длине, затем разность длин. Сравнение с учётом регистра. |
| RW `0x830E63(трекер, имя)` | Дать уровень. Для `i` по вектору: уровень, при ненулевом `+4` — его финальное переопределение (RW `0x830E7A` .. RW `0x830E81` → RW `0x465AF4`); имя `+0x10` равно (RW `0x830E8D`, RW `0x830E94`) → RW `0x830EAB` `call 0x830D1E(i)` и выход. Нет такого имени → ничего. |
| RW `0x830BD5(трекер, имя)` | Забрать уровень: тот же перебор (RW `0x830BEC` .. RW `0x830BFF`), на совпадении RW `0x830C1D` `call 0x830AB9(i)`. |
| RW `0x830E06(уровень)` | Добавить уровень в систему: имя уже есть (RW `0x830E17` → RW `0x830BA6`) → исключение со строкой RW `0xC53284` `A light point level %s already exists.` (RW `0x830E32` .. RW `0x830E4E`); иначе `push_back` (RW `0x830E59`). |

Без ссылок (ни вызова, ни данных): RW `0x830CD5` (обёртка поиска по имени) и RW `0x830A32` (`[финальное переопределение + 0x30]`). Не портируются.

## 4. `LightPointLevel` и блок INI

Размер `0x24` (RW `0x830F40` / RW `0x830F86` `push 0x24`), конструктор RW `0x830C27`, деструктор RW `0x830B0D`, vtable RW `0xC53248` с одним слотом RW `0x830B69` (удаляющий деструктор).

| Смещение | Что | Источник |
|---|---|---|
| `+4` | следующее переопределение | RW `0x830C31` |
| `+8` | флаг «это переопределение» (байт) | RW `0x830C34`, ставится на RW `0x830F7B` |
| `+0xC` | `-1` | RW `0x830C2D` |
| `+0x10` | имя из заголовка блока (AsciiString) | RW `0x830FA2` .. RW `0x830FA6` |
| `+0x14` | поле `Name`: переведённая метка (UnicodeString) | таблица RW `0xC532C0`, парсер RW `0x73B192` |
| `+0x18` .. `+0x20` | поле `SpecialAbilities`: вектор id спецсил | таблица RW `0xC532C0`, парсер RW `0x73B4FF` |

Парсеры полей:

- RW `0x73B192` (`Name`): токен (RW `0x73B1A5`), `TheGameText` `[0xDE4B04]->vtbl[+0x3C]` (RW `0x73B1BB`); пустой результат → исключение RW `0xC25128` `Label '%s' not found in game text` (RW `0x73B1D1` .. RW `0x73B1ED`); иначе присваивание строки (RW `0x73B1F9`). Тот же парсер у `Science/DisplayName` и `PlayerTemplate/DisplayName`; в порте метка хранится как написана (S-520, S-145).
- RW `0x73B4FF` (`SpecialAbilities`): цикл по токенам до конца строки (RW `0x73B53E` .. RW `0x73B545`); имя ищется в `TheSpecialPowerStore` `[0xDE878C]` (RW `0x73B517` → RW `0x69C146`); не найдено (RW `0x73B51E`) → токен молча пропускается; найдено → id `[финальное переопределение + 0x14]` (RW `0x73B522` .. RW `0x73B527`) добавляется в вектор (RW `0x73B534`).

Парсер блока RW `0x830EB5` (указатель в таблице блоков — данные RW `0xDADAEC`):

1. RW `0x830EC2` .. RW `0x830EC9`: система null → выход, блок не читается.
2. RW `0x830ED4` .. RW `0x830EE1`: имя = следующий токен.
3. RW `0x830EEA` `cmp [ini+8], 2` — тип загрузки 2 (переопределения из `map.ini`):
   - RW `0x830EF4` .. RW `0x830F02`: уровень ищется по имени; не найден (RW `0x830F0B`) → исключение RW `0xC532F0` `Light point level %s not found in map.ini` (RW `0x830F1F` .. RW `0x830F3B`).
   - RW `0x830F40` .. RW `0x830F4E`: новый уровень; RW `0x830F59` .. RW `0x830F65`: от найденного берётся финальное переопределение; RW `0x830F6A` `call 0x830CE5` — копия полей (имя, метка, вектор); RW `0x830F77` `[старый+4] = новый`; RW `0x830F7B` `[новый+8] = 1`; RW `0x830F7F` `initFromINI` (RW `0x42DB80`) с таблицей RW `0xC532C0`.
4. Иначе (RW `0x830F86`): новый уровень, имя в `+0x10` (RW `0x830FA6`), `initFromINI` (RW `0x830FB3`), затем RW `0x830FBF` `call 0x830E06` (повтор имени → исключение).

Следствие для переопределения: `SpecialAbilities` в `map.ini` **дописывает** id к скопированному вектору (парсер только добавляет). При этом RW `0x830A3B` читает вектор исходного уровня из системы, а не его переопределения, поэтому переопределённый список спецсил в проверке и трате не участвует; переопределение влияет только на имя, по которому RW `0x830E63` / RW `0x830BD5` ищут уровень (а имя копируется без изменений).

## 5. Скрипты

Номера взяты из таблиц переходов, а не из порядка имён.

Действия: диспетчер RW `0x7CAFA5`, RW `0x7CAFD5` `jmp [eax*4 + 0x7CF857]`. Проверка таблицы на известном случае: слот RW `0x7CFCB3` → RW `0x7CE020` даёт номер 279 (`PLAYER_SET_RANKLEVELLIMIT`, уже в порте).

| № | Имя (строка) | Слот таблицы → метка | Тело | Параметры |
|---|---|---|---|---|
| 351 | `PLAYER_GIVE_LIGHT_POINTS` (RW `0xC3FE44`) | RW `0x7CFDD3` → RW `0x7CE5B7` | RW `0x7BD2D0` | 0: игрок (строка `+0x10`), 1: число (`+8`) |
| 352 | `PLAYER_RESET_LIGHT_POINTS` (RW `0xC3FDF4`) | RW `0x7CFDD7` → RW `0x7CE5DB` | RW `0x7BD311` | 0: игрок |
| 353 | `PLAYER_GIVE_LIGHT_POINT_LEVEL` (RW `0xC3FD9C`) | RW `0x7CFDDB` → RW `0x7CE5F3` | RW `0x7BD34F` | 0: игрок, 1: имя уровня (строка) |
| 354 | `PLAYER_REMOVE_LIGHT_POINT_LEVEL` (RW `0xC3FD40`) | RW `0x7CFDDF` → RW `0x7CE618` | RW `0x7BD390` | 0: игрок, 1: имя уровня |
| 405 | `SET_PLAYER_LIGHT_POINTS_TO_COUNTER` | RW `0x7CFEAB` → RW `0x7CEC62` | RW `0x7C36BD` | 0: игрок, 1: счётчик |

Общая форма четырёх тел 351–354: маска игроков из параметра (`TheScriptEngine` `[0xDE3BAC]`, RW `0x758F7C(имя, 0)`); маска 0 → выход; цикл RW `0x6A85EE` по `ThePlayerList` `[0xDE4928]` (следующий игрок маски, бит снимается) до пустой маски; для каждого игрока вызов:

- 351: RW `0x7BD302` `call 0x6AB148(число)`;
- 352: RW `0x7BD340` `call 0x6AA931`;
- 353: RW `0x7BD381` `call 0x6AA939(имя)`;
- 354: RW `0x7BD3C2` `call 0x6AA957(имя)`.

Та же пара RW `0x758F7C` + RW `0x6A85EE` стоит в `PLAYER_SCIENCE_AVAILABILITY` (RW `0x7BD274`, RW `0x7BD28C`), которое в порте уже есть (`ScriptConditions::players`).

405, RW `0x7C36BD(параметр игрока, параметр счётчика)`: маска (RW `0x7C36D2`), цикл по игрокам с суммой `0x6AA8F4` (RW `0x7C36F3`, RW `0x7C36F8` `add esi, eax`); затем счётчик по имени (RW `0x7C370D` .. RW `0x7C3718` → RW `0x60817A`) и RW `0x7C371D` `mov [eax], esi`. Пустая маска → в счётчик пишется 0.

Условие: диспетчер с RW `0x7EB7D4` (`edx = тип - 5`), RW `0x7EB7EC` `jmp [edx*4 + 0x7ED414]`. Слот RW `0x7ED5F0` → RW `0x7ECD4B`: индекс 119, тип 124 — `PLAYER_COMPARE_LIGHT_POINTS`. Тело RW `0x7E5B56(игрок, сравнение, число)`:

- RW `0x7E5B65` маска игроков (RW `0x75968D`), сумма очков по игрокам (RW `0x7E5B86`, RW `0x7E5B8B`);
- вид сравнения `[параметр 1 + 8]`: 0 `<` (RW `0x7E5BE6` `setl`), 1 `<=` (RW `0x7E5BDB`), 2 `==` (RW `0x7E5BD0`), 3 `>=` (RW `0x7E5BC5`), 4 `>` (RW `0x7E5BBA`), 5 `!=` (RW `0x7E5BAF`); другое значение → ложь (RW `0x7E5B99` `xor al, al`). Слева сумма очков, справа `[параметр 2 + 8]`.

`engine/tests/data/script-census.json` (скрипты карт 2.01) не содержит ни одного из шести имён: карты оригинала их не зовут, это входы для скриптов карт мода.

## 6. Спецсилы: проверка и трата

Проверка — `SpecialPowerStore::canUseSpecialPower` (в порте RW `0x7B1D79`), после наук и перед запрещающими статусами:

- RW `0x7B1DFD` .. RW `0x7B1E07`: владелец объекта (RW `0x68B678`), `call 0x6AA8FB(шаблон)`; ложь (RW `0x7B1E0E`) → функция возвращает ложь.
- RW `0x7B1E10` .. RW `0x7B1E1A`: дальше `PreventActivationConditions` (RW `0x75CDC4`).

Трата в `SpecialAbilityUpdate` (функция RW `0x853EDF`, запуск способности), после очков опыта:

- RW `0x853FA5` `cmp [0xDE8C04], 0`, RW `0x853FAC` `je` — система null → без траты;
- RW `0x853FAE` .. RW `0x853FBB`: владелец объекта null → без траты;
- RW `0x853FBD` .. RW `0x853FCB`: `call 0x6AA91D([финальное переопределение шаблона + 0x30])`.

Трата в `SpecialPowerModule` (функция RW `0x897987`, срабатывание силы), после цикла `OnTriggerRechargeSpecialPower`:

- RW `0x897A41` .. RW `0x897A4E`: владелец объекта null → без траты;
- RW `0x897A50` .. RW `0x897A5E`: `call 0x6AA91D([финальное переопределение шаблона + 0x30])`. Проверки системы здесь **нет**.

Обе траты не смотрят, названа ли сила в каком-либо уровне: вычитается `LightPointCost` любого шаблона (0 по умолчанию, конструктор шаблона).

## 7. Что получается в игре

- Сила, не названная ни в одном уровне, проходит проверку всегда (RW `0x830AF0`).
- Сила, названная в уровне, проходит, если очков не меньше её `LightPointCost`. При стоимости 0 проходит всегда (очки не бывают отрицательными: RW `0x8309EC`, RW `0x6AA92B`).
- Уровни в трекере (действия 353, 354) в RotWK 2.01 читает только xfer: ни проверка, ни трата, ни звук от них не зависят. Читателей списка уровней трекера, кроме RW `0x8309F3` (вызов только из RW `0x830D25`) и xfer, в прочитанном коде нет. INFERENCE: список нужен интерфейсу «Войны Кольца» вне боя; это не проверено и здесь не портируется.

## 8. Xfer

Слоты Xfer подтверждены по пяти vtable (найдены поиском dword RW `0xA1F5B9`, `operator==(Version&)`, слот `+0x28`):

| vtable | `+4` | `+8` | `+0xC` | `+0x10` | Что это |
|---|---|---|---|---|---|
| RW `0xBD1940` | 0 | 0 | 0 | 0 | базовый Xfer |
| RW `0xC939E8` | 1 | 0 | 0 | 0 | XferLoad |
| RW `0xC93AE0` | 0 | 1 | 0 | 0 | XferSave |
| RW `0xBFD2A0`, RW `0xC7F5F8` | 0 | 1 | 1 | `[this+0x40]` | XferCRC (лёгкий, если флаг `+0x40`) |

Значит `+4` — загрузка, `+8` — запись (сохранение и CRC), `+0xC` — CRC, `+0x10` — лёгкий CRC. `+0x7C` — `int`, `+0x90` — `bool`, `+0x30` — `Snapshot&`, `+0x28` — версия. Имена — DONOR BFME2 (`Include/Common/BfmeXfer.h`: IsLoading, IsStoring, IsCRC, IsLightCRC); значения прочитаны в RW (`mov al, 1; ret` RW `0x8BD372`, `xor al, al; ret` RW `0x9188EB`, `mov al, [ecx+0x40]; ret` RW `0x931EBF`).

`Player::xfer` (функция RW `0x6B23FB`): RW `0x6B2B2D` `call [eax+0x10]`; лёгкий CRC (RW `0x6B2B32` `jne 0x6B2C56`) пропускает всё дальнейшее. Иначе RW `0x6B2B43` `bool` `+0x35D`, RW `0x6B2B4B` .. RW `0x6B2B54` трекер `+0x338` через слот `+0x30`, RW `0x6B2B62` `float` `+0x334`.

Xfer трекера RW `0x830D3F`:

1. RW `0x830D4D` версия (1, 1) (RW `0x404F15`).
2. RW `0x830D55` .. RW `0x830D5F`: `count` = размер списка.
3. RW `0x830D64` лёгкий CRC → RW `0x830D73` очки (`+4`), RW `0x830D7E` `count`. Из `Player::xfer` эта ветка недостижима (пункт выше).
4. Иначе RW `0x830D83` запись → RW `0x830D92` `count`, затем каждый индекс (RW `0x830DA1` .. RW `0x830DB9`). **Очки не передаются.**
5. Иначе (загрузка) → RW `0x830DBD` `count`, затем `count` раз: `int` во временную и `push_back` (RW `0x830DC7` .. RW `0x830DE1`). Список перед этим не чистится (его опустошил RW `0x6B0355`). **Очки не читаются.**

Итого: сохранение RotWK держит список уровней и не держит очки; после загрузки очки те, что оставила инициализация игрока (0, RW `0x6B0362`).

## 10. Порт до изменения

- `PlayerTemplate::m_lightPointsUpSound` разбирается и хранится, читателя нет (S-7231).
- `SpecialPowerTemplate::m_lightPointCost` (`+0x30`) разбирается; на месте траты `++m_unported` (`SpecialPowerModules.cpp`), в `SpecialAbilityModules.cpp` только комментарий.

## 11. Что портируется

5. Проверка в `canUseSpecialPower` и обе траты, с их разными условиями (раздел 6).
6. Сохранение трекера в `Player::xfer` и вклад в хеш.

## 12. INFERENCE, отличия и что не портируется

- **Очки в сохранении.** RotWK очки не сохраняет (раздел 8). Снимок порта — собственный формат (S-4190), и по `docs/SAVES.md` раздел 6 загруженная игра обязана совпасть с сохранённой кадр в кадр (тест T1; на том же снимке держатся возобновление и быстрое подключение в сети, где расхождение — рассинхрон). Поэтому порт сохраняет и очки, и уровни. Это сознательное отличие от RW; решение за владельцем.
- **`Name` уровня.** RW переводит метку через GameText и бросает исключение для неизвестной (RW `0x73B192`). В порте метка хранится как написана, как у остальных полей с этим парсером (S-520). Читатели `уровень + 0x14` не искались: это текст для интерфейса.
- **Читатели списка уровней трекера** вне прочитанного кода не найдены и не опровергнуты (раздел 7). Интерфейс «Войны Кольца» (S-531) в эту задачу не входит.
- **Формат сохранений RotWK** (версия (1, 1), порядок полей) не воспроизводится: S-4190.
- Недостижимый код RW `0x6B2EC4`, RW `0x830CD5`, RW `0x830A32` не портируется.
