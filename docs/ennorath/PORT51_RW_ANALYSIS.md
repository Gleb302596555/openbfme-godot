# Port 51: Object/InstanceScaleFuzziness — анализ RotWK 2.01

Рабочая запись по issue #155. Адреса прочитаны через `tools/mod/rw.py dis|xref` из RotWK 2.01 (`game.dat`, MD5 `daed3668006cd90f01c34e5a7da1901f`, оговорка S-001). Проверялись только инструкции; значения и выдержки INI мода здесь не приводятся.

## 1. Поле, его таблица и место в ThingTemplate

- Строка таблицы RW `0xDA4678`: имя `0xC25654` (`InstanceScaleFuzziness`), парсер RW `0x42ED00`, userData 0, смещение `+0x4F4`.
- Соседние строки той же таблицы (объектная таблица RW `0xDA3DB8` .. `0xDA49E8`): `Scale` RW `0xDA43C8` → `+0x4F0`, `ShadowSizeX` RW `0xDA44F8` → `+0x4F8`, `ShadowSizeY` RW `0xDA4508` → `+0x4FC`; у всех парсер RW `0x42ED00`.
- Парсер RW `0x42ED00` — `parseReal`: `mov ecx,[esp+4]` (INI) → RW `0x42DC9F` (чтение токена) → `push 0` и RW `0x42EAAD` (`scanReal`, результат в `st0`) → `mov eax,[esp+0xc]; fstp dword ptr [eax]`. Значение только записывается по адресу `store + offset`; никакой проверки диапазона и никакого побочного действия у парсера нет.
- Конструктор ThingTemplate (пролог RW `0x73ED19`, `sub esp,0x368`) ставит значения по умолчанию: `Scale +0x4F0 = 1.0` (RW `0x74008C`, `xmm1` из константы RW `0xBD1908` = 1.0), `InstanceScaleFuzziness +0x4F4 = 0.0` (RW `0x740190`, `xmm0` = 0.0), `ShadowSizeX/Y +0x4F8/+0x4FC = 0.0` (RW `0x740108` / RW `0x740110`).
- Копирование шаблона (функция с прологом RW `0x6D1D80`) переносит оба поля поштучно: RW `0x6D21CF` `mov ecx,[eax+0x4F0]` → RW `0x6D21D5` `mov [ebx+0x4F0],ecx`, затем RW `0x6D21DB` → RW `0x6D21E1` для `+0x4F4`.

## 2. Полный перебор обращений к `+0x4F4` в коде игры

Метод: в `.text` (RW `0x401000` .. `0xBD0000`) найдены все вхождения четырёх байт `F4 04 00 00` — 21 штука; для каждого вхождения обратным декодированием (все стартовые смещения в пределах 15 байт) найдена инструкция, накрывающая эти байты. Обращение к члену `+0x4F4` возможно только через disp32 либо через `lea`/`add` с непосредственным `0x4F4` — обе формы дают эти же четыре байта, поэтому список полный: 10 настоящих обращений и 11 совпадений байт (7 × `mov dword ptr [ebp-0xC],4` = `C7 45 F4 04 00 00 00` и 4 × `je rel32`, у которых цель ветвления содержит `F4 04 00 00`).

| адрес RW | инструкция | что это |
|---|---|---|
| `0x740190` | `movss dword ptr [ebx+0x4F4], xmm0` | конструктор ThingTemplate, значение по умолчанию 0.0 |
| `0x6D21DB`, `0x6D21E1` | `mov ecx,[eax+0x4F4]` / `mov [ebx+0x4F4],ecx` | копирование ThingTemplate |
| `0x46E2FC`, `0x46E323` | `movss xmm1,[esi+0x4F4]` / `movss [esi+0x4F4],xmm1` | функция тумана/освещения (вызывающий RW `0x471A27`; в порте VISUAL-2, `GameClient/Visual2Stops.h`, `w3dshadergen.cpp`): три вектора `+0x2C8`, `+0x4F0`, `+0x718` умножаются на долю тумана из GlobalData (`[0xDE4364]+0xBE8 / +0xBE9`, вектор `+0x944`); `+0x4F4` там — Y-компонента второго вектора, а не поле ThingTemplate |
| `0x699935` | `mov dword ptr [esi+0x4F4], 0xBDB8F0` | конструктор другого класса (перед этим RW `0x699930` `push 0xC123F8` — его таблица); `+0x4F4` — указатель на статический объект |
| `0x892A4A` | `mov [ecx+0x4F4], ebx` | другой класс: указатель в структуре |
| `0x892BC1` | `lea eax,[edi+0x4F4]` | другой класс: адрес передаётся в RW `0x707887` вместе с `[edi+0x4F8]` |
| `0x892DD3` | `push [esi+0x4F4]` | тот же другой класс |
| `0x893203` | `cmp byte ptr [esi+0x4F4], 0` | другой класс: байтовые флаги `+0x4F4` / `+0x4F5` |

Вывод: единственное чтение float по `+0x4F4` — RW `0x46E2FC` в функции тумана, где это компонента вектора другой структуры. **Ни один код RotWK 2.01 не читает поле `InstanceScaleFuzziness`.**

Дополнительно: строка `InstanceScaleFuzziness` есть в PE ровно одна (RW `0xC25654`) и на неё ссылается ровно одна строка таблицы (RW `0xDA4678`), поэтому второй таблицы или второго смещения у поля нет. Геттера для `+0x4F4` в игре нет вовсе (у соседнего `Scale` он есть — RW `0x625289` `fld [ecx+0x4F0]; ret`, без единого вызывающего).

## 3. Где масштаб экземпляра берётся на самом деле

- RW `0x679FD7` в конструкторе Drawable: `mov edi,[ebp+8]` (шаблон, дальше RW `0x67A021` берёт его список draw-модулей по `+0x2F0`) → `movss xmm0,[edi+0x4F0]` → RW `0x679FE2` `movss [esi+0x200],xmm0`. Масштаб экземпляра = шаблонный `Scale`; `+0x4F4` рядом не читается, вызовов случайного числа между этими инструкциями нет.
- Прочие чтения `+0x4F0` — тот же шаблонный `Scale`, без фуззи: RW `0x5F115A`, `0x5F185C`, `0x62C9CF`, `0x8C7CDD` берут `[esi+0x4F0]` и передают его аргументом в создание записи дерева/куста у TheTerrainLogic (RW `0xDE4690`, вызов RW `0x683D89`; порт: `GameLogic/Map/TerrainTrees.cpp`, `MapClient/MapObjectDrawables.h` «TREE → RW 0x683D89»), RW `0x62E36F` умножает `Scale` на уже вычисленный коэффициент перед таким же вызовом, RW `0x625289` — геттер `fld [ecx+0x4F0]; ret` без вызывающих. То есть даже путь деревьев — то место, где фуззи была бы заметнее всего, — читает только `Scale`.
- Вариативность экземпляров в RotWK есть, но не по масштабу: Drawable `+0x364` (RW `0x679FEA`, порт `Drawable::m_variation`) идёт в RandomTexture RW `0x4C238A`, выбор текстуры (порт `W3DScriptedModelDraw.cpp`, RW `0x4C46C4`).

## 4. Данные мода (для владельца, без выдержек INI)

Аудит 2026-11-08 (`field-audit-v4`, `manual-check`) и `ennorath-ini-1.9.8.2`: поле задано у 89 объектов, значения 0.1 / 0.3 / 0.4 — деревья, кусты и декор (`data/ini/object/nature/natureprop.ini`, `data/ini/object/civilian/civilianprop.ini`, `data/ini/object/modcinematic/cinematicobjects.ini`). В нескольких файлах строки закомментированы (`;`). У части строк `natureprop.ini` стоит комментарий EA «will instance with scale from 70% to 130%».

Этот комментарий поведением не считается: он остался от редакции, где поле работало (BFME1, `engine/src/Common/Thing/Bfme1ObjectFields.inc:79`), а в RW 2.01 читателя нет (раздел 2). INFERENCE: в RotWK 2.01 размер пропа задаётся только `Scale`, а разными пропы в лесу выглядят из-за RandomTexture и расстановки, а не из-за масштаба.

## 5. Что делает порт сейчас

- `engine/data/rotwk-201/field-tables.json` содержит строку `InstanceScaleFuzziness` со смещением 1268 (`0x4F4`); порт разбирает её в слот поля шаблона (`ThingTemplate::findField`) — в аудите состояние `parsed-unused`.
- `Object::m_instanceScale` (`GameLogic/Object/Object.cpp`, RW `0x679FD7`) и `Drawable::m_scale` (`GameClient/Drawable.cpp`) стартуют как `Scale` шаблона; поле нигде не читается.
- Значит порт **уже** ведёт себя как RotWK 2.01: случайного масштаба у поставленных объектов нет. Второй путь не добавлялся, код не менялся.

## 6. Вердикт и тесты

Код не меняется, новое состояние симуляции не появляется (PROCESS 15.5 неприменим: сохранять нечего), строка в `docs/STOPS.md` фиксирует вердикт.

`engine/tests/test_port_51.cpp` держит это поведение:

- `PORT-51` №1: шаблон хранит разобранное значение (`+0x4F4`, значения 0.1/0.3/0.4), а масштаб экземпляра равен ровно `Scale`: восемь объектов одного шаблона имеют одинаковый масштаб бит в бит, при отсутствии `Scale` — 1.0 (значение по умолчанию из RW `0x74008C`), в том числе при `InstanceScaleFuzziness = 0` и при `0.4`.
- `PORT-51` №2 (соседнее поведение): `Scale` сам по себе по-прежнему задаёт масштаб, `ChildObject` наследует обе строки (копирование RW `0x6D21DB`), а переопределение фуззи у ребёнка масштаб не меняет.

Тест падает, если кто-то перенесёт поведение BFME1 (случайный масштаб): восемь экземпляров перестанут совпадать.
