# PORT-238: ArnorArveduiNew ring forms (partial trace)

## Entry and two alternatives

`object/goodfaction/units/arnor/new/arnorarveduinew.ini:1` defines `ArnorArveduiNew`; `:1534–1548` defines its `CitadelSlaughterHordeContain`, ring carrier status, `TheDroppedRing` destruction and the two OBJECT upgrades `Upgrade_RingHero` and `Upgrade_FortressRingHero`. The ordinary carrier auto-attachment macro explicitly excludes the named base and both forms (`_gamedata.inc:31`); that does **not** rule out delivery by another carrier, or prove effective filters after loading.

Source `:1460–1487` unpauses `SpecialAbilityToggleSauronGestaltenSauron` on `Upgrade_RingHero`; its automatic `DoCommandUpgrade` is blocked by `Upgrade_NoMoreMalberth`, and its `ToggleMountedSpecialAbilityUpdate` names `ArnorArveduiEvilRing`. Source `:1489–1517` unpauses and issues the separate `SpecialAbilityToggleSarumanRing` when **both** `Upgrade_RingHero` and `Upgrade_NoMoreMalberth` are present and names `ArnorArveduiGoodRing`. Both replacements have 2000 ms unpack and seven timer names. Both button declarations are `InPalantir = No` (`includes/commandbutton.inc:20433–20458`).

The protection flag is an OBJECT upgrade (`upgrade.ini:46–54`). The PLAYER upgrade `Upgrade_TheArveduiRing` (`includes/upgrade.inc:2558–2561`) triggers `ObjectCreationUpgrade` to grant that object flag, and also triggers a second good-form `DoCommandUpgrade` (`arnorarveduinew.ini:1519–1530`). The evil form declares a corresponding later good transition (`:2820–2861`). **Order matters**: the concurrent player upgrade, asynchronous grant, already-started replacement, upgrade transfer, seven timers and later evil-to-good route are not tested here. Generic RW upgrade-mux conditions (`0x8D26F3`), automatic command (`0x8B8E2E`) and replacement (`0x8B1690 -> 0x8B140D`) are traced in `PORT238_RW_ANALYSIS.md` / `PORT238_BOROMIR_TRACE.md`. For `ObjectCreationUpgrade`, upstream PORT-294 (`engine/tests/test_port_294.cpp`) covers its mux and delayed grant in general, not this route. S-7321, S-7446 and S-861 remain.

Synthetic `PORT-238 Arvedui-style ring delivery*` checks two independent cases: unprotected and the object protection upgrade given **before** delivery. Ring delivery grants both named synthetic upgrades; the expected evil or good synthetic template appears with the same owner and the original goes away. It passes 56/56 assertions on matching isolated `3f0105c8` core/headers with only the upstream PORT-286 parser change separately compiled in. Replacing the fixture's evil `ConflictsWith` protection with an unrelated upgrade causes the protected subcase to fail (52/53); this is fixture sensitivity, not a code-fix control. It does not emulate the player upgrade or later conversion, all seven timer transfers, actual data, selection or rendering.

## Death and appearance

The separate evil object declares unconditional `CreateObjectDie` with `OCL_TheOneRing` (`:2567–2569`) and respawn as the base (`:2416–2432`). In the literal separate good object (`:2963–4292`), no direct `CreateObjectDie`/`OCL_TheOneRing` line was found; its `SlowDeathBehavior` (`:3957–3964`) has no OCL and its `RespawnUpdate` names the base. This is a **source observation only**, not a finding that the ring is lost: preprocess/includes, overrides, generic death and actual game behavior remain unresolved. Do not add a guessed drop.

Evil default model `arnarveduie` has `SaronRingSpark`, `Predator` / `Predator02` and a stealth model `arvedring` (`:1850–1880`); good default `arnarveduig` has mounted and HERO_MODE model/particle states (`:2976–3008`).
