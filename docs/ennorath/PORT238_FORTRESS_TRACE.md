# PORT-238: fortress ring drop (partial trace)

Literal references are to extracted Ennorath 1.9.8.3 (INI archive MD5 `c53b6dea885cab044f80e783565f41f3`), relative to `data/ini`. Later versions and effective loading have not been independently checked. The lexical list of nine active-looking `FortressRingFunc.inc` includes is in `PORT238_CANDIDATES.md`; it is not proof of each effective fortress module, inherited overrides, ownership path or availability.

`object/fortressringfunc.inc` declares an `FXListDie` before `CreateObjectDie`; the latter creates `OCL_TheOneRing` only with `UpgradeRequired = Upgrade_RingHero Upgrade_FortressRingHero`. Its `ModelConditionUpgrade` requires both triggers for `ONE_RING`; draw states use `EXOneRing` or `EXOneRing_CR` for `ONE_RING BUILD_VARIATION_TWO`. The inline comment says player and object versions, but in the extracted `upgrade.ini:181–184,198–200` **both** are declared OBJECT; do not infer the effective PLAYER mask from the comment. FX order, actual draws, sounds and a complete death are not checked here. `OCL_TheOneRing` names `TheDroppedRing` (`objectcreationlist.ini:9566–9573`); the subsequent attach/drop lifecycle has its own limits in `PORT238_FRODO_TRACE.md`.

DONOR BFME2 `CreateObjectDie.cpp` supplies the class lead. RW `0x888F04` invokes DieMux at `0x85FED5`, iterates the requirement vector at `0x888F22–0x888F61`, resolves each name `0x66F5E5`, and checks player `0x6AC2AF` or object `0x691421` according to the upgrade type; a missing known requirement exits before OCL creation. Unknown names are skipped in that RW loop. The port's `CreateObjectDie::onDie` in `GameLogic/Module/ExtraDieModules.cpp` implements that shared gate; PORT-237 separately forwarded primary and secondary OCL objects. This is not an all-type or unknown-name audit.

`PORT-238 fortress-style death drop requires both object upgrades` uses synthetic fortress, OCL, two OBJECT upgrades and four cases (neither, each alone, both): it checks the model bit and on NORMAL kill that exactly one synthetic ring appears only with both. It passes **64/64**; isolated `PORT-238*` **35/35 cases, 2184/2184 assertions** on matched `3f0105c8` core/headers plus separately compiled upstream PORT-286 parser, not current-main full binary. Deleting the second `UpgradeRequired` name in the fixture makes the hero-only case fail (**63/64**). This is fixture sensitivity, not an engine-fix control. It does not test the FX-before-drop order, player upgrades, textually included real object, admission or in-game appearance. Shared S-7321, S-7446, S-1041 and S-1361, among others, remain.

## Erebor throne declarations and bounded admission

Two separate objects in `object/civilian/ereborbuildings.ini` declare ring entry: `EreborThrone` (`:5470,5594–5612`) and `WOR_EreborThrone` (`:5638,6081–6099`). Both specify `PassengerFilter = GENERIC_FACTION_SLAUGHTERABLE`, own-player override, no enemy/allied/neutral admission, capacity 99, ring status, both ring upgrades and the dropped-ring destroy filter. `_gamedata.inc:35` defines the filter's KindOf portion as `ANY +INFANTRY +CAVALRY -HERO -DOZER -SUMMONED`, followed by a long list of excluded object names. `EreborThrone` directly declares `KeepObjectDie` but no literal `FortressRingFunc.inc` include or `CreateObjectDie` within its own object block; `WOR_EreborThrone` directly includes `FortressRingFunc.inc` (`:6101`). This is a source distinction, not proof of an effective missing drop: preprocessing, other death paths, map instantiation and actual game routes are not resolved. Its many faction/clan `CommandSetUpgrade`s and object-creation upgrades also remain unaudited.

`PORT-238 Erebor throne-style passenger filter*` reproduces only the KindOf portion of that macro, not its excluded template names. At the contain interface with path checking explicitly **off**, a same-player ordinary infantry object satisfies inherited passenger admission; same-player HERO and SUMMONED infantry do not without ring status but do with it, while an enemy HERO with that status is refused. This is a hypothetical synthetic status assignment, not proof that the real SUMMONED object can acquire the ring. RW `0x88397F` calls the inherited test `0x8838C3` first, then the same-player/ring-status branch; the shared logic is in `GarrisonContain.cpp`. Test: **30/30**, isolated `PORT-238*` **44/44 cases, 2961/2961 assertions** on matching `3f0105c8` core/headers plus the separately compiled upstream PORT-286 parser. Removing `-HERO` only from the synthetic filter yields **28/30**, a fixture sensitivity control, not an engine-fix control. Actual HUD capacity/path selection S-7321, named exclusions, slaughter/cashback, attached ring, delivery, death/respawn, ownership and appearance have not been tested for these two objects.
