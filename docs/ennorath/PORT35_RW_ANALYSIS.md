# Port 35: HordeContain/ComboHorde — анализ RotWK 2.01

Рабочая запись по issue #120. Адреса ниже прочитаны через `tools/mod/rw.py dis` / `lin` из RotWK 2.01 (`game.dat`, MD5 `daed3668006cd90f01c34e5a7da1901f`); где вывод сделан по коду BFME2 или только по имени, это помечено `INFERENCE`. Исследование сопровождает перенос механизма слияния двух орд в одну.

## Данные и разбор

- Строка таблицы полей HordeContain RW `0xC5BBA0`; парсер RW `0x872654`; запись — 0x10 байт (`Target` +0, `Result` +8); ключи `Target` RW `0xBE56BC`, `Result` RW `0xC5B1EC`, `InitiateVoice` RW `0xC55778` → RW `0x73AB45`; неизвестный ключ — RW `0xA3CE04` (исключение 3), см. RW `0xC5B1DC` / `0xC5B1B8`.
  Порт разбирает тот же список (`HordeContain.cpp:308` `parseComboHorde`, `HordeContain.h:69` `ComboHordeEntry`, `HordeContain.h:123` — данные модуля + 0x198) и хранит `InitiateVoice` с EVA.
- Вектор списка лежит в данных модуля по + 0x198: RW `0x87044B` читает `[ecx + 4]` (данные модуля), затем + 0x198.

## Поиск записи: RW 0x87043B

- RW `0x87043B` — отдельный помощник: `[ecx + 4]` → данные модуля, RW `0x87044B` → вектор (начало/конец), обход записей RW `0x870451 .. 0x870469`, сравнение имени через RW `0x4065AA` (std::string `compare`), поля записи `+0` (`Target`) и `+8` (`Result`). Возврат: указатель на запись или 0.
- Вызывающие: RW `0x871EC1` (ветка «можно слиться» слота 0x70), RW `0x871F67` (вторая ветка того же слота) и RW `0x8765CC` (ветка слияния слота 0x74). Других вызовов в `.text` нет (xref пуст: вызовы только прямые).

## Слот 0x70 (RW 0x871D41): можно ли принять объект

Порядок проверок пролога (любой отказ → RW `0x871F16` → 0):

- RW `0x871D41`: нулевой объект и бит 1 байта `[obj + 0x458]`;
- RW `0x44DDEC(obj, 0x3b)` и `(obj, 0x3e)` — тест бита статуса: `0x3b` = 59 `DEPLOYED`, `0x3e` = 62 `TEMPORARILY_DEFECTED` (имена по таблице RW `0xD8AFF0`, файл `engine/tests/data/horde1/list_object_status_names.tsv`);
- RW `0x44DDEC([esi - 0x114], 0x3e)` — второй объект не `TEMPORARILY_DEFECTED`;
- RW `0x9325B4(module + 0x1c8)`, RW `0x46E918(obj, 0xda)`, RW `0x693A1A(obj, 0)`, RW `0x68B678` на обоих объектах (`[[ecx + 0x31C]]` → RW `0x79FD6F`, объекты должны совпасть);
- RW `0x871E4C`: `jle` по `[[obj + 0x26C] + 0x24]` — не больше одного члена → отказ.

Ветка «можно слиться» RW `0x871E89 .. 0x871F12`:

- RW `0x871E89` / RW `0x871E92`: нулевой объект и собственная орда отклоняются;
- RW `0x871E9A .. 0x871EBB`: имя шаблона `[obj + 4] + 0x64` складывается в std::string (RW `0x436030` / `0x435f30`) — ключ поиска;
- RW `0x871EBB` / RW `0x871EC1`: `0x87043B` на своей орде; нет записи (RW `0x871EC6` / `0x871ECA`) → false;
- RW `0x871ECE .. 0x871F02`: RW `0x44DDEC` с 2 и 3 на обоих объектах (2 = `UNDER_CONSTRUCTION`, 3 = `UNSELECTABLE`), любой установленный бит → false;
- RW `0x871F04` / RW `0x871F12`: результат (байт `bl`) возвращается как ответ слота.

`INFERENCE`: в слоте 0x70 непонятно, какой из двух объектов попадает в `[ebp - 0x10]`, а какой — в `edi`/`esi`; направление поиска принято таким же, как в слоте 0x74 (RW `0x8765CC` читает `[ebx + 4] + 0x64`, шаблон второго объекта, в списке **своей** орды). Для слияния нужны оба ответа, поэтому порт держит одно направление в `canCombineWith` и `combineWith`.

Пять проверок пролога (RW `0x9325B4` с `+0x1c8`, RW `0x46E918(0xda)`, RW `0x693A1A(0)`, RW `0x68B678`, ветка счёта членов RW `0x871E4C`) в порт не перенесены: вызываемые ими функции не опознаны (S-6027).

## Слот 0x74 (RW 0x876481): слияние

Сигнатура: `(this = интерфейс модуля + 0x11C, Object *target, int source, int flag)`, `ret 0x10`.

- RW `0x876481 .. 0x8764A9`: нулевая цель → 0; RW `0x86C4EA`-класса постройка таблицы слотов (порт: `onObjectCreated`); исходник команды сохраняется.
- RW `0x8764AA`: цель — член контейнера, значит сливается её контейнер (`target->getContainedBy()`).
- RW `0x8764E4`: шаблон + 0x115, бит 0x20 = KindOf 109 `HORDE` (таблица RW `0xDA0E68`); не орда → далее ветки лидера/знамени.
- RW `0x876560`: байт данных модуля + 0x2B4 (охранный флаг рекурсивного вызова) и `sete al`; RW `0x876406` — отдельная передача знамени, не слияние.
- RW `0x87657F .. 0x87658B`: проверки машины (`+0x240`) и списка; дальше ветка слияния RW `0x8765B4`.
- RW `0x8765B4 .. 0x8765D1`: `[ebx + 4] + 0x64` (имя шаблона второй орды) → RW `0x87043B` в списке своей; нет записи → RW `0x8765D1` → 0.
- RW `0x876601`: `0x6D1305` (`Result` → ThingTemplate); null → 0.
- RW `0x6D165E`: создание объекта по шаблону `Result` с командой кастующей (порт: `logic.newObject(result, player->getDefaultTeam(), {})`, как в `splitHorde`).
- RW `0x70BA76` с `[ebx + 8]`: новая орда получает трансформ второй орды. `INFERENCE`: угол тоже копируется.
- RW `0x68C17D`: новая орда получает команду своей (`[esi - 0x114] + 0x47C`).
- RW `0x87680A .. 0x876840`: маска улучшений своей и второй орды (`0x444DB3`, копия `0x68CC6C` в `+0x28c`).
- RW `0x8769D0`: `0x44DDEC(this, 0x49)` (73 `HUNT_WHEN_IDLE`) → RW `0x62684D(made, 0x49, 1)`.
- RW `0x86C962` (слот 0x1E8) на орде-цели: снятие модификаторов формации с её членов до переезда.
- RW `0x87317A` (слот 0x44): обход членов — `lea ecx,[edi - 0xfc]`, `vt[0x118]` в стековый список, обход узлов (`[esi]` — следующий, `[esi + 8]` — полезная нагрузка) с вызовом RW `0x5EB775` на каждого, затем обход списка `[edi + 0x54]`.
- RW `0x876A08` (слот 30): принятие члена новой ордой — слот 0x2C = RW `0x873F30` (`acceptCreatedMember`), принудительный локомотор `+0x244`, затем проверка знамени RW `0x8719E4` и RW `0x876B10` (слот 0x1E4, модификаторы формации новой орды).
- RW `0x8768AE`: выжившая орда определяется по `[[obj + 0x26C] + 0x24]` (счёт членов).
- RW `0x62BBAB` в RW `0x8769A1` (орда-цель) и RW `0x8769B9` (своя): обе старые орды уничтожаются.
- RW `0x87566B` (слот 0x174) в RW `0x8769D4`: улучшения новой орды раздаются её членам.
- `ret 0xc` — RW `0x876A05`, затем RW `0x876A08` (хвост принятия членов).

`INFERENCE`: что члены **своей** орды тоже переезжают — это единственное прочтение теста выжившего RW `0x8768AE`, при котором не теряется ни один член (обе ветки RW `0x87317A` читают списки обеих орд).

## Спорные места

- Тай-брейк знамени RW `0x8768A0 .. 0x8768FC` не расшифрован: там вызывается слот 0x74 рекурсивно (охранный флаг RW `0x876560`, байт данных модуля + 0x2B4) и одна из двух знамён уничтожается. Порт: первое пришедшее знамя остаётся носильщиком новой орды, второе уничтожается (S-6028).
- Ветки машины/лидера RW `0x87657F` и RW `0x876406` (передача знамени, `0x876394` / `0x86BF96` / `0x79DA0A` / `0x79D7E5`) не перенесены.
- `InitiateVoice` записи (entry + 0x10, RW `0x73AB45`) не проигрывается: в порте нет ни вызова, ни пути звука слияния (S-6028).
- Модуль `CombineHordeSpecialPower`, который запускает слияние, в порт не перенесён: в Ennorath он на `HaradrimBanner`, `LothlorienBanner`, `LothlorienBanner2` (`SpecialPowerTemplate = SpecialAbilityCombineWithNearest`, `InitiateSound`, `ScanRange = 15000.0`). Его код лежит около RW `0x8CC000 .. 0x8CE000`; RW `0x8CD940` — это его `xfer` (слоты Xfer 0x70/0x84/0x90), поэтому попадания `call [reg + 0x70]` в RW `0x8CD967 .. 0x8CD9C5` — записи xfer, а не запросы орды. Вызывающие модульные узлы RW `0x87230F` / RW `0x872368` (код модуля, решающий сливать) не расшифрованы.

## Что в порте

- `HordeContain::comboHordeEntryFor` (RW `0x87043B`), `HordeContain::canCombineWith` (слот 0x70, RW `0x871D41`), `HordeContain::combineWith` (слот 0x74, RW `0x8765B4 .. 0x8769F7`) и `HordeContain::takeMembersFrom` (переезд членов, RW `0x87317A` → RW `0x876A08` / RW `0x873F30`, по образцу смены формации HORDE-2).
- Нового состояния симуляции нет: слитая орда — обычный объект мира, поэтому `xfer` и `crc` не меняются.
- Тесты `PORT-35*` (`engine/tests/test_port_35.cpp`): слияние по записи, отказ без записи, проверки входа, цель-член / отсутствующий `Result` / выбор записи по цели.
