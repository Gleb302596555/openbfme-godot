# PORT-67 (issue #181): Weapon/`CanSwoop` и строки Swoop локомотора

Разбор по RotWK 2.01 (`game.dat`, MD5 `daed3668006cd90f01c34e5a7da1901f`, оговорка S-001) и сверка с донором
BFME2 1.06 (`/tmp/open-bfme-2`, `Code/…`). Итог: **в RotWK у этих полей нет читателя** — они разбираются и
копируются, но ни один путь симуляции их не читает. Переносить в порт нечего; порт уже разбирает все пять полей с
теми же смещениями, парсерами и теми же значениями по умолчанию, что и RW.

## 1. Weapon/`CanSwoop` = `+0x83`

| что | адрес RW |
|---|---|
| запись таблицы полей `WeaponTemplate` | `RW 0xC16DD8`, строка `CanSwoop`: член `+0x83`, парсер `RW 0x42E558` (`parseBool`) |
| соседи по таблице | `HoldDuringReload` `+0x80`, `CanFireWhileMoving` `+0x81`, `CanFireWhileCharging` `+0x82`, дальше float `WeaponRecoil` `+0x84` |
| геттер поля | `RW 0x6CA152`: `mov al, byte ptr [ecx + 0x83]; ret` — **0 ссылок** |
| соседние геттеры того же блока | `RW 0x6CA144` (`+0x126`, 3 ссылки: `RW 0x662E68`, `RW 0x741380`, `RW 0x745A0F`), `RW 0x6CA14B` (`+0x81`, 4 ссылки: `RW 0x741388`, `RW 0x74C367`, `RW 0x74C96D`, `RW 0x74D039`) |

Ноль ссылок у геттера сам по себе ничего не доказывает (вызовы могли быть заинлайнены), поэтому переписаны **все**
байтовые чтения смещения `0x83` в `.text` — их девять; каждое привязано к классу:

| адрес | что это |
|---|---|
| `RW 0x865899` | `OpenContain::getKillPassengersOnDeath`: `[this+0xE1]` (байт «убить при смерти», ставит ctor `RW 0x86806C`) и `[moduleData+0x83]` = `KillPassengersOnDeath`. Уже перенесено (`OpenContainRuntime.cpp`, комментарий с этими адресами). К `WeaponTemplate` отношения не имеет |
| `RW 0x5F371F` | `mov al, byte ptr [ebp + 0x83]` в `RW 0x5F3664` (вызов из `RW 0x5FC601`): `ebp+0x83` — байт **аргумента в стеке**, не поле объекта |
| `RW 0x6CA152` | сам геттер `CanSwoop` (0 ссылок, см. выше) |
| `RW 0x6CE48B` | последовательное копирование структуры `RW 0x6CE39C` (`mov eax,[edi+4]; mov [esi+4],eax; …`): копия, а не потребитель |
| `RW 0xA9590C`, `RW 0xA97ED7` | упаковка байтов `+0x84..+0x87` и `+0x82..+0x83` в целое (`RW 0xA958C0` / `RW 0xA97E28`). У `WeaponTemplate` на `+0x84` лежит **float** `WeaponRecoil`, поэтому это не `WeaponTemplate` |
| `RW 0x5F507F`, `RW 0x5FC0E6` | не инструкции: кандидаты в начала функций `RW 0x5F5000` / `RW 0x5FC000` не имеют ни вызова, ни vtable-ссылки; разбор байтов от реального начала (`RW 0x5F5060`, `RW 0x5FC0C0`) даёт другой поток. Артефакты множества кандидатов |

Дополнительно: строка `"CanSwoop"` в образе ровно одна — `RW 0xC17CF0` (запись таблицы 0xC16DD8), то есть поля с
именем `CanSwoop` у другого класса нет; чтений 4-байтового слова `+0x80` (когда четыре bool слиты в dword) в области
`WeaponTemplate` (`0x6C7000..0x6D2000`) нет вовсе.

Донор: BFME2 1.06 `GameLogic/Object/WeaponStoreNewOverride.cpp` — только строка таблицы разбора, ни одного читателя.

## 2. Строки Swoop локомотора

| поле | запись таблицы RW 0xBF4478 | значение ctor `RW 0x5E4326` |
|---|---|---|
| `SwoopStandoffRadius` | `+0x124`, парсер `RW 0x42ED00` | `RW 0xBE4170` = **200.0** (тот же xmm3, что и для высоты) |
| `SwoopStandoffHeight` | `+0x128`, `RW 0x42ED00` | `RW 0xBE4170` = **200.0** |
| `SwoopTerminalVelocity` | `+0x12C`, `RW 0x42ED00` | `RW 0xBF4A2C` = **0.07** |
| `SwoopAccelerationRate` | `+0x130`, `RW 0x42ED00` | `RW 0xBF4A28` = **0.003** |
| `SwoopSpeedTuningFactor` | `+0x134`, `RW 0x42ED00` | `RW 0xBD1908` = **1.0** (в списке issue этого поля нет, но оно есть в таблице RW и в порте) |

Тело шаблона, которое их трогает:

* ctor `RW 0x5E4326`: `movss [eax+0x124], xmm3` (`0x5E4520`), `[eax+0x128]` (`0x5E4528`), `[eax+0x12C]` (`0x5E4540`,
  из `RW 0xBF4A2C`), `[eax+0x130]` (`0x5E45E9`, из `RW 0xBF4A28`), `[eax+0x134]` (`0x5E4550`, xmm1 = `RW 0xBD1908`);
* copy ctor `RW 0x5E4653`: копирует `+0x120…+0x138` подряд (`0x5E495A`…`0x5E49AB`);
* assignment `RW 0x5E31DF`: то же (`0x5E34CF`…`0x5E351D`).

Потребители шаблона. `Locomotor` держит `LocomotorTemplate*` в `+4`; функции, которые читают шаблон через `[X+4]`
(проверено трассировкой: `mov R,[X+4]` помечает R, затем читаются поля шаблона): `RW 0x5E357E` (`+0x20` Speed, `+0x44`
Acceleration, `+0x54` MinTurnSpeed), `RW 0x5E372D` (`+0x2C` TurnTime), `RW 0x5E3796` (`+0x54`), `RW 0x5E3C56`
(`+0x20`, `+0x2C`), `RW 0x5E40AD` (`+0x44`), `RW 0x5F2F55` (`+0x20`, `+0x2C`). **Ни одна не читает `+0x124…+0x134`.**
Моторы гигантских птиц `RW 0x5E91E2` (аэродвижение) и `RW 0x5E4CD3` (парение), уже перенесённые в
`LocomotorGiantBird.cpp`, берут PreferredHeight `+0x48`, Lift `+0xA0`, предел подъёма, ускорение и торможение —
строк Swoop среди них нет.

Геттеров у этих полей нет: шаблон поиска `mov eax,[reg+off]; ret` / `movss xmm0,[reg+off]; ret` по `+0x124` даёт
`RW 0x59AF80` и `RW 0x96B6EC` (0 ссылок), по `+0x128` — `RW 0x6A7AB5` (0 ссылок), по `+0x12C` — `RW 0x6C9BF1`, это
геттер блока `WeaponTemplate` (следующий байт `RW 0x6C9BF8` — геттер `+0x154`), у него тоже 0 ссылок.

Донор BFME2 1.06: `Include/GameLogic/LocomotorTemplate.h` (таблица смещений и дефолты ctor `Rva001E4DB0Ctor.cpp`:
200 / 200 / 0.07 / 0.003 / 1.0 — совпадают с RW), `Rva001E72B4Reload.cpp` (таблица разбора),
`LocomotorTemplate.cpp` / `Rva001E3955Assign.cpp` (copy/assign) — читателя нет ни одного.

## 3. Что это значит для порта

* `WeaponTemplate::m_canSwoop` и `LocomotorTemplate::m_swoop*` остаются **разобранными и мёртвыми**, как в RotWK:
  `engine/src/GameLogic/Weapon.h` (`m_canSwoop`, `// 0x83`), `engine/src/GameLogic/Locomotor.h` (`+124…+134`),
  таблицы разбора `Weapon.cpp` / `Locomotor.cpp`, дефолты `Locomotor.cpp:117-121` = RW `0x5E4326`.
* Поведения, которое надо перенести, нет: если бы порт начал читать эти поля, он разошёлся бы с RotWK. Тесты
  `PORT-67*` (`engine/tests/test_port_67.cpp`) держат именно это: разбор, значения ctor и то, что шаблон, который
  отличается только строками Swoop, не меняет ни одного поля движения.
* Вердикт записан строкой `S-7217` в `docs/STOPS.md` (аудит: поля остаются `parsed-unused` намеренно).

## Границы работы (INFERENCE)

Статический анализ, а не наблюдение запущенной игры: «читателя нет» означает, что читателя нет среди всех
инструкций `.text`, разобранных от 92 601 кандидата в начала функций (цели вызовов + указатели из `.data`/`.rdata`),
плюс сплошное перечисление операндов по смещению (9 байтовых чтений `+0x83`; чтения `+0x124…+0x134` в области
локомотора `0x5E0000..0x5F6000` — только ctor/copy/assign). Остаётся теоретическая лазейка: читатель, который берёт
указатель на шаблон не из `[X+4]` и не через геттер, — но такие обращения покрыты перечислением по смещению, а для
`+0x83` ещё и отсутствием второго поля с этим именем в образе.
