# Port 117: «призыватель Ангмара возвращает орду по одному солдату» (P-57) — анализ RotWK 2.01

Рабочая запись по issue #301. Адреса прочитаны через `tools/mod/rw.py dis|xref|str` из RotWK 2.01 (`game.dat`, MD5 `daed3668006cd90f01c34e5a7da1901f`, оговорка S-001). Донор — Open-BFME-2 (декомпиляция BFME2 1.06). Значения и выдержки INI мода здесь не приводятся: только имена объектов, модулей и полей.

Перед открытием PR ключевые места прочитаны второй раз по тому же файлу: RW `0x7977C9` .. RW `0x7978B9`, RW `0x7979D4` .. RW `0x797A07`, RW `0x68B6A1`, RW `0x8718ED` .. RW `0x87190E`, RW `0x871B9B` .. RW `0x871BBB`, RW `0x8B22EB` .. RW `0x8B2302`, RW `0x89AE5A` .. RW `0x89AE67`, слоты vtable и имена KindOf 14, 104, 109. Расхождений с первой записью нет; добавлены две ветки `buildObjectNow` (раздел 2.2) и `HorseHordeContain` (раздел 2.3).

После открытия PR по INI мода пройдены все вызовы функции, в которой стоит правка. Нашлось, кого она меняет кроме Ангмара: три призывателя Рохана и четыре орды, которые заменяют себя другой ордой через `ToggleMountedSpecialAbilityUpdate` (раздел 1). Для второго пути прочитана его функция замены RW `0x8B140D` (раздел 2.1) и добавлен тест `PORT-117 toggle: …` (раздел 7).

Итог коротко: призыв заменяет призывателя ордой через `BuildAssistant::buildObjectNow` (RW `0x797796`). В RotWK эта функция завершает объект вида `HORDE` **без производителя**: снимает его перед `Object::onBuildComplete` и ставит обратно после (RW `0x7979D4` .. RW `0x797A02`). `HordeContain` создаёт начальный состав только объекту без производителя (RW `0x871BAB`), поэтому в RotWK орда появляется сразу целиком. В порте этого шага не было: производитель оставался, орда появлялась пустой, а её знаменосец (`BannerCarrierUpdate`, RW `0x89ACE4`) добавлял по одному бойцу раз в `IdleSpawnRate` — это и видел владелец. В доноре BFME2 этого шага нет, он появился в RotWK. Правка — одно место в `engine/src/GameLogic/Construction.cpp`.

## 1. Какой призыв имеет в виду владелец

В issue названы три кандидата. По данным мода (Ennorath 1.9.8.2) за ними стоят три разных механизма:

| Кандидат из issue | Что это в данных мода | Механизм RotWK | Затронут ли |
|---|---|---|---|
| Призыв отряда рабов у `AngmarThrallMaster` (четыре кнопки: орки, всадники на волках, копейщики и пращники Рудаура) | четыре модуля `SummonReplacementSpecialAbilityUpdate`, у каждого `MountedTemplate` — орда (`AngmarOrcWarriors`, `AngmarWolfRiders`, `AngmarRhudaurSpearmen`, `AngmarRhudaurSlingers`); запускаются апгрейдами `Upgrade_ThrallMaster…` через `DoCommandUpgrade` | замена объекта через `buildObjectNow` (раздел 2) | **да, это P-57** |
| `AngmarSummonOrcEgg`, `Hillman1SummonEgg`, `Hillman2SummonEgg` | объект-«яйцо» сразу умирает, его `ObjectCreationList` создаёт орды `…_Summoned` | OCL `CreateObject` (раздел 2.5) | нет: порядок уже как в RotWK |
| `AngmarNecromancerHorde` и кнопки `Command_Necromancer*` | орда из очереди производства; кнопки — обычные способности, не призыв орды | производство: бойцы выходят из здания по одному, это штатно (RW `0x871BAB`) | нет |

Тот же модуль `SummonReplacementSpecialAbilityUpdate` в моде стоит ещё у трёх объектов Ангмара (файлы `units/angmar/new/`):

- `AngmarNecromancer` — три модуля, `MountedTemplate` — орды `AngmarNecromancerHordeFrost`, `AngmarNecromancerHordePlague`, `AngmarNecromancerHordeSoul`;
- `RhudaurWarlord` — шесть модулей, `MountedTemplate` — орды `RhudaurBarbarian…Horde` и `RhudaurWolfRiderHorde`;
- `HarbringerOfDark` — три модуля с одним и тем же `MountedTemplate` (`HarbringerThingObjectDunedainReal`). Этот объект не вида `HORDE` и без `HordeContain`: правка его не меняет.

Все они идут через ту же функцию, поэтому правка одна на всех: кого бы из них владелец ни называл «призывателем», механизм один.

Правка стоит в общей функции, поэтому по INI мода пройдены все её вызовы (раздел 4) — кого ещё она меняет:

- `SummonReplacementSpecialAbilityUpdate` вне Ангмара: `RohanHerold` (семь модулей), `RohanHeroldBow` (два), `RohanHeroldHorse` (четыре). У всех `MountedTemplate` — орда вида `HORDE` с `InitialPayload` и `BannerCarriersAllowed`; у четырёх орд `RohanHeroldHorse` контейнер — `HorseHordeContain`. Их орды в порте тоже наполнялись по одному бойцу и теперь тоже появляются целиком.
- Тот же модуль с `MountedTemplate` не вида `HORDE`: `ImladrisLoremaster` (пять модулей), `MordorTribute_forHarad` и `MordorTribute_forHaradSmall` (по одному). Для них, как и для `HarbringerOfDark`, ничего не меняется.
- `ToggleMountedSpecialAbilityUpdate` с `MountedTemplate` вида `HORDE` — орда, которая заменяет себя другой ордой: `DolguldurArcherHorde`, `MordorMorgulOrkHorde`, `IsengardVerraeterHorde` (по одному модулю) и `RohanPeasantHorde_modneu` (четыре модуля). Замена идёт через тот же слот (RW `0x8B1483`, раздел 2.1), значит новая орда теперь тоже стоит целиком. У двух из этих семи шаблонов (`IsengardVerraeterHorde`, `IsengardVerraeterCavalryHorde`) нет `BannerCarriersAllowed`: такую орду в порте до правки не наполнял никто, она оставалась пустой.
- Остальные вызовы орду в данных мода не строят: среди имён в `ReplacementObjectName` (`ReplaceObjectUpdate`), `ReplaceWith` и `AndThenAddA` (`ReplaceSelfUpgrade`), `BreadcrumbName` (`OilSpillUpdate`) и в полях шаблонов `WallHubBehavior` нет объектов вида `HORDE`; ни один объект с `RebuildHoleExposeDie` и ни один объект с `WallHubBehavior` сам не орда.

Итого по моду: шаг HORDE срабатывает для 26 модулей `SummonReplacementSpecialAbilityUpdate` у шести объектов (24 разных шаблона орды: 18 с `HordeContain`, 6 с `HorseHordeContain`) и для 7 модулей `ToggleMountedSpecialAbilityUpdate` у четырёх орд (6 шаблонов с `HordeContain`, 1 с `HorseHordeContain`).

Что проверено по данным мода для шага HORDE (раздел 2.2):

- все тринадцать орд Ангмара (четыре у `AngmarThrallMaster`, три у `AngmarNecromancer`, шесть у `RhudaurWarlord`) — объекты вида `HORDE` с `InitialPayload` и `BannerCarriersAllowed`;
- орды всадников на волках (`AngmarWolfRiders`, `RhudaurWolfRiderHorde`) используют `HorseHordeContain`, остальные одиннадцать — `HordeContain`; в RotWK состав у обоих создаёт одна и та же функция (раздел 2.3);
- ни один из десяти объектов с `SummonReplacementSpecialAbilityUpdate` и ни одна из четырёх орд с `ToggleMountedSpecialAbilityUpdate` не вида `DOZER` и не вида `BASE_FOUNDATION`, то есть `buildObjectNow` для них доходит до шага HORDE, а не уходит в ветки строителя;
- у каждого из 31 шаблона орды, названного в этих модулях, есть `InitialPayload` и контейнер `HordeContain` или `HorseHordeContain`.

Почему «по одному солдату»: у всех четырёх орд надсмотрщика в `HordeContain` задан знаменосец (`BannerCarriersAllowed`), а `BannerCarrierMinLevel` ниже начального ранга, то есть знаменосец положен орде с самого начала. В порте пустая орда получала знаменосца на первом обновлении, и он восполнял её по одному бойцу — ровно как повреждённую в бою.

Файла локализации в архиве INI нет, поэтому русское имя юнита («призыватель») с объектом не сверено. Вывод о том, какой юнит имел в виду владелец, сделан по механизму и симптому: это **INFERENCE** в части имени, но не в части поведения — других путей «замена юнита ордой по кнопке» у Ангмара в данных мода нет.

## 2. Цепочка RotWK

### 2.1. От кнопки до `buildObjectNow`

Часть цепочки до срабатывания способности установлена дорожкой SUMMON-1 и в этой задаче не перечитывалась: `DoCommandUpgrade` RW `0x8B8DAF` → кнопка → `SpecialPowerModule` (RW `0x8B8E2E` → RW `0x696FD2` → RW `0x68E5A3`) → `SummonReplacementSpecialAbilityUpdate` (инициация RW `0x8B1FDA`, срабатывание RW `0x8B2584`).

Перечитано в этой задаче — функция замены RW `0x8B228C`:

- RW `0x8B22A1` .. RW `0x8B22B3`: имя `MountedTemplate` (данные модуля `+0xE8`) → `ThingFactory::findTemplate` RW `0x6D1305` (TheThingFactory RW `0xDE4A40`). Нет шаблона — выход (RW `0x8B22BD` → RW `0x8B2500`).
- RW `0x8B22C3`: `edi` = объект-призыватель (`this + 8`). RW `0x8B22D4` .. RW `0x8B22DD`: его угол (`+0x44`) и позиция (`+0x38`). RW `0x8B22E3`: его игрок (RW `0x68B678`).
- RW `0x8B22EB` .. RW `0x8B2302`: `ecx` = TheBuildAssistant (RW `0xDE8200`), вызов слота `+0x38` его vtable с аргументами (строитель = призыватель, шаблон, позиция, угол, игрок).
- RW `0x8B2305` .. RW `0x8B2309`: объект не создан — выход. Дальше переносятся счёт (RW `0x8B2318` → RW `0x79F0E1(old, -1)`), имя (`+0x88`), опыт, здоровье, команда, таймеры. Ничего про состав орды здесь нет.

Привязка слота: vtable `BuildAssistant` — RW `0xC307D8` (её пишет конструктор, RW `0x7945ED`); слот `+0x38` — RW `0xC30810`, в нём RW `0x797796`. Это 14-й слот; в доноре `buildObjectNow` тоже vslot 14.

Вторая функция замены — у `ToggleMountedSpecialAbilityUpdate`, RW `0x8B140D` — зовёт тот же слот:

- RW `0x8B1422` .. RW `0x8B1434`: имя `MountedTemplate` (данные модуля `+0xD8`) → RW `0x6D1305`; нет шаблона — выход (RW `0x8B143E` → RW `0x8B1681`).
- RW `0x8B1444`: объект (`this + 8`); RW `0x8B1455` и RW `0x8B145E`: его угол (`+0x44`) и позиция (`+0x38`); RW `0x8B1464`: его игрок (RW `0x68B678`).
- RW `0x8B146C` .. RW `0x8B1483`: `ecx` = TheBuildAssistant (RW `0xDE8200`), вызов слота `+0x38` с теми же пятью аргументами.
- дальше до RW `0x8B168F` — тот же перенос счёта, имени, опыта, здоровья, команды и таймеров (прочитано по списку вызовов, без разбора каждого). Про состав орды и здесь ничего нет.
- старый объект уничтожается после упаковки: RW `0x8B1E9A` на RW `0x8B1ED9` .. RW `0x8B1EE0` зовёт RW `0x62BBAB` у объекта RW `0xDE412C` — по записям порта это `GameLogic::destroyObject` и TheGameLogic (`ConstructionSite.cpp`, `SpecialAbilityModules.cpp`, дорожка HERO-2). Что при этом делает `HordeContain` старой орды со своими бойцами, не читалось.

Так в моде устроена замена орды другой ордой (раздел 1).

### 2.2. `BuildAssistant::buildObjectNow` — RW `0x797796`

Аргументы: `[ebp+8]` строитель, `[ebp+0xC]` шаблон, `[ebp+0x10]` позиция, `[ebp+0x14]` угол, `[ebp+0x18]` игрок.

| Адреса | Что делает |
|---|---|
| RW `0x7977A8` .. RW `0x7977C3` | нет шаблона, позиции или игрока → возвращает NULL (RW `0x797A0B`) |
| RW `0x7977C9` .. RW `0x797807` | расчистка места (RW `0x7977F3` → RW `0x796576`) и второй вызов RW `0x797807` → RW `0x797465` (в порте это отвод юнитов с места, `ConstructionSite::prepareSite`; сама функция здесь не читалась), кроме случаев: строитель вида DOZER (KindOf бит 14, шаблон строителя `+0x109 & 0x40`), шаблон NO_COLLIDE (бит 30, `+0x10B & 0x40`) или DO_NOT_CLASSIFY (бит 149, `+0x11A & 0x20`). Строитель читается без проверки на NULL (RW `0x7977CC`) |
| RW `0x79780C` .. RW `0x79784A` | строитель вида DOZER (тот же бит 14): объект строит не эта функция, а ИИ строителя — `[строитель+0x260]`, слот `+0x1F8` (RW `0x797844`). Выход на RW `0x797A0D`, мимо шага HORDE |
| RW `0x79784F` .. RW `0x797876` | строитель вида BASE_FOUNDATION (бит 104, шаблон строителя `+0x115 & 1`): объект строит интерфейс участка — RW `0x68C3C3`, слот `+0x1C` (RW `0x797873`). Выход на RW `0x797A0D`, мимо шага HORDE |
| RW `0x7978A1` .. RW `0x7978AF` | `ThingFactory::newObject` RW `0x6D165E` |
| RW `0x7978B6` .. RW `0x7978B9` | `Object::setProducer(строитель)` RW `0x68B6A1`: `[obj+0x78] = arg ? [arg+0x74] : 0` |
| дальше до RW `0x7979D4` | позиция, угол, слой, карта проходимости; для постройки — RW `0x6AAF3B` / RW `0x6AA72B`, для остального — RW `0x6AA688` и голосовое сообщение `0x7DA` |
| RW `0x7979D4` .. RW `0x7979E2` | `eax` = шаблон нового объекта (`[esi+4]`), `ebx = 0x2000`, `test [eax+0x114], ebx`. Слово `+0x114` — биты KindOf 96..127, `0x2000` — бит 109. В таблице имён KindOf RW `0xDA0E68` индекс 109 — `HORDE` |
| RW `0x7979E4` .. RW `0x7979E8` | **только для HORDE**: `push 0` → `Object::setProducer(NULL)` |
| RW `0x7979ED` .. RW `0x7979EF` | `Object::onBuildComplete` RW `0x68D252` |
| RW `0x7979F4` .. RW `0x7979FD` | та же проверка бита 109 ещё раз |
| RW `0x7979FF` .. RW `0x797A02` | **только для HORDE**: `push edi` (тот же аргумент-строитель) → `Object::setProducer(строитель)` |
| RW `0x797A07` | возвращает объект |

То есть для орды производитель снят ровно на время `onBuildComplete` и возвращён сразу после. Для любого другого объекта производитель стоит всё время.

До шага HORDE доходит только третья ветка — «построить сразу» (RW `0x79787B` и дальше). В порте первые две ветки — отдельные функции (постройка дозером и постройка на участке, описаны в `engine/src/GameLogic/Construction.h`), а `Construction::buildObjectNow` — как раз третья. Призыватели мода — не DOZER и не BASE_FOUNDATION (раздел 1), поэтому призыв идёт через шаг HORDE.

Регистр `edi` на RW `0x7979FF` — тот же аргумент-строитель, что на RW `0x7978B6`: он загружен на RW `0x7977C9` (`[ebp+8]`), а меняет его только ветка DOZER (RW `0x797818`), которая до этих мест не доходит.

`Object::onBuildComplete` RW `0x68D252`: обходит модули объекта (`+0x24C`), у каждого берёт интерфейс создания (слот `+0xC` подобъекта `+0xC`) и вызывает его слот 1 (`call [edx+4]`, RW `0x68D26E`); затем то же для модулей клиента (RW `0x68D27A` и дальше).

### 2.3. `HordeContain`: слот создания и начальный состав

Привязка класса по цепочке «регистрация → создание → конструктор → vtable → слот»:

- строка реестра модулей с именем `HordeContain` (RW `0xC0BBE8`): RW `0x65822F` .. RW `0x65824D`, функция создания — RW `0x64B5D5`;
- RW `0x64B5D5`: выделяет `0x30C` байт (RW `0x64B5E0`) и вызывает конструктор RW `0x8727F9` (RW `0x64B5FF`);
- конструктор пишет основную vtable RW `0xC5B5F8` (RW `0x87282B`) и vtable интерфейса создания RW `0xC5B470` в подобъект `+0x34` (RW `0x872862`);
- слот 1 интерфейса создания (RW `0xC5B474`) — RW `0x8718ED`; слот `+0x70` основной vtable (RW `0xC5B668`) — RW `0x871B9B`.

`HorseHordeContain` (орды всадников) — тот же путь. Его функция создания RW `0x64B664` (адрес из реестра модулей порта, `engine/data/rotwk-201/module-registry.json`) выделяет те же `0x30C` байт и вызывает конструктор RW `0x879849`. Конструктор сначала вызывает конструктор `HordeContain` (RW `0x879854` → RW `0x8727F9`), затем ставит свою основную vtable RW `0xC5C288`, а в подобъект `+0x34` — ту же vtable интерфейса создания RW `0xC5B470` (RW `0x879890`). Слот `+0x70` его основной vtable (RW `0xC5C2F8`) — тот же RW `0x871B9B`. Значит, завершение орды и создание состава у `HorseHordeContain` — те же две функции, что разобраны ниже. В порте оба имени привязаны к одному классу (`HordeContain::registerClasses`).

RW `0x8718ED` (`onBuildComplete` орды, `this` — подобъект `+0x34`):

| Адреса | Что делает |
|---|---|
| RW `0x8718F0` | переходник RW `0x869ED4` (`add ecx, -0x34; jmp [vtable+0x70]`) → `createPayload` RW `0x871B9B` |
| RW `0x8718F5` .. RW `0x8718FC` | у объекта есть производитель (`[obj+0x78] != 0`) → выход |
| RW `0x8718FE` .. RW `0x871908` | байт данных модуля `+0x27C` не ноль → выход. Это `BannerCarrierMinLevel`: строка таблицы полей RW `0xC5BB50` со смещением 636 = `0x27C` |
| RW `0x87190A` .. RW `0x87190E` | иначе переход на создание знаменосца RW `0x870204` (раздел 2.4) |

RW `0x871B9B` (`createPayload` орды):

- RW `0x871BAB` .. RW `0x871BB3`: `[obj+0x78]` (производитель) не ноль → `jne 0x871D34`, то есть выход без единого действия.
- RW `0x871BBB`: иначе `TransportContain::createPayload` RW `0x86A1FA`, затем расстановка по строю.

RW `0x86A1FA`: цикл по списку `InitialPayload` (данные `+0xA4`, имя записи `+8`, количество `+0xC`). Запись с неположительным количеством (RW `0x86A234`) или без шаблона (RW `0x86A241` .. RW `0x86A24B`) прекращает весь цикл; иначе создаются **все** экземпляры записи подряд (внутренний цикл RW `0x86A27F` .. RW `0x86A2A6`, вызов создания RW `0x86A2A1`), после чего берётся следующая запись (RW `0x86A2B7` .. RW `0x86A2C5`). Вся орда создаётся одним вызовом, внутри `onBuildComplete`.

Значит, в кадре срабатывания призыва: `buildObjectNow` → производитель снят → `onBuildComplete` → `createPayload` видит ноль → создаёт весь `InitialPayload` → производитель возвращён. Орда целиком существует в тот же кадр, что и сам объект орды.

### 2.4. Знаменосец

Создание знаменосца RW `0x870204` (прочитано до RW `0x8703B3`, дальше не читалось):

- RW `0x870217` .. RW `0x870220`: знаменосец уже есть (`H+0x26C != 0`) → выход.
- RW `0x870226` .. RW `0x870233`: список `BannerCarriersAllowed` (данные `+0x218`) пуст → выход.
- RW `0x870239` .. RW `0x87024A`: шаблон первого имени списка; нет шаблона → выход.
- RW `0x87025D` .. RW `0x87027C`: счётчик очков игрока орды (`игрок + 0x3DC`) выключается на время создания (RW `0x79DC9E(0)`), потом возвращается (RW `0x8702F6`).
- RW `0x870281` .. RW `0x8702EA`: команда нового объекта. Без статуса `0x3E` у орды (RW `0x44DDEC`; в реестре порта это TEMPORARILY_DEFECTED) берётся команда орды (`+0x31C`); со статусом команда ищется по имени (RW `0x86DBC4` → RW `0x7A7483`), и если её нет — выход. Затем `newObject` RW `0x6D165E`.
- RW `0x8702FB` .. RW `0x870338`: три флага `0x18`, `0x19`, `0x1A` орды (проверка RW `0x68DEEC`) ставятся знаменосцу (RW `0x691059`).
- дальше — ИИ знаменосца (RW `0x70E013`), статус `0x3E` (RW `0x6930C9`), RW `0x625E0A`, поиск производителя орды (RW `0x870396` .. RW `0x87039F`). Эта часть прочитана только по вызовам, без разбора.

Важное для этой задачи: RW `0x8718F5` .. RW `0x87190E` создаёт знаменосца **прямо при завершении** орды, если у неё нет производителя и `BannerCarrierMinLevel` равен нулю. Так как `buildObjectNow` снимает производителя у орды, призванная орда с нулевым `BannerCarrierMinLevel` получает и весь состав, и знаменосца в одном вызове.

Обновление знаменосца RW `0x89ACE4` (`BannerCarrierUpdate::update`):

- все ветки заканчиваются на RW `0x89AE67`: `mov eax, [data+8]` — возвращается `IdleSpawnRate` как время сна;
- боец добавляется в одном месте — RW `0x89AE5A` .. RW `0x89AE61` (вызов RW `0x89A392`), не более одного раза за обновление.

Отсюда «один боец раз в `IdleSpawnRate`» — штатное восполнение повреждённой орды. Правка его не трогает.

### 2.5. Путь «яиц» — `ObjectCreationList`

RW `0x5F1600` .. RW `0x5F1656` (создание объекта в OCL): `Object::onBuildComplete` вызывается на RW `0x5F1623` (вокруг него выключен счётчик очков: RW `0x5F161B`, RW `0x5F162D`), а `Object::setProducer(источник)` — позже, на RW `0x5F1656`. В момент `onBuildComplete` производителя ещё нет, орда создаётся целиком.

В порте порядок тот же: `engine/src/GameLogic/ObjectCreationList.cpp`, `friend_onBuildComplete()` (строка с пометкой RW `0x5F1623`) стоит раньше `setProducer(source)` (RW `0x5F1656`). Этот путь не затронут и не менялся.

## 3. Донор BFME2 1.06

- `BuildAssistant::buildObjectNow` — DONOR BFME2 `0x003952D8` (`Code/GameEngine/Source/Common/System/BuildAssistant.cpp`, vslot 14): `setProducer` после `newObject`, затем `onBuildComplete`. Снятия и возврата производителя для HORDE там **нет**.
- Класса `SummonReplacementSpecialAbilityUpdate` в доноре нет (ближайший — `ToggleMountedSpecialAbilityUpdate`). Всё, что сказано о нём выше, взято из RotWK.

Вывод: шаг RW `0x7979D4` .. RW `0x797A02` — собственный шаг RotWK. Он подтверждён инструкциями RotWK, донор для него не источник.

## 4. Порт: первое расхождение

`Construction::buildObjectNow` (`engine/src/GameLogic/Construction.cpp`) — порт RW `0x797796`. До правки: `setProducer(builder)` после создания объекта и сразу `friend_onBuildComplete()` в конце, без шага для HORDE.

Следствие по цепочке порта:

1. `HordeContain::onBuildComplete` → `createPayload` (`engine/src/GameLogic/Object/Contain/HordeContainRuntime.cpp`) выходит, потому что производитель задан (это верный перенос RW `0x871BAB`). Орда пуста.
2. `HordeContain::update` → `bannerCheck` (RW `0x8719E4`, `HordeBanner.cpp`) создаёт знаменосца, если `BannerCarrierMinLevel` ниже ранга орды.
3. `BannerCarrierUpdate::update` (RW `0x89ACE4`) добавляет по одному бойцу раз в `IdleSpawnRate`, пока состав меньше `Slots`.

Первое место, где порт расходится с RotWK, — шаг 0: `buildObjectNow`. Шаги 1–3 перенесены верно и работают как в RotWK для своих входных данных.

Вызовы `Construction::buildObjectNow` в порте: `replaceWithTemplate` (`SpecialAbilityModules.cpp`: ToggleMounted RW `0x8B140D` и SummonReplacement RW `0x8B228C`), `ReplaceObjectUpdate`, `ReplaceSelfUpgrade`, `RebuildHoleModules`, `OilSpillUpdate`, `WallSpan`. Правка действует на любой из них, если строится объект вида HORDE. В данных мода орду строит только `replaceWithTemplate` — оба его модуля; у остальных четырёх вызовов шаблонов вида HORDE в моде нет (раздел 1).

## 5. Правка

В `Construction::buildObjectNow`, вместо одиночного `friend_onBuildComplete()`:

- если шаблон нового объекта имеет KindOf `HORDE` — `setProducer(nullptr)` (RW `0x7979E4` .. RW `0x7979E8`);
- `friend_onBuildComplete()` (RW `0x7979EF`);
- если HORDE — `setProducer(builder)` тем же аргументом (RW `0x7979FF` .. RW `0x797A02`).

Нового состояния симуляции нет: `m_producerID` уже сохраняется и хэшируется, его конечное значение не меняется. `HordeContain*` не тронут.

Строитель NULL: RotWK читает строителя без проверки (RW `0x7977CC`), у него такого случая нет. В порте функция допускает NULL, но все шесть вызовов в коде игры передают объект; без строителя её зовёт только один тест (`test_build_rate.cpp`, постройка, не HORDE). Для NULL поведение прежнее — производителя нет, орда целая.

## 6. Что осталось и INFERENCE

- **Не перенесено (область S-587; своя строка этой задачи в `docs/STOPS.md` — S-7317):** создание знаменосца при завершении орды, RW `0x8718F5` .. RW `0x87190E` → RW `0x870204`. В RotWK призванная орда с нулевым `BannerCarrierMinLevel` получает знаменосца в том же вызове, что и состав. В порте знаменосца создаёт `bannerCheck` на первом обновлении орды (нужен ранг выше `BannerCarrierMinLevel`); по замеру теста на синтетической орде — через 1 логический кадр после вызова. Стоп виден в отчёте игры: строка `[S-7317]` из `Construction::stopLines` попадает в `GameLogic::report().stops`. Это общий механизм `HordeContain` для любой орды, у которой в момент `onBuildComplete` нет производителя (так идёт и путь OCL, раздел 2.5; вызывается ли `onBuildComplete` у орд карты и скриптов, в этой задаче не проверялось). Он лежит в области S-587 и в файлах, которые этой задаче править нельзя (issue #301: в `HordeContain*` только свой вызов). Наблюдение для S-587: у орды **из производства** производитель задан, и ветка RW `0x8718F5` ей знаменосца при завершении не даёт.
- **INFERENCE:** какой именно юнит владелец называет «призывателем» (раздел 1) — по механизму и симптому, без файла локализации.
- **INFERENCE (чужая, SUMMON-1):** звенья от кнопки до RW `0x8B2584` в этой задаче не перечитывались.
- Функция RW `0x870204` прочитана не до конца (после RW `0x8703B3` — нет).
- **Не читалось:** что RotWK делает с бойцами старой орды, когда орда заменяет себя другой ордой (`ToggleMountedSpecialAbilityUpdate`, раздел 2.1). В порте старая орда и её бойцы уходят вместе (`HordeContain::onDelete`); правка этого не трогает, она касается только новой орды. Тест `PORT-117 toggle: …` это печатает, но не проверяет.
- Вторая функция замены RW `0x8B140D` после вызова слота прочитана по списку вызовов, без разбора каждого.
