DONOR BFME2 0x0046279C / 0x0046282B (`Code/GameEngine/Source/GameLogic/Object/Contain/OpenContainSounds.cpp`).

Both main tables map slot 0x54 to RW 0x8658A3 and 0x58 to RW 0x865932. OpenContain's contain table slot 0x14C maps to RW 0x867AA1.
* The field table places EnterSound at module data +0x38 and ExitSound at +0x3C. RW 0x8658B6 checks the module's load-sound enabled byte +0xDD; RW 0x8658C8 skips if the current frame equals +0x80. Otherwise, when data is non-null, RW 0x8658D9 constructs an event from +0x38, RW 0x8658EB uses the container object ID, and RW 0x86590C calls audio slot 0x64. RW 0x86591E records the frame even if data is null. Disabled skips the frame update.
* RW 0x86594E skips unloading if the frame equals +0x7C; otherwise RW 0x86595C uses data +0x3C, RW 0x86596E uses the container object ID, RW 0x86598F calls audio slot 0x64, and RW 0x8659A1 stores the frame, including when data is null. The two last-frame counters are independent.
* RW 0x86804E / 0x868051 initialize those counters to zero and RW 0x868098 initializes +0xDD to true. RW 0x867AA5 changes +0xDD through contain interface slot 0x14C. Snapshot RW 0x869265 / 0x869270 transfers both counters and RW 0x869476 transfers the enable byte.

The parsed sounds are not played there. `TransportContainRuntime.cpp` and `SiegeEngineContainRuntime.cpp` already identify RW enable/disable calls but currently omit them; these need confirmation before implementation.

The unrelated callbacks RW 0x865F9A / 0x8680F4 use object-specific audio getters RW 0x865C98 / 0x865CB1, not module data +0x38 / +0x3C. The current comments identifying those callbacks as the module-data sounds need correction in the implementation step.

## Scope conflict discovered

RW 0x872811 calls TransportContain's constructor from HordeContain's constructor; RW 0x87282B / 0x87283F install primary table 0xC5B5F8 and contain table 0xC5B480. The latter's slots 0x9C / 0xA4 / 0x14C resolve to the shared OpenContain implementations RW 0x8674C2 / 0x8665BE / 0x867AA1. The former's slots 0x54 / 0x58 resolve to RW 0x8658A3 / 0x865932. RW 0x872D29 then calls the unrelated onContaining callback RW 0x865F9A before HordeContain's rank/slot logic. Thus the shared sound mechanism applies to HordeContain too, not only OpenContain's ported heirs.

In the port `HordeContain` is an independent `ContainModuleInterface` implementation (`HordeContainRuntime.h:182`), not an `OpenContain` subclass; `HordeContainRuntime.cpp:387` implements its own add and member/rank placement and `:977` its own removal, while `HordeContainModuleData::m_transport.m_open` stores the same parsed sound fields. Implementing only OpenContain's path would miss this class; merging or sharing its add/remove mechanism affects horde-member and rank paths, which overlap the separately assigned horde-ranks task. No solution is selected without the owner's direction.

## Owner's proposed callback paths versus the module fields

After rebasing on `origin/main` (which contains Port 81 and Local 23), RW 0x872D29 was re-read: HordeContain's onContaining really calls RW 0x865F9A. Its onRemoving calls RW 0x8680F4 at RW 0x86CF35. GarrisonContain likewise calls them at RW 0x87BEDA / 0x87BFD8. DONOR BFME2 0x00463097 (`OpenContain_onContaining.cpp`) and 0x00464D02 (`OpenContainOnRemoving.cpp`) are the corresponding callbacks.

However, RW 0x865FB6 / 0x865FB9 obtains the container object's drawable (RW 0x70E013, object +0x84); RW 0x865FD0 calls the drawable's sound-row getter 0x865C98, which requests row 0x2F at RW 0x865CA0. RW 0x868123 calls the analogous getter 0x865CB1, requesting row 0x30 at RW 0x865CB9. Those are object sound rows `SoundEnter` / `SoundExit`, not the contain-module fields `EnterSound` / `ExitSound` at module data +0x38 / +0x3C. The latter are read in the separate main slots 0x54 / 0x58 (RW 0x8658D9 / 0x86595C), and are deduplicated per frame (RW 0x8658C8 / 0x86594E). Calling the module-field sound from each callback would therefore alter the specified behavior and can multiply the sound for members of a horde. It would also conflate the separate object-sound issue S-707 with Port 90. Owner direction is needed before proceeding.

Owner decision: implement module fields via the proven 0x54 / 0x58 paths, separately from object sound rows, and leave horde rank/placement logic untouched. The counters are module state: RW 0x86804E / 0x868051 initialize them, and RW 0x869265 / 0x869270 transfers them, so the port must persist and hash them. Both are per containing module, not global or per passenger. RW 0x86754C / 0x865F73 invoke those slots after each successful base add / remove; same-frame calls on that one container collapse independently for entry and exit. RW 0x86A264 / 0x86A2B1 disable and re-enable entry sounds when the transport base creates an initial payload. DONOR BFME2 0x0046E8EE (`HordeContain_createPayload.cpp`) calls TransportContain::createPayload, so the equivalent RW path requires validation for the port's independent HordeContain payload loop.

Further slot-call review found an additional relevant path: RW 0x880FC6 is TunnelContain::onRemoving, and RW 0x881033 calls the main 0x58 unload-sound slot after its GarrisonContain base callback. This matters for horde members that use the special garrison callback instead of base removal. The corresponding port function `TunnelContainRuntime.cpp` already identifies the missing sound. Any implementation limited to base remove would miss that path. RW 0x869A10 is a separate CaveContain unload-sound call; the port does not implement CaveContain. RW 0x871BBB calls TransportContain::createPayload from HordeContain, confirming RW suppression of initial horde payload sounds via RW 0x86A264 / 0x86A2B1. `HordeContainRuntime.cpp` has an independent payload loop and must reproduce that toggle without modifying rank or placement statements.

The apparent additional `+0x58` call at RW 0x867530 is not a module sound call: RW 0x867520 loads the container object's +0x258 pointer into `ecx`, checks it, and RW 0x86752D loads that object's vtable before the call. DONOR BFME2 `OpenContainRva00464EE7.cpp` identifies Object+0x258 as the AI interface; unlike RW 0x86754C, this call does not use the contain module's main vtable. Thus it is not another reader of the module ExitSound slot.
