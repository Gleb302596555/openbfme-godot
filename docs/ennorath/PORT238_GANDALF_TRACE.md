# PORT-238: Gandalf ring branching (partial trace)

Declarations below are from extracted Ennorath 1.9.8.3 (INI archive MD5 `c53b6dea885cab044f80e783565f41f3`). Paths are relative to `data/ini`. The 1.9.8.4/1.9.8.5 files have not been independently compared. This is not effective inheritance/load, real-game, complete ability or visual validation.

## Declared branching

`GondorGandalf_mod` has a white-form toggle on PLAYER `Upgrade_GandalfWhite` (`upgrade.ini:1062`; `object/goodfaction/units/gondor/gondorgandalf.ini:1415–1441`). Its ring delivery grants OBJECT `Upgrade_RingHero Upgrade_FortressRingHero` (`:1481–1499`). The base's ring `DoCommandUpgrade` triggers on those names, conflicts with `Upgrade_GandalfWhite`, and calls the corrupted-form toggle `GondorGandalfVerfhrte` (`:1448–1473`). This declaration does **not** specify `RequiresAllTriggers = Yes`. The white child `GondorGandalfWhite_mod` overrides the corresponding command to choose `GondorGandalfGeprfte`, and has its own ring entry (`:2055,2772–2792,2979–3003`). The corrupted form also has a white-upgrade command toggling to `GondorGandalfGeprfte` (`gondorgandalfverfhrte.ini:1328–1350`). All three toggles list the same five named cooldowns; the synthetic case below does not test them.

`PORT-238 Gandalf-style white choice before or after ring delivery` constructs separate synthetic objects rather than loading the mod's child inheritance. With the white flag before ring delivery and after the first toggle finishes, it delivers the ring to synthetic white and obtains synthetic good. With ring delivery first and after the corrupted toggle finishes, a direct PLAYER grant produces synthetic good from corrupted. Both assert ownership and ring destruction. A third subcase directly delivers during an already started synthetic white transition: the conflict prevents the corrupted command; in the isolated port the replacement is white with neither OBJECT upgrade and no subsequent good replacement after 50 further frames. This is an **observation**, not evidence that RW or a real UI permits or handles that sequence identically. In particular the fixture directly invokes containment and bypasses actual admission/timing checks. Reproduce with real inheritance, player commands, saves and mod before concluding there is a gameplay defect.

RW `0x8B140D` is the mounted replacement routine; vtable `0xC307D8` slot `+0x38` is `0x797796` (`PORT117_RW_ANALYSIS.md`), called at `0x8B1483` with the old object as builder, and `0x8B15FA` calls the timer-copy routine `0x8B12BF`. The BFME2 donor `ToggleMountedSpecialAbilityUpdate.cpp` contains its analogous `createMountedTemplate`; current port calls `Construction::buildObjectNow` and explicitly copies selected properties and named timers in `SpecialAbilityModules.cpp:2492`. These facts do not alone establish every indirect construction/upgrade side effect in RW, or effective child defaults; no change or RW parity verdict is inferred for the simultaneous sequence. Shared replacement limitations include S-861.

The three subcases passed **97/97 assertions**; isolated `PORT-238*` passed **32/32 cases, 2048/2048 assertions**, using matching `3f0105c8` core/headers with the upstream PORT-286 parser separately compiled, not the current-main full binary. Removing only `ConflictsWith` from the synthetic fixture gives **96/97**; the erroneous cursed-command execution check fails. This is fixture sensitivity, not proof of an engine fix.

## Separate legacy `GondorGandalf` declaration

`object/goodfaction/units/men/gandalf.ini:9` is a separate object from `GondorGandalf_mod` in `units/gondor/gondorgandalf.ini`. Its literal ring contain grants the same two OBJECT upgrades, consumes `TheDroppedRing`, and gates its death OCL on both (`men/gandalf.ini:1572–1601`). Its `SpecialAbilityGandalfVerfhrte` starter unpauses on OBJECT `Upgrade_RingHero` and toggles to `GondorGandalfVerfhrte`; the file does **not** declare an automatic command for that branch (`:1511–1532`). `SpecialAbilityGandalfGeprfte` unpause and automatic `DoCommandUpgrade` both require **all** of PLAYER `Upgrade_GandalfWhite` and OBJECT `Upgrade_RingHero` (`:1538–1567`, types in `upgrade.ini:181,1062`). The good toggle targets `GondorGandalfGeprfte`; both toggles list four timer names, not the five in the separate `_mod` trace (`:1525,1554`). The direct command-set declaration names `GondorGandalfModCommandSet` (`:934`); that set lists the corrupted button, while the separately selected `GondorGandalfModChangeCommandSet` lists both buttons (`includes/commandset.inc:13822–13866`, object weapon-toggle selection `men/gandalf.ini:1223–1228`). Both buttons declare `ON_GROUND_ONLY` and `InPalantir = Yes` (`includes/commandbutton.inc:18698–18724`). These literal facts do not prove the effective set, an available UI route or real play.

The BFME2 UpgradeMux/Object implementation is a lead; RW `Object::updateUpgradeModules` starts `0x6936FE`, takes the owning player's upgrade mask and ORs in the object's (`0x693765–0x693780`), then calls the mux; `0x8D26F3` selects the all/any tests for conflicts and triggers. RW `UnpauseSpecialPowerUpgrade::upgradeImplementation` `0x8B9676` walks power interfaces and unpauses matching templates; the port's `Object.cpp`, `UpgradeModule.cpp` and `HeroModules.cpp` implement this bounded mechanism. `DoCommandUpgrade` and replacement leads are in the preceding section.

`PORT-238 legacy Gandalf-style PLAYER white and OBJECT ring jointly unlock the good form` uses a synthetic base and destination (not the mod inheritance graph). Both grants execute the good enabler and auto-command and eventually replace the base with a friendly good form. Direct ring containment also consumes the test ring and grants both OBJECT upgrades; a second player's base stays present and does not get white. The test is **100/100 assertions**, isolated `PORT-238*` **43/43 cases, 2907/2907 assertions**, on matching `3f0105c8` core/headers plus the separately compiled upstream PORT-286 parser. Changing only both good-path synthetic `RequiresAllTriggers` values to No fails **6 checks (94/100)**. This is fixture sensitivity, not a pre-fix engine control. Neither the manual corrupted path, four cooldown copies, effective command set, acquisition of white, UI admission, save/death, real game, nor appearance are established.
