# PORT-246 — исследование клиентского fade (не завершено)

По решению владельца деревья переданы Port 266 (issue 625, S-7402), пол — Port 267 (issue 626, S-7403); этот порт реализует только общий путь fade субобъектов.

Рабочая заметка: данные игры и мода сюда не копируются. Ниже только проверенные инструкции RotWK 2.01; это пока не основание считать какой-либо пункт перенесённым или нечитанным.

## Деревья

* Таблица W3DTreeDraw — RW 0xBE2E80; create данных RW 0x464402 вызывает конструктор RW 0x4CE3A8, который устанавливает vtable 0xBE2C88. FadeTarget разбирается в +0x5C, FadeDistance в +0x60.
* DONOR BFME2 0x000EDB47 (`GameEngineDevice/Source/W3DDevice/GameClient/W3DTreeBufferUpdate.cpp`): обновление буфера ищет подходящие объекты вокруг видимого дерева, не расстояние до камеры. Проверено RW 0x4ED508: глобальные/пауза-условия в начале; RW 0x4ED6F1 берёт радиус +0x60 данных типа и передаёт его в запрос объектов RW 0xA39340; RW 0x4ED70A–0x4ED76F фильтруют найденные объекты; RW 0x4ED780 выбирает 255 при отсутствии, RW 0x4ED7DD–0x4ED7F2 — +0x5C при наличии. RW 0x4ED796–0x4ED7AF помечает изменившуюся прозрачность.
* DONOR BFME2 0x000EBFD1 (`GameEngineDevice/Source/W3DDevice/GameClient/W3DTreeBuffer.cpp`): обновление вершин сдвигает прозрачность к цели. RW 0x4EB992, инструкции 0x4EBA54–0x4EBA94, при включённом глобальном переключателе приближает текущую прозрачность дерева к цели на FadeRate (+0x58), ограничивая её целью.
* Зависимость: RW 0x4ED578–0x4ED5B2 строит фильтр из GlobalData +0xEB0, RW 0x4ED689–0x4ED6B2 проверяет глобальный переключатель и доступность служб. В порте `TreeTopple` и `MapObjectRuntime` нет соответствующего чтения `AllowTreeFading` / `TreeFadeObjectFilter`; данные об этих полях есть в `engine/tests/data/port70/gamedata-rows.txt`. Нужно изучить общий GameData/filter и рендер экземпляров, не заменяя фильтр догадкой.

## Пол

* Таблица RW 0xBE3548, строка FloorFadeRateOnObjectDeath RW 0xBE3578 разбирает +0x20; create данных RW 0x46459D вызывает конструктор RW 0x4CEE74, vtable данных 0xBE3470. Конструктор экземпляра RW 0x4CE91B и деструктор RW 0x4CE9B6 устанавливают vtable 0xBE3378; её слот +0x2C содержит RW 0x4CEBCA (doDrawModule).
* DONOR BFME2 0x000CF3BA (`GameEngineDevice/Source/W3DDevice/GameClient/Drawable/Draw/W3DFloorDraw_doDrawModule.cpp`): проверка данных, drawable, ненулевой скорости и effectively-dead. RW 0x4CEBCA выполняет те же проверки (0x4CEBDA читает +0x20, 0x4CEBEC–0x4CEBFD проверяет объект и статус), 0x4CEC1E передаёт имя модели и скорость в RW 0x46AFCA; RW 0x46AFCA передаёт в буфер пола RW 0x4E5A5B. Последний проверяет вход и доступность буфера, проходит записи, сверяет drawable и имя и записывает скорость в запись +0x88 (0x4E5A98).
* DONOR BFME2 `W3DFloorBuffer.cpp` (0x000E6135 и 0x000E5406): общий буфер пола хранит отдельно прозрачность и скорость и рисует пол. RW 0x4E3EC5 при наличии drawable и состоянии записи 1 берёт ненулевую скорость +0x88 и прибавляет её к opacity +0x84 с ограничением 0..1; при нулевой скорости берёт opacity drawable и проверяет его матрицу. RW 0x4E547D вызывает обновление записи; RW 0x4E504B передаёт обе величины через xfer (0x4E50C3–0x4E50DA). В порте пол — статическая запись `Drawable` / `MapObjectRuntime` и экземпляр Godot, а не этот буфер. Нужно разобрать жизненный цикл записи и сохранение; точечное изменение opacity живого объекта не воспроизводит общий update.

## Субобъекты upgrade

* Таблица RW 0xC6E928: FadeTimeInSeconds +0x168, WaitBeforeFadeInSeconds +0x16C и SkipFadeOnCreate +0x171. Create RW 0x64FE80 вызывает конструктор RW 0x8B8EE4.
* DONOR BFME2 0x004B4DBF (`GameEngine/Source/GameLogic/Object/Upgrade/SubObjectsUpgrade.cpp`): получение двух скоростей. RW 0x8B8F40 выходит при SkipFadeOnCreate, а при нуле в object +0x78 — также до истечения трёх логических кадров после создания; 0x8B8F6A–0x8B8FA5 рассчитывает скорость fade для ненулевого времени, 0x8B8FA9–0x8B8FD0 аналогично рассчитывает скорость ожидания при ненулевом WaitBeforeFadeInSeconds. Вызывающие RW 0x8B91AD и RW 0x8B928E инициализируют обе скорости нулём и передают их в обработчики show/hide RW 0x8B9050 / 0x8B909E; второй инвертирует скорость fade для скрытия. RW 0x672823 рассылает обе скорости во все draw-модули через слот 0x88; RW 0x4C3B25 записывает их вместе с именем и состоянием permanent-запроса.
* DONOR BFME2 `W3DModelDrawUpdateSubObjects.cpp` описывает общий вектор fade-запросов. RW 0x4B31C9 при ненулевой скорости и доступном drawable сначала уменьшает ожидание +0x14 на скорость +0x10 (0x4B3230–0x4B325F), затем изменяет opacity +0x0C на скорость +0x08, ограничивая 0..1 (0x4B3261–0x4B3291); при нулевой скорости переключает видимость напрямую (0x4B3293). При drawable +0x442 == 0 завершает fade сразу (0x4B31E8–0x4B322E).
* RW 0x8B8EE4 сохраняет именно кадр создания **модуля** (+0x1C), а не кадр создания объекта; RW 0x8B8F50–0x8B8F68 пропускает трёхкадровую задержку при ненулевом producer ID объекта (+0x78; `Object::getProducerID` в порте). Частота клиентских кадров RW 0xD9F60C = 30. Это состояние модуля нужно сохранить и включить в CRC вместе с реализацией; подмена кадром объекта не доказана.
* RW 0x4C3B25 для нового permanent-запроса инициализирует opacity константами RW 0xBE0358 (0.9999f, show) и RW 0xBD19E0 (0.0001f, hide), а не 1 и 0; существующий запрос сохраняет текущую opacity. RW 0x4BA74F имеет wildcard-ветку, которая может вызывать RW 0x4B31C9 для каждого совпадения, так что обновление нельзя без доказательства свести к одному шагу на имя.
* Сохранение: `GameLogicObjectSnapshot.cpp` регистрирует объектные блоки, а документация `docs/SAVES.md` S-4192 прямо говорит, что клиент не синхронизируется после загрузки; `m_permanentSubObjectOps` в `W3DScriptedModelDraw` не участвует в xfer. По решению владельца это оставляется отдельным остатком S-7404, не маскируется новым simulation snapshot.
* Порт `UpgradeModuleClasses.cpp` вызывает существующий `ObjectClientHooks::showSubObject`, далее `ClientEventRecorder`, `DrawableManager::SHOW_SUB_OBJECT`, `Drawable::showSubObject`, `W3DScriptedModelDraw::setSubObjectHidden`; этот путь в настоящее время несёт только флаги, а не две скорости и промежуточную непрозрачность. Продолжению нужно разобрать обновление записи RW и общий вывод непрозрачности отдельных субобъектов, включая скриптовые запросы и сохранение client state; отдельный путь только для upgrade был бы заплаткой.
