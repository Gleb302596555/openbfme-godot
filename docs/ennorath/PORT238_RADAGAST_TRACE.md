## Directional crow timer: distinct names, same enum

Both templates exist in `includes/specialpower.inc:4978–4996`: `SpecialAbilityRadagastKrhenruf` has 60000 ms reload and `SpecialAbilityRadagastRavens` 120000 ms. They share `SPECIAL_SPELL_BOOK_DRAGON_STRIKE`, but are separately named templates. The eagle→ground list says `Krhenruf`; the eagle's active crow `OCLSpecialPower` says `Ravens` (the alternative after `;;` is commented). Ground→eagle instead lists `Ravens`. The ground ring child has no direct crow override; its parent declares `Ravens`, subject to effective inheritance. Neither literal form declares a `Krhenruf` power module in its own body.

The BFME2 donor `ToggleMountedSpecialAbilityUpdate.cpp` (`rva004ADCE8`) resolves each list name, finds that template's module on each object and copies only if both exist. RW `0x8B12BF` follows that structure (`0x8B12F7` template lookup, `0x8B1307/0x8B1314` interface lookup, `0x8B134D` copy); the special-power predicate `0x8969D1` compares template pointers rather than their common enum. `0x897368` also checks the power identity and source paused/disabled/shared state before copying. Current port's `replaceWithTemplate`, `SpecialPowerModules::findModule` and `SpecialPowerModule::copyTimerFrom` implement this chain; no ring-specific fix is justified solely by the mod's different list names.

`PORT-238 Radagast-style eagle toggle*` uses two synthetic objects with five `SpecialPowerModule`s each, separate Ravens/Krhenruf templates with the same enum and the literal directional names. The source is explicitly unpaused, and synthetic timers are `AvailableAtStart = Yes`. In separate take-off and landing cases, four timers copy both ways; the Ravens ready frame copies on take-off, but is not copied on landing, where the synthetic new timer is at its creation frame. Both objects lack the Krhenruf module. The test passes 72/72 assertions on matching isolated `3f0105c8` core/headers with the separately compiled upstream PORT-286 parser; changing the landing fixture's name to `Ravens` fails 1/72 (fixture sensitivity, **not** a code-fix negative control). It does not load the child or actual OCL modules, demonstrate the original unpause/recharge, or establish that the real landing ability becomes ready: the real new module starts paused, has an upgrade gate, and needs an end-to-end test. The same caveat applies to behavior on current full main, pending its build.
