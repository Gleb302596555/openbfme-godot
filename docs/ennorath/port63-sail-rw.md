# Port 63 / issue #173 — RotWK W3DSailModelDraw: transform vtable and callback

Source: RotWK 2.01 `game.dat` (md5 daed3668006cd90f01c34e5a7da1901f; caveat S-001), inspected with `tools/mod/rw.py ... dis` and PE vtable/offset scans. The BFME2 1.06 decomp is a **donor**, not the source of RotWK behaviour. No game/mod bytes or INI excerpts are included here.

## Reachable class and callback

* Data factory **RW 0x4647CA** allocates `0x194` bytes and calls data ctor **RW 0x4CFF2A**; its `+0x188`, `+0x18C`, `+0x190` are initialized at **RW 0x4CFF35–0x4CFF5B**. The parse table **RW 0xBE3B30** maps `MaxRotationDegrees`, `BlowingThresholdDegrees`, `AboutDamping` to those offsets (the first two through angle parsing). Already parsed by `W3DModelDrawVariants.cpp`.
* Instance factory **RW 0x46478F** allocates `0x2F0` bytes and calls ctor **RW 0x4CFF82**. The ctor writes primary vtable `0xBE3C40` at **RW 0x4CFF95**, sets `+0x2E8 = 0` and clears the valid flag `+0x2EC` (**RW 0x4CFFA9–0x4CFFB1**). Primary vtable slot `+0x104` at `0xBE3D44` contains **RW 0x4D00CD** (checked in the PE, not assigned by code proximity).
* The *shared* scripted-model transform path **RW 0x4B686D** invokes `call [vtable+0x104]` at **RW 0x4B6B21–0x4B6B26** with its assembled matrix. **The dispatch is conditional:** **RW 0x4B6A77–0x4B6A81** branches straight to `0x4B6B2C` when module data `+0x40` (`AttachToBoneInAnotherModule`) is empty; **RW 0x4B6AA2–0x4B6AA4** makes the same skip if that drawable's bone lookup fails. The parent-attached branch can also return at **RW 0x4B6A5B** without this call. On success, RW copies the found bone's 3×4 matrix into `esi` and calls the hook **before** shared interpolation/construction-height (**RW 0x4B6B2C–0x4B6C8D**). DONOR BFME2 **0x000B710D** (`Code/GameEngineDevice/Source/W3DDevice/GameClient/Drawable/Draw/W3DScriptedModelDrawAdjustTransformMtx.cpp`) confirms the guards and order. It is *not* an unconditional call on every model or a per-object sail special case.

## Every primary vtable slot (owner's follow-up)

Read the 68 entries `0xBE3C40..0xBE3D4C` from the PE and compared **each** to the shared scripted-model primary vtable `0xBDFFE8` installed at **RW 0x4C04D1**. Exactly six slots differ; the other **62 slots**, including `+0x014..+0x100` and `+0x108..+0x10C`, point to **identical inherited functions** (not merely code in the same address range):

| slot | base | sail | instruction/role |
|---|---|---|---|
| `+0x000` | `0x4C7D11` | **RW 0x4D00AC** | deleting destructor; tail jumps at **RW 0x4D00C8** |
| `+0x004` | `0x4B32FD` | **RW 0x4CA6F0** | jump to same inherited name-key function, no data read |
| `+0x008` | `0x4C0911` | **RW 0x4D0003** | class-name literal getter |
| `+0x00C` | `0x4C52FE` | **RW 0x4D0009** | base xfer then last angle and valid flag, not module data |
| `+0x010` | `0x4C08CC` | **RW 0x4CFFBE** | module-name key cache |
| `+0x104` | `0x9F3A3C` | **RW 0x4D00CD** | base `ret 4` at **RW 0x9F3A3C**; sail matrix turn below |

The derived implementations above contain **no read of Sail data `+0x18C`**. Inherited slots address the base scripted-model fields (the base module data ends before the sail-only offsets), and are byte-for-byte the same targets as for a non-sail draw. A displacement scan of the surrounding `.text` also distinguishes two misleading `+0x18C` hits: **RW 0x4B1BA7** is a one-byte getter on a *draw object*, not on its module data; **RW 0x4B4AA5** explicitly loads `ecx` from global `0xDE3D84` before reading that byte (global game data). Other hits near the sail class belong to other variant data constructors; the sail data ctor **RW 0x4CFF45** *writes*, not reads, `+0x18C`. DONOR BFME2 **0x000D08C3** (`Code/GameEngineDevice/Source/W3DDevice/GameClient/Drawable/Draw/W3DSailModelDrawCtor.cpp`) and the `W3DSailModelDraw.cpp` parse/ctor provide no other reader. Thus, after the full slot audit, `BlowingThresholdDegrees` is **parsed-unused** in RotWK 2.01. This is a negative conclusion about this reachable class and its inherited slots, not about a missing string search.

## Callback branches, RW 0x4D00CD–0x4D033B

* **RW 0x4D00D1–0x4D0119:** one lazily initialized direction is set to `(0.5, 0.5, 0)` and normalized by **RW 0x405553**. The callback takes only a matrix argument. No weather/global wind is read here: the direction is fixed, not a caller-supplied wind vector. DONOR BFME2 **0x000D08C3** (`Code/GameEngineDevice/Source/W3DDevice/GameClient/Drawable/Draw/W3DSailModelDrawCtor.cpp`) names the direction and the matrix-column arithmetic.
* **RW 0x4D0123–0x4D01B5:** dot the normalized direction with the input transform's X and Y columns; clamp the X dot to `[-1,1]` (branches **0x4D0184–0x4D01B5**). **RW 0x4D01B5–0x4D01D1** computes `normalizeAngle(acos(Xdot))` (angle normalization is **RW 0x644FD0**).
* **RW 0x4D01D4–0x4D01EA:** if the angle exceeds data `+0x188` (`MaxRotationDegrees`), cap it. **RW 0x4D01EF–0x4D020B:** if the Y dot is negative, negate and normalize the angle; otherwise keep it.
* **RW 0x4D020C–0x4D0265:** if valid flag `+0x2EC` is false, use the target immediately. Otherwise compare the absolute difference from saved `+0x2E8` to data `+0x190` (`AboutDamping`); if larger, move from the saved angle toward the target by exactly that amount (**RW 0x4D0238–0x4D0260**). This is a per-call angle step, not time-scaled damping and not a sine/threshold check.
* **RW 0x4D0265–0x4D0330:** write the angle to `+0x2E8`, apply a Z rotation to each of the three matrix basis rows (sine/cosine), then set valid flag `+0x2EC`. **RW 0x4D0009–0x4D004E** xfers the base draw and these two runtime fields via the virtual xfer primitives. DONOR BFME2 **0x000D0816** (`Code/GameEngineDevice/Source/W3DDevice/GameClient/Drawable/Draw/W3DModelDrawBfmeXfers.cpp`) also saves the angle and flag.

`BlowingThresholdDegrees` is parsed and initialized at data `+0x18C`, but **the entire derived callback and the other SailModelDraw instance routines (RW 0x4CFF82–0x4D033B) have no read from data `+0x18C`**. In particular, **RW 0x4D0228 reads `+0x190` (`AboutDamping`)**, not `+0x18C`; the earlier triage's description of a sine/threshold comparison is not supported by the instructions. A disassembly scan (including one-byte displacements) and DONOR BFME2 **0x000D08C3** find no threshold gate in the sail callback. Therefore a test saying “below BlowingThresholdDegrees the sail does not turn” would contradict the demonstrated RotWK callback; do not invent it.

## Port integration on top of Local 29 (issue #218, main 2753b687)

`W3DModelDraw.cpp/.h` hold *module data*; `W3DScriptedModelDraw` is the client runtime base. Local 29 now owns the **only** runtime-base vslot `adjustAttachedTransform(Matrix3D &)`: a no-op like RW 0x9F3A3C. `Drawable::boneTransform` finds another module's bone in its current pose, and `Drawable::entryTransform` replaces the matrix and calls this slot **only on a successful lookup**, as RW 0x4B6A77 / 0x4B6AA2 / 0x4B6B26 do. PORT-63 adds only the separate `W3DSailModelDraw` override (RW 0x4D00CD..0x4D033B): fixed wind, `MaxRotationDegrees`, initial angle without damping, subsequent per-draw `AboutDamping`, and the independent angle/valid flag. The factory in `GameClient/Drawable.cpp` selects it from typed module data. No `adjustModelMatrix`, `W3DModelDrawMatrix.h`, unconditional dispatch, or sail-only dirty flag remains.

`GodotGameWorld::refresh_view` and `GodotPlacementGhost::drawIcon` use Local 29's `Drawable::entryTransform` for every module. For a live attached sail, `GameWorld` compares the new result with `ev.lastEntryXf` on each draw frame: a damping step on a stationary ship changes that matrix and the instancer receives it without a special dirty flag. The generic and truck runtimes use the inherited no-op slot. The two sails in Ennorath `corsairship.ini` attach to `SAIL_BONE01` and `SAIL_BONE02` on the ship's parent draw; `EvilShip_Interface` and `GondorShip_Interface` are the owner check in the game. The expected movement is smooth, not more than `MaxRotationDegrees`, and stays on the mast.

`MapObjectRuntime` still chooses the sail runtime for a map-placed model, but `GodotMapObjectBuilder` has **no** cross-module bone placement (Local 29 is for live drawables/ghosts), so it does not call the slot there: **на объектах, поставленных на карту, модули не встают на кость, и парус не поворачивается**. This remains S-7232, not a new unconditional or sail-specific hook. No simulation state, simulation snapshot, hash or logic RNG changed.

`engine/tests/test_port_63.cpp` uses a synthetic hull with `SAIL_BONE01` at a nonzero offset and a separately owned sail module. The explicit two-module fixture gives the hull and the sail **different Harness instances**, preserving both parsed data lifetimes; the other integration cases use ThingTemplate nuggets, each with independently owned typed module data. The tests exercise the live drawable's *single* entryTransform dispatch: attached narrow/wide sails, fixed wind, limit, undamped first call, subsequent damping and independent instances; an unattached/missing-bone sail does not turn; the adjacent generic and truck draws keep the bone matrix/pose. A map-object test checks the factory and reports S-7232 without calling the sail slot on the unplaced model. No test uses retail game or mod bytes. The former direct post-attachment callback test and its build-directory mutation are from r1 and do not establish the new gate. **r2 checks:** `PORT-63*` 6/6 and 245/245 assertions; each of the six new tests passed 15 consecutive invocations (90/90 runs, 3675/3675 assertions). `LOCAL-29*` 5/5 (59), `LOCAL-28*` 8/8 (119), `mapobj*` 35/35 (916); three retail-only mapobj tests print SKIP without retail paths, as does `play1 placement ghost*` (1/1, zero assertions). The three Godot renderer TUs compile with Godot 4.7 bindings; the complete extension was not linked and no retail scene/Ennorath installation is available for a visual owner check.

**Remaining S-7232:** RW's *client draw* xfer at 0x4D0009..0x4D004E saves +0x2E8/+0x2EC, but this port has no client-draw snapshot path, so visual damping history restarts after loading; the rule for simulation fields does not apply. The map-placed object path lacks bone placement as above. A parent module with `NoRotate` may give a different bone transform (Local 29 INFERENCE); no such parent/sail pair is known in Ennorath 1.9.8.2. A full Godot-enabled link and owner visual check have not been demonstrated; only the affected renderer translation units have compiled.
