# Port 219: анализ источников карты

Первые разделы ниже сохраняют журнал предварительных экспериментов; итог,
результаты реального прогона и шесть ручных проверок — в конце файла. Цель —
граф от виртуальных функций **модулей**, а не ModuleData. `module-registry.json` строится через `data_vtable` и его поле
`vtable` нельзя считать адресом таблицы модуля. Проверено на retail RotWK 2.01
(md5 `daed3668006cd90f01c34e5a7da1901f`):

| Класс | create: инструкция вызова | конструктор | запись основной vtable | vtable из реестра (данные) |
|---|---|---|---|---|
| AIGateUpdate | RW 0x64F7ED | RW 0x8B49F5 | RW 0x8B4A19 → 0xC6D070 | 0xC07A30 |
| FireWeaponUpdate | RW 0x64CC1E | RW 0x88F731 | RW 0x88F75C → 0xC629C8 | 0xC62940 |
| LifetimeUpdate | RW 0x64E07A | RW 0x7A7EE6 | RW 0x7A7F13 → 0xC317AC | 0xC07A30 |
| GiveUpgradeUpdate | RW 0x64E4D7 | RW 0x89FB2F | RW 0x89FB42 → 0xC67B58 | 0xC67BB8 |

У всех четырёх create после выделения вызывает указанный конструктор при
ненулевом результате выделения. Инструкции перечитаны `tools/mod/rw.py dis`.
Конструкторы также записывают дополнительные интерфейсные таблицы (например,
RW 0x8B4A26 и RW 0x89FB4F/0x89FB56), поэтому одной основной таблицы мало.
Границу таблицы нельзя выбирать фиксированным числом слотов: после первых
трёх основных таблиц по смещению +0x34 встречаются данные, а у четвёртой по
этому смещению находится указатель кода. Метод выделения таблиц и сравнение с
правильными базовыми классами ещё предстоит доказать.

Первый код — только синтетически проверяемые примитивы анализа: не строит
реальный реестр/граф, не формирует выходные отчёты и не доказывает полноту.
Пустая `workspace/rebuild/xmap/rw_map.csv` в песочнице отсутствует, поэтому
поле decomp при реальном запуске должно быть пустым. `TurretAI` не найден как
точное имя в реестре: соответствие имени модуля нужно отдельно выяснить, не
подставляя догадку.

## Проверка всего реестра (предварительная)

На том же бинарнике алгоритм `tools/rw_object_model/update_phases.py`
нашёл конструктор и запись таблицы по смещению 0 для всех 329 записей
`module-registry.json` (0 нерешённых). Это автоматическая эвристика по
инструкциям, не доказательство корректности каждой таблицы и не определение
границ её слотов. Синтетический тест требует явной ошибки при отсутствии
конструктора или основной таблицы; поле ModuleData не используется как таблица
модуля.

Для первых трёх классов конструктор вызывает RW 0x653114 (например, вызов
RW 0x8B4A00), который устанавливает основную таблицу 0xC062E4 и интерфейсную
0xC8746C (RW 0x653137 и 0x653144). У GiveUpgradeUpdate вызов RW 0x89FB3A
ведёт в RW 0x851D42, где устанавливаются 0xC563D0, 0xC769EC и 0xC64658
(RW 0x851D6D, 0x851D7A, 0x851D81); сам этот конструктор вызывает
RW 0x653114 по адресу RW 0x851D5A. Базы и границы всех остальных таблиц ещё
не подтверждены. Архив аудита от 2026-11-14 основан на Ennorath **1.9.8.2**;
его `module-coverage.tsv` — таблица реестра порта, а не счётчик объектов
1.9.8.3. Для итогового ранжирования нужны данные актуального INI-архива.

## Предварительная проверка входа 1.9.8.3

Архив `ennorath-ini-1.9.8.3.zip` с MD5
`c53b6dea885cab044f80e783565f41f3` содержит 1593 пути в `data/ini/`.
Опытный адаптер Zip к `ennorath_graph.load_db` за 6,88 с прочитал 31306
определений, включая 8186 объектов, и не сообщил пропущенных `#include`.
Простое объединение имён модулей через `effective_fields` дало 258 имён.
Эти числа — диагностика адаптера, **не** подтверждённые счётчики для отчёта:
нужно отдельно проверить удаление и замену унаследованных модулей и учёт только
верхнеуровневых объявлений. Скрипт адаптера пока не включён в инструмент.

## Проверка границ модулей (незавершённая)

RW `0x8B618C` различает однострочный `AddEmotion` и `AddEmotion = OVERRIDE ...`,
у которого отдельный блок до `End` (см. `parseAddEmotion`, вызов чтения
`0x8E0D47`). Синтетический тест включает пустой блок OVERRIDE и соседние
однострочные записи. Эксперимент с INI 1.9.8.3 сравнил 8971 предположительный
заголовок с границами разбора; после исправления осталось 8 расхождений по
наивному критерию. Часть — ложные заголовки (`CommandSet` без `=` внутри
объекта), другие — определения типов, которых нет в `BLOCK_TYPES`, или
посторонние строки между определениями. Это не доказательство корректного
inventory: требуется явно обработать область верхнего уровня и порядок загрузки,
а не считать такое сравнение валидацией реального числа объектов. Сырые строки
и файлы мода в репозиторий не включаются.

## Проверка наследования на архиве (эксперимент)

Чтение `data/ini/default/object.ini` перед каталогом Object принципиально:
без default диагностика не могла воспроизвести 42 определения с заменой
унаследованного тега. При предварительном лексическом порядке, после включения
default, из 8919 найденных заголовков 8914 уникальных объектов воспроизведены
без исключений, ещё пять — повторные определения, которые в эксперименте
пропускались. В коде повторный `Object` теперь разбирается в существующий
шаблон при обычном типе загрузки (RW `0x6D29...`, см. ThingFactory). Числа не
являются финальным inventory: нужны повторный прогон с обработкой повторов,
проверка полноты перечня файлов и границ верхнего уровня.

Независимый inventory функций и доказанные границы таблиц ещё отсутствуют.
`tools/re/inventory.py` использует список Ghidra и требует локального GhidraMCP;
его результаты отсутствуют в текущем workspace. Примитив `decode_inventory`
не подменяет это предположительным линейным сканированием и не выдаёт полный
отчёт. Примитив сравнения слотов также требует уже подтверждённые родительские
таблицы и их реальные размеры. Число статусов карты и шесть ручных проверок
пока отсутствуют.

## Повторяемый INI inventory

`inventory_from_ini` читает ZIP без извлечения игровых файлов, разрешает include,
применяет default, ChildObject/ObjectReskin и повторные Object. Синтетический
тест проверяет совместно default, относительный include, повторное определение
и удаление унаследованного тега. Прогон на архиве с указанным выше MD5:
8919 объявлений, 8914 уникальных шаблонов, 255 классов модулей, 7,91 с;
ошибок include и replay нет. Пять повторов теперь применены, а не пропущены.
Это счётчики парсера, не завершённая карта функций: порядок каталогов и
полноту распознавания верхнего уровня ещё необходимо независимо проверить.

Загрузка Ghidra 12.2 и Temurin 21 через `gh release download` недоступна:
redirect на `release-assets.githubusercontent.com` заканчивается EOF. Проверяется
альтернативный независимый анализатор angr из PyPI, без внесения зависимостей
или игровых данных в Git.

## Раздельные тела функций

Добавлен `decode_block_inventory` для внешнего CFG: список блоков не заменяется
интервалом до следующей функции. Промежутки (включая jump tables) не декодируются;
оборванная инструкция — ошибка. Общие хвосты допускаются, но частота вызовов
считается по уникальным физическим call-site, а не умножается на число владельцев
общего блока. Два новых синтетических теста; всего 18 passed.

angr 9.2.213 удалось запустить после фиксации локальных зависимостей
`bitstring==4.4.0`, `pycparser==3.0` (версии по умолчанию несовместимы с ним).
CFGFast запущен без библиотек, с нормализацией блоков, разрешением indirect jumps
и factory-адресами registry в качестве дополнительных entry points. До его
окончания нельзя приводить число найденных функций или статусы как результат.

## Итоговый независимый inventory и реальный прогон

Внешний CFG восстановлен один раз и сохранён только в игнорируемом
`workspace/rebuild/rw_function_blocks.json` (адреса и размеры basic blocks,
без игровых байтов). `angr 9.2.213` / CFGFast запущен с 3727 начальными
точками: factory `create` / `createData`, все уникальные override-слоты и
обнаружение tail calls; symbol/prologue/full scan, data references и разрешение
indirect jumps отключены. Анализ занял 69,84 с, дал 11861 функцию, 0 потерянных
seeds. На всём полученном графе `decode_block_inventory` не нашёл усечённых
инструкций, а `verify_direct_calls` — ни одного прямого вызова внутри `.text`
без собственной функции. Это независимый статический inventory, а не
доказательство полноты непрямых переходов.

`recover_module_layouts` по create → constructor → запись vtable в `this`
восстановил таблицы всех 329 классов реестра: 4253 override-слота, 3099
уникальных адресов. Для 255 классов, найденных в INI 1.9.8.3, это 3430
override-строк и 2551 уникальный адрес. Поле `vtable` реестра у этих классов —
**ModuleData-таблица**, а не искомая таблица модуля; правки в реестр не
вносились, реальные таблицы перечислены в `RW_FUNCTION_MAP.md`. Исключение
`GateOpenAndCloseBehavior` (вторичный UpdateModule по смещению +4) проверено
по RW `0x89C068` / `0x89C06E`.

**INFERENCE:** границы таблиц оканчиваются на другой известной
установленной в конструкторе таблице либо на первом не-кодовом указателе;
неиспользуемые соседние таблицы могут объединиться. Вызов базы принимается
только при `ecx == this` до записи производной таблицы. Порядок путей INI —
лексический, после default/object.ini; порядок перечисления retail-каталога и
полнота верхнего уровня не доказаны независимо. Разрешение виртуальных и
регистровых непрямых вызовов в задаче не выполняется.

Реальная команда (розничные файлы остаются вне Git; в отчёте та же команда записана portable `python ...`, без абсолютного пути интерпретатора):

```sh
.venv/bin/python tools/mod/rw_function_map.py \
  --game workspace/RotWK/game.dat \
  --ini /tmp/ennorath-ini-1.9.8.3.zip \
  --src engine/src \
  --inventory workspace/rebuild/rw_function_blocks.json \
  --threshold 200 \
  --out docs/ennorath/RW_FUNCTION_MAP
```

Вход: `game.dat` md5 `daed3668006cd90f01c34e5a7da1901f`, архив INI md5
`c53b6dea885cab044f80e783565f41f3`. Два последовательных прогона: 52638 строк
(пар module/function), 11861 функций, 26451 `ported`, 831 `partial`, 25356
`none`; 12,21 с и 12,26 с. Оба вывода имеют одинаковые SHA256:
TSV `5a87c38d…`, MD `28fc7279…`; второй печатает `0 rows moved from none/partial to
ported`. Inventory INI: 8919 объявлений, 8914 уникальных шаблонов, 255 классов.
Опубликованы 20 ручных стопов и 13 частотных (>200 физических call sites);
максимум — RW `0xA3CEF0` (2255). `workspace/rebuild/xmap/rw_map.csv`
отсутствует, поэтому столбец `decomp` пуст: BFME2/DONOR здесь не использовался.
Перед PR ветка перебазирована на `origin/main` `976b2710`; реальные новые RW
цитаты main дали шесть переходов при первом повторном прогоне:

Синтетический «порт-батч» с добавленной цитатой RW `0x8B4983` во временном

## Ограничения итогового отчёта

`ported`, `partial`, `none` строятся по **точному начальному адресу функции** в
цитатах `engine/src`. Цитата внутри функции, реализация под другим адресом,
inline, thunk или непомеченная target-facts ссылка дают ложные статусы; цитируемые
соседи — только подсказка. `partial` назначается, если на строке цитаты или
следующей строке есть `S-<id>`, `NOT PORTED` / `not ported` / `INFERENCE`.
Новая стопа для движка не заводилась: ветка меняет только инструмент и отчёт,
`engine/`, registry, чужие тесты и пины не тронуты. Сборка движка и doctest не
требовались задачей и не запускались; строка NIGHT_WATCH добавлена отдельным
фрагментом.
