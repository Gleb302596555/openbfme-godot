# PORT-238: Saruman ring forms and PLAYER choice (partial trace)

Literal declarations come from the locally extracted Ennorath 1.9.8.3 INI archive (MD5 `c53b6dea885cab044f80e783565f41f3`), with paths relative to `data/ini`. Main reports the principal INI unchanged through 1.9.8.5; this archive has not been independently compared to the current installation. This is **not** an effective-load, complete object/ability inventory, real-game or visual audit.

## Delivery and branching

Both `IsengardSaruman_Mod` (`object/evilfaction/units/isengard/saruman.ini:1`) and the separate `IsengardSarumanKorrumpierte` (`:1701`) declare ring-entry contains (`:1283–1302`, `:2957–2976`) with `HOLDING_THE_RING`, destruction of `TheDroppedRing`, and OBJECT `Upgrade_RingHero Upgrade_FortressRingHero`. `_gamedata.inc:31` excludes these two named objects from automatic carrier attachment, but that does not exclude a different carrier delivering the ring.

For both objects, the unpause and `DoCommandUpgrade` for cursed form use `Upgrade_RingHero`; that command has `ConflictsWith = Upgrade_SarumanVielfarbig` (`:1110–1137`, `:2809–2836`). The blessed branch requires **both** `Upgrade_RingHero` and `Upgrade_SarumanVielfarbig` (`:1140–1168`, `:2839–2867`). The latter is a **PLAYER** upgrade (`includes/upgrade.inc:509–512`), unlike Arvedui's OBJECT protection. Their toggles target `IsengardSarumanVerfluchter` and `IsengardSarumanGesegneter` and list thirteen named synchronized timers. In both source blocks the older toggle directly to `IsengardSarumanRing` is commented; do not treat that comment as a live transformation.

`IsengardSarumanRing` is nonetheless a separate declared object with `BuildVariations = IsengardSarumanVerfluchter IsengardSarumanGesegneter` (`:3084–3126`), and `IsengardSarumanRing_RingHero` is its child (`:3128`). Those declarations are not the same thing as the live base toggle; construction/build-variation paths and inheritance still need investigation. A `HaldirStufe3Ping` declares a `GrantUpgradeCreate` for the PLAYER upgrade (`object/projectile.ini:19001–19035`), but that alone does not prove its reachability, ownership or that it is the only producer.

Cursed form has a further `DoCommandUpgrade` on the PLAYER upgrade to the blessed toggle (`saruman.ini:4150–4175`); its corresponding starter is `StartsPaused = Yes` and that block has no direct matching unpause. This is **not** sufficient to conclude the automatic transition is blocked. RW `0x8B8E2E -> 0x696FD2` dispatches the command, the SPECIAL_POWER case ORs `0x40000` at `0x6971DD` and calls `0x68E5A3`; `0x7B1D79` still checks the special-power requirements/filter, while `0x8980A6..0x8980C7` skips the power module's pause/disabled gate for that option. The BFME2 donor `DoCommandUpgrade.cpp` and `ToggleMountedSpecialAbilityUpdate.cpp` supply the related command and replacement structure. Other disabled-object checks and actual reachability are separate; this generic disassembly is not a capture of a mod run.

`PORT-238 Saruman-style player flag selects ring replacement` uses synthetic data. With no flag, ring delivery selects the synthetic cursed form; with PLAYER flag granted before delivery, it selects blessed. With flag granted after the synthetic cursed replacement completes, the synthetic cursed starter remains paused but the auto-command starts its toggle and reaches blessed. It also checks the `DoCommandUpgrade` executed flags, both delivered upgrades, ring destruction and owner. Three subcases pass **110/110 assertions**; the complete isolated `PORT-238*` suite is **30/30, 1927/1927**, on matching `3f0105c8` core/headers and the separately compiled upstream PORT-286 parser, not current-main full executable. Removing `ConflictsWith` only in the fixture makes the cursed-command-executed check fail (**109/110**); before that execution check was added, the same control still produced the blessed final form and passed, so final form alone was insufficient to detect both commands being issued. This is a fixture sensitivity control, not an engine-fix control.

The synthetic test uses direct PLAYER grants, synthetic power enums, no thirteen-timer check and no actual purchase, spellbook or mod files. It does not cover a flag arriving during an active transition, failure/requirements filters, network/save, tower path, death or HUD. S-7321, S-7446 and S-861 remain.
