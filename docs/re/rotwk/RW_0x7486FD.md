# RW 0x7486FD — the generic attack machine's condition records (S-325, port issue 437)

Source: supplied RotWK 2.01 `game.dat`, MD5 `daed3668006cd90f01c34e5a7da1901f` (caveat S-001). Every instruction address below was read with
`tools/mod/rw.py ... dis` against that file; the BFME2 1.06 decompile is a donor and is labelled `DONOR BFME2` wherever it is cited. No retail
or mod bytes are reproduced: only addresses, instruction excerpts and the shape of the tables.

This is the map the port follows for the object conditions of the generic attack machine (stop S-325, "the B1 conditions to Pursue").

## 1. The constructor chain

| fact | address |
|---|---|
| `AIAttackState` builds its inner machine through its own virtual | RW 0x74CD94 … |
| the generic machine: `AttackStateMachine` ctor (owner, attackState, name, follow, attackingObject, forceAttacking) | **RW 0x7486FD**, called from RW 0x74CD78 for `AIAttackState` |
| shared `StateMachine` base ctor (owner, name) | RW 0x8DBD03; its own base RW 0x9A2931 |
| `defineState(id, state, successId, failureId, conditions)` | RW 0x8DBE1D (ret 0x14) |
| a `StateConditionInfo` is 12 bytes: `{test, toId, userData}`, a null `test` ends the list | RW 0x8DB4DB (stores the count) / RW 0x8DB4FC (evaluates) |

`defineState`'s argument order at the call sites (RW 0x8DBE1D under `__thiscall`): `push conditions; push failureId; push successId; push state; push id`.

## 2. The six states, their transitions and their tables

| state | ctor | success | failure | condition table |
|---|---|---|---|---|
| Aim 0x66 (`AIAttackAimAtTargetState`) | RW 0x740D6C | Fire 0x67 (RW 0x7487A4) | 0x270F (RW 0x74879E, `esi = 0x270F` at RW 0x4879E) | `[ebp+0x1C]` — the chosen table (RW 0x74879D) |
| Fire 0x67 (`AIAttackFireWeaponState`) | RW 0x740E39 (takes the `NotifyWeaponFiredInterface` at +0x20) | Wait 0x68 (RW 0x7487FC) | Chase/Pursue 0x64 (RW 0x7487FA) | `[ebp+0x10]` — the chosen table (RW 0x7487F5) |
| Wait 0x68 (`AIWaitUntilFinishedFiringState`) | RW 0x740DF3 | Aim 0x66 (RW 0x74882A) | 0x270F | `[esi]` = 0x270F-the-failure? no: RW 0x748828 pushes `ebx`=0 for the table (none) and 0x270F for the failure id → **no conditions** |
| Chase 0x64, immobile owner: `AIAttackApproachTargetState` | RW 0x740C39-derived, RW 0x744310 with (follow=0, attackingObject=0) | 0x270F | 0x270F | RW 0xC29D80 (RW 0x748773 / 0x7487C0 when follow is 0) |

| Approach 0x65 (`AIAttackApproachTargetState`, vtable RW 0xC28C70) | RW 0x744310 | Aim 0x66 (RW 0x748941) | 0x270F (RW 0x748940 pushes `esi`=0x270F) | none (`ebx`=0, RW 0x748940) |

Branches of the constructor (RW 0x74873C onward):

* RW 0x74873C: `owner->testStatus(0x26)` (the object status tested by RW 0x44DDEC) and, at RW 0x748749, the AI's turret for the current weapon
  (RW 0x66243F: walks `AI + 0x20C`, one entry, answers the index or -1) pick the table:
  * no status 0x26 → `forceAttacking ? 0xC29E04 : 0xC29DD4` (RW 0x74872C / 0x748735);
  * status 0x26, no turret → RW 0xC29DBC;
  * status 0x26 and a turret → RW 0xC29D98.
* RW 0x74876B: `follow` false forces the Chase table to RW 0xC29D80 (RW 0x748773).
* RW 0x748839: `owner->isKindOf`/template bits RW 0x108 bit 2 (immobile, RW 0x748846), else RW 0x10F bit 2 and RW 0x108 bit 3 (portable structure
  that can attack, RW 0x48853 / RW 0x48855) choose the stub chase RW 0x8DB860 with the one-entry table RW 0xC29D68 (RW 0x4887D).
* RW 0x748887: otherwise, `follow` (RW 0x748887) picks Pursue 0x64 (`AIAttackPursueTargetState`, RW 0x744401) from RW 0x7488AB; when `follow` is
  false, Chase is Approach (`AIAttackApproachTargetState` with attackingObject = 0, RW 0x748909) from RW 0x748909. Approach 0x65 is defined in both
  branches (RW 0x7488E5 with the attackingObject / forceAttacking pair, RW 0x74893E with the follow branch's Approach).

## 3. The condition records (`.rdata`; these are data addresses, not code)

Each record is `{test, toId, userData}`, 12 bytes; a record with a null test ends a table.

| table | record 1 | record 2 | record 3 |
|---|---|---|---|
| **0xC29DD4** (mobile, not forced) | `0x7457DF` → 0x64, ud 0 | `0x745901` → 0x64, ud 0 | `0x741798` → 0x270F, ud 2 |
| **0xC29E04** (mobile, forced) | `0x7457DF` → 0x64, ud 0 | `0x741798` → 0x270F, ud 3 | `0x745901` → 0x64, ud 0 |
| **0xC29DBC** (status 0x26, no turret) | `0x741798` → 0x270F, ud 2 | end | |
| **0xC29D98** (status 0x26 + turret) | `0x7457DF` → 0x270F, ud 2 | `0x741798` → 0x270F, ud 2 | end |
| **0xC29D68** (portable-structure chase) | `0x7458EC` → 0x66, ud 0 | end | |
| **0xC29D80** (follow = 0 / immobile chase) | `0x741745` → 0x64, ud 0 | end | |

Three predicates are involved, and one of them (`0x741798`) is already ported as `cannotPossiblyAttackObject` (lane SPELL-3):

* **RW 0x7457DF — "the victim is out of weapon reach, walk to it"** (the port's name; donor `outOfWeaponRangeObject`). Reads the machine owner
  (`state->machine + 0x14`) and the goal object (RW 0x8DBACE). `no owner` → **true** (RW 0x745802); `no goal` → true (RW 0x74580B → RW 0x7458E5);
  the owner's AI container `+ 0x27C` and the current weapon's substitutes (RW 0x745812 … 0x745876) only set a "cannot be blocked by the view" flag.
  Then: the current weapon is not a contact/melee weapon (RW 0x9188EB / RW 0x441B59 both false, RW 0x745876), the victim is not significantly above
  the terrain (RW 0x70C55D, RW 0x745894), and the attack-path view (RW 0x6F4557, RW 0x7458A2 call inside RW 0x744AAA) — when the view is blocked,
  true (RW 0x7458C1). Finally the weapon's own test `Weapon::isWithinAttackRange` (RW 0x6CC622 at RW 0x7458D8: extra 0, min range checked,
  RW 0x7458D0) — in reach → **false**, out of reach → **true**.
* **RW 0x745901 — "the victim can be crushed instead"** (the port's name; donor `wantToSquishTarget`). All of: the owner's template
  `+ 0x60D` (UseCrushAttack, RW 0x74591C), the goal has no AI container (`+ 0x27C` == 0, RW 0x745928), the owner's AI turret for the current
  weapon is **invalid** (RW 0x745931 → RW 0x66243F == -1, RW 0x745940), `TheAI->AIData + 0x8C` AICrushesInfantry set (RW 0x745945), the owner's
  locomotor exists and its `+ 0x5C` == 1 (RW 0x745956 → RW 0x68B678, RW 0x745968), `owner->canCrushOrSquish(goal)` with policy 2
  (RW 0x69519A, RW 0x745973) and the owner's template `+ 0x113` bit 0x10 clear (RW 0x74597C). True → the machine goes to Chase 0x64.
* **RW 0x741798 — "cannot possibly attack"**: already ported (see `AIAttack.cpp`); the tables above give it its real `userData` (2 or 3) and
  one more target (Aim **and** Fire, plus the status-0x26 tables) — ported already for Aim/Fire.
* **RW 0x7458EC — "in reach from where I stand"** (donor `inWeaponRangeObject`): `!RW 0x7457DF`, i.e. true when the victim **is** in reach; sends
  the portable-structure chase to Aim 0x66.
* **RW 0x741745 — "out of reach for a chase that cannot move"** (donor `outOfWeaponRangePosition`): a goal object → `!RW 0x6CC622`-based test via
  RW 0x741745 (the same `Weapon::isWithinAttackRange` with extra 0 and min range), a goal position → RW 0x74177E false. True → Chase 0x64.

## 4. The Pursue state (0x64), `AIAttackPursueTargetState`

* vtable RW 0xC28D90; slot 0x18 (update) RW **0x74AF91**, slot 0x1C (updateInternal) RW **0x74AD8E**; onEnter RW 0x744451, ctor RW 0x744401
  (+0x4C..0x58 zeroed, +0x5C follow, +0x5D attackingObject, +0x5E cleared, +0x5F = 1 "initial approach", +0x60 forceAttacking).
* RW 0x74AF91: `updateInternal()`; when the flag `+0x5F` still stands (first frame), the AI's turret for the current weapon (RW 0x66243F) is valid
  and `AI::getNextMoodTarget` (RW 0x66844A) answers an object, it is aimed at the turret (RW 0x6622C7) and `AI + 0x3C7` is set (RW 0x74AFDE).
* RW 0x74AD8E `updateInternal`: the machine's goal object destroyed (RW 0x8DBDFF) → `AI->notifyVictimIsDead` (AI vslot 0x240) and
  `setCurrentVictim(0)` (RW 0x6682B1), FAILURE (-2). Then for a goal object: status 0x33 (RW 0x44DDEC) → FAILURE; stealth (RW 0x694C0D, the
  owner's locomotor, RW 0x68B678) → FAILURE; `setCurrentVictim(victim)` (RW 0x6682B1); the state's virtual slot 0x44 (RW 0x74AE40); the AI's
  `getWhichTurretForCurWeapon`-like slot 0x224; then the walk decision: the current weapon (RW 0x68B58C), the turret index (RW 0x66243F), the AI's
  `+0x224` "can move" test; for a turreted or view-blocked owner (RW 0x6F4557 at RW 0x74AEA9) the machine falls through to RW 0x74AF77; else the
  goal object's AI container `+ 0x264` (RW 0x74AEB6) and the weapon reach (RW 0x6CC653, RW 0x74AED0) decide: in reach → aim the turret
  (RW 0x6622C7) and clear `+0x5F` (RW 0x74AEEF), then the approach's own path (RW 0x68B34C distance, RW 0x6CC07C with `* 0.9` of RW 0xBDAD74 when
  in reach, RW 0x69519A crush policy → the distance constant RW 0xC27440) is requested through the mover (RW 0x6625DA) and the locomotor
  (AI + 0x1F0, RW 0x5E36F7).

INFERENCE: the port does not have `AIAttackPursueTargetState` as a class; the port's `AIAttackApproachState` already walks to the victim with the
attack path (RW 0x749A3E), re-paths it when the victim moves, fails on a dead victim and succeeds on reaching weapon range. The pursue state's
own `updateInternal` (RW 0x74AD8E) is that same walk plus the crush check and the turret aim, so the port keeps the Approach state as the chase
and only has to add the conditions; see the PR for the exact subset.

## 5. What the port already does, and where it departs

* `AIAttackState::makeGenericAttackMachine` (`engine/src/GameLogic/AI/AIAttack.cpp`) defines Aim/Fire with only `cannotPossiblyAttackObject`;
  the chase is a `PursueStub` (immediate success) and the state ids come from B1. No Chase/Fire/Pursue conditions from the tables above exist.
* `AIAttackAimState::update` re-paths to Approach when the victim leaves the weapon's reach — a stand-in the file itself marks as the missing
  RW 0x7457DF.
* `AIAttackApproachState::inRange` is `ObjectWeapons::isWithinAttackRange` (RW 0x6CC653), which is exactly the tail of RW 0x7457DF.

## 6. Not ported after this task

* The turret variants of the tables (RW 0xC29D98 / RW 0xC29DBC, status 0x26): the port's turret machine keeps its own transitions (GARRISON-2).
* The portable-structure chase stub (RW 0x8DB860, table RW 0xC29D68): the condition RW 0x7458EC ("in reach") is portable, but its state is a
  no-op stub whose only effect is the transition to Aim, which the Approach state already reaches; recorded as a stop, not implemented.
* `AIAttackPursueTargetState` itself (RW 0x744401 / 0x74AD8E / 0x74AF91), its turret aim and `AI + 0x3C7`, and the crush chase's distance
  constants (RW 0xC27440, the 0.9 factor RW 0xBDAD74): stop, the port walks through the Approach state.

## 7. Second reading: the exact record bytes and the remaining call sites

The tables, read as dwords starting at the records PORT-154 named (RW 0xC29DD4 / RW 0xC29E04 are the **first record of each table**; the dump
`inc ebp / pop ss` earlier was a disassembly of data, not code — every pointer below is a table entry):

| table | dwords (test, toId, userData) |
|---|---|
| 0xC29D80 | 0x741745, 0x64, 0 |
| 0xC29D98 | 0x7457DF, 0x270F, 2; 0x741798, 0x270F, 2 |
| 0xC29DBC | 0x741798, 0x270F, 2 |
| 0xC29DD4 | 0x7457DF, 0x64, 0; 0x745901, 0x64, 0; 0x741798, 0x270F, 2 |
| 0xC29E04 | 0x7457DF, 0x64, 0; 0x741798, 0x270F, 3; 0x745901, 0x64, 0 |
| 0xC29D68 | 0x7458EC, 0x66, 0 |

`RW 0x745901` (wantToSquishTarget) gates, in instruction order: template +0x60D (RW 0x74591C), goal +0x27C == 0 (RW 0x745928), the AI's turret for
the current weapon **is TURRET_INVALID** (RW 0x745931 -> RW 0x66243F; `cmp eax,-1` at RW 0x745940), `TheAI + 0x18 -> + 0x8C` AICrushesInfantry
(RW 0x745945), the owner's locomotor (RW 0x68B678 through AI + 0x31C) non-null with `+0x5C == 1` (RW 0x745968), `Object::canCrushOrSquish(goal)`
policy 2 (RW 0x69519A, RW 0x745973), the template +0x113 bit 0x10 clear (RW 0x74597C).

`RW 0x7457DF` (out of range) shape as instructions: owner (machine +0x14) / goal (RW 0x8DBACE); the owner's container + 0x27C, the template bits
+0x108 bit 4 and +0x112 bit 0x10, and the aux +0x94 bit only set an "ignore the view" flag (RW 0x745812 .. 0x745876); a weapon that is neither a
contact/melee weapon (RW 0x441B59, RW 0x9188EB) nor has a nonzero weapon template byte (RW 0x9188EB family at RW 0x745885) and a victim not
significantly above the terrain (RW 0x70C55D, RW 0x745894), plus the attack view RW 0x744AAA -> RW 0x7458A2, give `bl` = view blocked
(RW 0x7458AA .. 0x7458B0). Then RW 0x6CA32D (`weapon + 0x50` against `TheGameLogic + 0x40`'s clock, an "is the weapon ready" test that returns
true for the branch at RW 0x7458B9) or the blocked view → **true**; else `weapon->isWithinAttackRange(owner, goal, 0, 1)` (RW 0x6CC653, RW 0x7458DC)
true → **false**, false → **true**.

`RW 0x741745` (out of range, no path): with a goal object, `owner->getRelationship`-free position test — the goal's position (machine + 0x24 for the
no-object branch) and `RW 0x6CC622(owner, goal, extra 0, checkMin 1)`; a refusal of the range test → **true**, else false. RW 0x741798 (cannot
possibly attack, already ported) follows the same pattern.

## 8. Where the goal is placed in the port and what stays

The port's `makeGenericAttackMachine` currently holds `cannotPossiblyAttackObject` on Aim and Fire only, i.e. record 3 of the table RW 0xC29DD4 /
RW 0xC29E04, and its chase is a stub that returns success at once. The tables' other two records are missing, which is the whole of stop S-325's
"B1 conditions to Pursue": a victim that leaves the weapon's reach or a unit that could crush its victim instead never sends the machine to
Chase/Fire.
