## Why the crew path remains open

The crew reader is not merely an FX callback. `CastleBehavior::update` RW `0x79B0F1` walks the crew list and checks each member's damage/body interface: RW `0x79B17A..0x79B185` obtains last-damage frame (body vslot `0x44`) against castle module `+0x48`; RW `0x79B18A..0x79B1A8` obtains the last damage record (body vslot `0x40`) and tests record `+0x20` (damage amount); RW `0x79B1B1` reads record `+0x0C` (source player mask) before the owner/relationship check at `0x79B1C5..0x79B1E8`. The recovery path uses the prepare timer/data and eventually `releaseCrew(false)` at `0x79B2B2`, heals members and completes construction in the later block. The port has last-damage frame/source/type/no-effect state but no last-damage amount reader/state. That amount belongs to shared `ActiveBody`/damage-record behavior, not a Castle-only member field; implementing it here as a castle-specific approximation would bypass RotWK's Body interface and potentially desync every consumer. It is therefore left as a shared-mechanism follow-up, not claimed as ported or not-read. Any implementation requires the common state CRC, snapshot xfer, and save-version bump together, per PROCESS 15.5.

The crew release object effects, timed recovery decision, player-mask eligibility, health recovery, and forced completion stay within this unresolved end-to-end crew path; Ennorath's three fields are confirmed used but their user-visible effect is not claimed as ported. The exact OpenBFME follow-up is to add the `ActiveBody` damage-record amount through its established record interface and synchronized state protocol, then port `CastleBehavior::update`/release using these verified readers and synthetic tests. This shared change is outside this task's allowed area.
