# RW 0x735941 — Lua object registration and `ThingTemplate::ForceLuaRegistration` (issue #96)

Analysis of RotWK 2.01 (`RotWK/game.dat`, md5 `daed3668006cd90f01c34e5a7da1901f`, provenance
caveat S-001), every address read with `python tools/mod/rw.py workspace/RotWK/game.dat dis|xref <address>`.
Port: `engine/src/GameClient/LiveScripting.cpp` (`LiveScripting::describe`) and
`engine/src/GameClient/MapCreationHooks.cpp` (`templateForcesLuaRegistration`), lane PORT-24.
Mod data is not reproduced here (PROCESS.md 15.11).

The question the port had open: an object that has no AI — does RotWK still give it the Lua object
record? The answer is in one gate inside `RW 0x735941`, and the gate is the template field
`ForceLuaRegistration`. An object with an AI never reaches the field test: **that** is the pair of
branches `RW 0x73595A` (AI) and `RW 0x73595F` (no AI, field) that this document pins down.

### Every access to the byte in `.text`

A linear disassembly of `.text` (`RW 0x401000` .. `RW 0xBD0000`, 2,701,800 instructions) with
`capstone` was filtered for memory operands with displacement `0x640` and **byte** width. Six
instructions match; the `dword` matches (`RW 0x4EA03B`, `RW 0x4EA9BF`, `RW 0x4EACED`, ...) are a
different structure's array element and are not this field.

| Address | Instruction | Role |
|---|---|---|
| RW 0x74021F | `mov byte [ebx+0x640], al` | constructor default (0) |
| RW 0x6D26CA | `mov cl, byte [eax+0x640]` | copy source |
| RW 0x6D26D0 | `mov byte [ebx+0x640], cl` | copy destination |
| RW 0x734471 | `mov al, byte [ecx+0x640]` | template getter — **no reference in the binary** |
| RW 0x73491D | `mov al, byte [eax+0x640]` | object getter (via `[ecx+4]`) — **no reference in the binary** |
| **RW 0x73595F** | `cmp byte [eax+0x640], 0` | **the only game read**, in `RW 0x735941` |

The "no reference" statement is a scan of the whole image for the four-byte little-endian
addresses `0x00734471` / `0x0073491A` and for `call` / `jmp` rel32 targets equal to them: zero
hits. The two getters are dead in RotWK 2.01 (they stay in `.text`, most likely from an earlier
build); the field has exactly one consumer — the registration gate.

## 2. `RW 0x735941` — the registration gate

`RW 0x735941` is `ret 4` and takes one argument, the `Object *` at `[ebp+8]`; `ecx` / `esi` is the
Lua engine object (`[esi+0x0C]` is the object table that the record is written to, `[esi+0x10]` a
second table handle). The script engine singleton is `[0xDE7804]` at every call site.

| Address | Instruction | Meaning |
|---|---|---|
| RW 0x735941 | `mov eax, 0xB90573; call 0xA3CEF0` | SEH prologue (as in the rest of the binary) |
| RW 0x73594D | `mov edi, [ebp+8]` | `edi` = `Object *` |
| **RW 0x735950** | **`mov eax, [edi+0x260]`** | the object's AI update interface |
| RW 0x735956 | `test eax, eax` | |
| RW 0x735958 | `mov esi, ecx` | `esi` = the Lua engine |
| **RW 0x73595A** | **`jne 0x73596C`** | **AI non-null -> jump straight to the record; the field is never read** |
| **RW 0x73595C** | **`mov eax, [edi+4]`** | no AI: `eax` = the `ThingTemplate *` (Object `+0x04`) |
| **RW 0x73595F** | **`cmp byte ptr [eax+0x640], 0`** | the field |
| **RW 0x735966** | **`je 0x735A0D`** | **field 0 -> the shared epilogue at RW 0x735A0D: no record, no Lua call at all** |

So there are exactly three entrance branches, and the port had implemented only two of them:

1. **AI present** (RW 0x73595A taken): record, whatever the template says — `ForceLuaRegistration`
   does not matter for an object with an AI, and the INI value of an AI object is never read.
2. **No AI, field 0** (RW 0x73595F / RW 0x735966 taken): return at RW 0x735A0D. The epilogue is
   entered before the temporary `AsciiString` of the name exists, so nothing is allocated and no
   `RW 0xB5B9xx` Lua call runs.
3. **No AI, field non-zero**: falls through to RW 0x73596C and gets the same record an AI object
   gets.

### What the record is (branch 1 and branch 3 alike)

| Address | Instruction | Meaning |
|---|---|---|
| RW 0x73596C .. RW 0x73597C | `push 0; push [esi+0x10]; call 0xB5B190`, `lea eax,[ebp+8]; push edi; push eax; call 0x734C93` | build the name from the object |
| RW 0x734CA8 .. RW 0x734CB3 | `push [ebp+0xC + 4]` == `[object+0x74]` (the object id), `push 0xC244BC` | format string at RW 0xC244BC = `"ObjID#%08x"` |
| RW 0x73599E | `call 0xB5B910` | hand the name to the state (`[esi+0x0C]`) |
| RW 0x7359AD .. RW 0x7359C3 | `call 0xB5B2F0`, `call 0xB5B3E0`, `cmp edi, eax`, `jne 0x7359D1` | the "already there?" test on the object table |
| RW 0x7359C5 .. RW 0x7359CF | `push -2; push [esi+0xC]; call 0xB5B190; jmp 0x7359FE` | entry already present (the table holds one element and it is this id) -> skip the two stores, go to the name's destructor at RW 0x7359FE |
| **RW 0x7359DF** | `call 0xB5BB30` | store the record under the name `ObjID#%08x` |
| **RW 0x7359F9** | `call 0xB5BB70` | and under the numeric key (the object id kept in `edi` at RW 0x735989) |
| RW 0x735A04 | `call 0x435D50` | destroy the temporary name |
| RW 0x735A0D | `mov ecx,[ebp-0xC]; pop edi; pop esi; mov fs:[0],ecx; leave; ret 4` | shared epilogue |

`0xB5B190` / `0xB5B910` / `0xB5BB30` / `0xB5BB70` are the statically linked Lua 4.0 C API entry
points (`0xB5BB30` writes `type = 4` (`LUA_TTABLE`) into the state at `[ecx]`/`[ecx+8]`), so the
record is an ordinary Lua table reachable by name from every script of that state.

`INFERENCE:` that the table also becomes visible to scripts as a global is the Lua 4.0 registry
semantics of those calls; the binary shows the two stores and the name, not the global lookup a
script performs.

## 3. The counterpart: `RW 0x735A1D` unregister

| Address | Instruction | Meaning |
|---|---|---|
| RW 0x735A1D | `mov eax, 0xB9060D; call 0xA3CEF0` | prologue |
| RW 0x735A2B | `cmp dword ptr [esi+0xC], 0; je 0x735ADA` | no table -> nothing to do |
| RW 0x735A39 | `push 0; push [esi+0x10]; call 0xB5B190` | |
| RW 0x735A49 | `call 0x734C93` | the same `ObjID#%08x` name |

Neither `RW 0x735A1D` nor `RW 0x735941` reads `+0x640`; registration and unregistration stay
symmetric, which is why an AI-less forced object is removed again when its owner changes.

## 4. Call sites

Direct `call` targets found by scanning every decoded `call` rel32 in `.text`:

| Function | Call sites | Context |
|---|---|---|
| `RW 0x735941` register | RW 0x667C6E, RW 0x68E421, RW 0x699623 | see below |
| `RW 0x735A1D` unregister | RW 0x68C1F5, RW 0x699617 | leaving the world, and the owner change |

* **RW 0x68E421** — inside `Object::enterWorld`-side code: after the drawable and the world
  notifications, `mov ecx,[0xDE7804]; test ecx,ecx; je; push esi; call 0x735941`. The engine is
  null-checked here.
* **RW 0x699623** — a change of owner: `call 0x735A1D` at RW 0x699617 immediately followed by
  `call 0x735941` at RW 0x699623, both under the `[0xDE7804]` null check.
* **RW 0x667C6E** — the object's post-load hook (near `RW 0x68BBE0` / `RW 0x68B44B`), and the only
  site that does **not** null-check `[0xDE7804]` (the caller guarantees a script world).
* **RW 0x68C1F5** — leaving the world; guarded by `test ecx,ecx; je`.

Every call site passes the object unconditionally, so **the gate lives inside `RW 0x735941` and
nowhere else**. A port that decides at a call site would have to repeat the field read three times
and would diverge; the port therefore keeps the single gate inside `LuaScriptEngine::registerObject`
and reads the field through one function (`MapCreationHooks::templateForcesLuaRegistration`).

## 5. What the record does and does not do: `RW 0x735F53` dispatch

The record is a name, not a handler list. `RW 0x735F53` (Lua event dispatch) has its own,
independent gates, and the first of them is the AI:

| Address | Instruction | Meaning |
|---|---|---|
| RW 0x735F64 | `mov eax, [esi+0xC]; cmp eax, ebx (0); je 0x73616F` | no object table |
| RW 0x735F71 | `cmp dword ptr [esi+0xD4], 0xA; jg 0x73616F` | a per-state counter above 10 stops dispatch (not the object test) |
| RW 0x735F85 | `mov edi, [ebp+0xC]` | `edi` = the `Object *` |
| **RW 0x735F8F** | **`mov ecx, [edi+0x260]`** | the AI |
| **RW 0x735F95** | **`cmp ecx, ebx`** | with `ebx = 0` |
| **RW 0x735F9D** | **`je 0x73616E`** | **no AI -> return: no event is sent to this object** |
| RW 0x735FA3 | `test byte ptr [edi+0x458], 1; je 0x735FBD` | a status bit, then a filter against `[esi+0xDC]` |
| **RW 0x735FBD** | **`mov ecx, [ecx+0x220]`** | **the AI's `AILuaEventsList`** |
| RW 0x735FC3 | `cmp ecx, ebx; je 0x73616E` | no handler list -> return |

So an AI-less object that `ForceLuaRegistration` let in is **referenced by scripts but receives no
event**: the dispatch stops at its own `Object + 0x260` test (RW 0x735F8F / RW 0x735F95 /
RW 0x735F9D) before it ever looks at a handler list (RW 0x735FBD, the list at `AI + 0x220`).
`RW 0x73616E` / `RW 0x73616F` are the two shared returns of the epilogue.

The eleven direct callers of the dispatch are RW 0x73735E, RW 0x737473, RW 0x737925,
RW 0x73799F, RW 0x7379DC, RW 0x737EEE, RW 0x738061, RW 0x7381FF, RW 0x73836B, RW 0x8E1082 and
RW 0x911FC3 (the per-event senders); the port's `LuaScriptEngine::dispatch` keeps the same order of
gates.

## 6. What the port does now (lane PORT-24)

| RW | Port |
|---|---|
| Field row RW 0xDA4838, parser RW 0x42E558, offset `+0x640` | `MapCreationHooks::templateForcesLuaRegistration` — the one reader; the raw `parsed-unused` row is gone |
| Default 0 (RW 0x74021F), copy (RW 0x6D26CA / RW 0x6D26D0) | the template field starts `false` and is copied with the template |
| Gate RW 0x735950 / RW 0x73595A | `LiveScripting::describe`: an object with an AI (`AILuaEventsList` present) registers as before, `hasAI = true` |
| Gate RW 0x73595C / RW 0x73595F / RW 0x735966 | an object with no AI registers only when the template sets the field; `hasAI = false`, `forceLuaRegistration = true`, `luaEvents = nullptr` |
| Record RW 0x7359DF / RW 0x7359F9 | `LuaScriptEngine::registerObject` (unchanged; it already built `ObjID#%08x` and the table) |
| Dispatch RW 0x735F8F / RW 0x735F95 / RW 0x735F9D | `LuaScriptEngine::dispatch` (unchanged; it stops without an AI) |

State: no new logic state, nothing to add to a snapshot / `xfer` (PROCESS.md 15.5) — the flag is a
template property, and the registry is rebuilt on load by `RW 0x68E421`.

## 7. What stays unported

* The offline map preview (`MapObjectRuntime::LuaMapHost::findObject`) still answers with
  `hasAI = true` / `forceLuaRegistration = false`: the game builds that runtime without a Lua state
  (`build(clientOnly(), false)`), so it has no registry to consult. This is the S-110 approximation,
  recorded as item 1 of the `S-147` stop in `docs/STOPS.md`; nothing new is hidden.
* The record's use by scripts (any handler that needs AI, upgrades, special powers or emotions) is
  the existing `S-147` / `S-124` body of work, not this field.
