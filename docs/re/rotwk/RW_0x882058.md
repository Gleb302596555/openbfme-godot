### The alleged second reader, RW 0x883A55

batch-4 row 26 lists `RW 0x883A55 push dword ptr [esi+0x78]` with `ecx = [RW 0xDE412C]`
(`TheGameLogic`) and `call RW 0x449681` as a second use of the field. RW 0x449681 is
`GameLogic::findObjectByID` — see [RW_0x74C4A7.md](RW_0x74C4A7.md), which fixes it through
RW 0x8DBACE (`machine->getGoalObject()`). An argument to `findObjectByID` is an `ObjectID`,
and RW 0x883A55 lies outside `AnimalAIUpdate::update`, which ends at RW 0x882BBC
(0x882058 + 2916). **INFERENCE**: `+0x78` there is another class's object id, not
`UpdateTimer`; the class is not named by the image. `UpdateTimer` therefore has one reader.

### RW 0x882508 is not a return

issue #60 asks what RW 0x882508 returns. It returns nothing — it is a jump **target inside**
the function:

* `AnimalAIUpdate::update` is 2,916 bytes (AMBIENT_MOVEMENT.md, and the donor's own header
  `0x0047EDC9..0x0047F92D (2916 B)`), so it spans RW 0x882058 .. RW 0x882BBC.
* RW 0x882508 is 0x4B0 = **1,200 bytes into** it, and **1,716 bytes of code follow**. A
  return would leave those 1,716 bytes unreachable.
* Both of the gate's skip branches (`jbe` at RW 0x882292, `jne` at RW 0x8822A6) jump there,
  and in the donor the code after the gated block is the idle test `if (stateID != 0)` — the
  one statement that both a zero timer and a non-zero remainder have to reach, because the
  wander below it runs on every idle frame in either case.

So the gate skips **the enemy scan only**. The wander dice, the SALT_LICK scan and the wander
orders are outside it: an animal with `UpdateTimer = 10` still rolls `[0,100]` (line 0x9a) on
every idle frame. This is what the port has to reproduce, and it is narrower than "the
critter decides only every `UpdateTimer` frames".

### The gate, instruction by instruction

```
RW 0x882288  mov ecx, [eax+0x78]     ; eax = the module data ([ebp-0x18]): UpdateTimer
RW 0x88228B  test ecx, ecx
RW 0x882292  jbe  RW 0x882508        ; UpdateTimer == 0 -> no scan at all, idle test
RW 0x882298  mov eax, [RW 0xDE412C]  ; TheGameLogic
RW 0x88229D  mov eax, [eax+0x40]     ; the logic frame counter
RW 0x8822A2  div ecx                 ; edx:eax / UpdateTimer
RW 0x8822A4  test edx, edx
RW 0x8822A6  jne  RW 0x882508        ; remainder != 0 -> no scan this frame, idle test
RW 0x8822AC  …                       ; the gated block: the enemy scan
```

### RW 0xDE9184 — the debug switch

issue #60 asks what the global tested at RW 0x8820B3 and RW 0x8822AC is. In the donor every
message of this function is behind `if (g_bfmeCritterDesyncLog && theLogicRandomLogFile)` —
the `'CritterDesync: …'` trace of the critter-desync log, written to the logic random log
file. RW 0x8820B3 is the test in front of the bad-area message (step 4) and RW 0x8822AC the
one in front of `'CritterDesync: animal %s is doing periodic search for enemies.'`, the first
statement of the gated block. **INFERENCE**: `[RW 0xDE9184]` is that switch
(`g_bfmeCritterDesyncLog`); the image does not name it, and the second half of the pair (the
log file handle) is the neighbouring global. It is a logging switch only — no branch of the
simulation depends on it, and the port has no equivalent to add.

### The gated block

```
enemy = ThePartitionManager->getClosestObject(position, (float)m_fleeRange, FROM_CENTER_3D, filters)
if (enemy) {
        same = enemy->getID() == scaringObjectID
            && (ai->currentStateID() == 20 || ai->currentStateID() == 19)
        if (!same) {
                animal->m_fleeDistance /* +0x1AC */ = m_fleeDistance
                aiFleeFromObject(TheGameLogic->findObjectByID(enemy->getID()), CMD_FROM_SCRIPT)
                scaringObjectID = enemy->getID()
        }
        return UPDATE_SLEEP_NONE          ; also when the enemy is the same one
}
```

Three things here are outside this lane and stay stops:

* the flee itself is `aiFleeFromObject` with `CMD_FROM_SCRIPT` and the object's own
  `m_fleeDistance` (`Object + 0x1AC`); the port emulates it with a computed destination,
  `aiMoveToPosition(CMD_FROM_AI)` and `LOCOMOTORSET_PANIC` (S-5910);
* the re-issue suppression — the same enemy while the animal is already in state 19 or 20 —
  has no counterpart in the port, whose AI state ids are BFME1's (S-221: RotWK's own
  numbering is not read) and which has no panic state to be in. Porting it needs
  `aiFleeFromObject` first;
* the layer check of step 4 and the `returning` state of step 5 are S-5910 as well.

What this lane takes from the block is only **when it runs**: on frames whose logic frame
number is a multiple of `UpdateTimer`, and never when `UpdateTimer` is 0 — and that it runs
before the idle test, so a moving animal scans too.
