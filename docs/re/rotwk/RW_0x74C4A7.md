# RW 0x74C4A7 — AIAttackFireWeaponState::update and Weapon/FinishAttackOnceStarted (issue #53)

Analysis of RotWK 2.01 (`RotWK/game.dat`, md5 `daed3668006cd90f01c34e5a7da1901f`), every
address read with `python tools/mod/rw.py <game.dat> dis|xref <address>`. The image carries
the extra sections the other `docs/re/rotwk/` notes mention (PLAN rule 9 / S-001 provenance
caveat); `.text` is the retail code. Port: `engine/src/GameLogic/AI/AIAttack.cpp`
(`AIAttackFireState`, lane PORT-1). Data of the mod is not reproduced here; the field's
readers and the branch are what this note fixes.

## The field

| What | Address | Instruction |
|---|---|---|
| Parser | RW 0x42E558 | `parseBool` (field table row RW 0xC17208, order 67, offset 0x161) |
| Constructor default = 1 (Yes) | RW 0x6CE164 | `mov byte ptr [esi + 0x161], 1` — the only byte initialised to 1 in that run (0x160, 0x168 .. 0x16B, 0x16C, 0x16E .. 0x171 get 0; 0x16D gets 1) |
| Copy | RW 0x6CE764 / RW 0x6CE76A | `8A 87 61 01 00 00` = `mov al, byte ptr [edi+0x161]`, `88 86 61 01 00 00` = `mov byte ptr [esi+0x161], al` (a field-by-field `*this = *src`: 0x150, 0x154 .. 0x158, 0x15C, 0x160, 0x161, 0x164, 0x168 ..; `edi` source, `esi` destination) |

The member is `WeaponTemplate + 0x161`; the runtime `Weapon` reaches it through `Weapon + 4`
(RW 0x74C509 `mov eax, [ebp-0x18]; mov eax, [eax+4]`, the same `+4` the aim adjustment at
RW 0x74C604 reads AimDirection / AcceptableAimDelta from).

## update RW 0x74C4A7, start to returns

STATE_CONTINUE (RW 0x74C72B `push -2; pop eax`), `-1` = STATE_FAILURE (RW 0x74C8AC
`or eax, -1`).


Then the decision this issue is about. It is the same test as the aim state's (RW 0x752382 ..
0x7523B2, already ported): *the victim is gone*.

```
RW 0x74C6A8  if ([state+0x20] == 0) goto FIRE               ; no notify: no decision
RW 0x74C6B3  if (!notify->vslot3()) goto FIRE              ; RW 0x9DBF60: not an attack on an object
RW 0x74C6C0  if (victim == 0) goto RW 0x74C6DF              ; RW 0x74C6C3: no victim object
RW 0x74C6C7  if ([victim+0x458] & 1) goto RW 0x74C6DF       ; the victim is dead
RW 0x74C6D0  if (!victim->testStatus(0x32 FLEE_OFF_MAP)) goto FIRE
RW 0x74C6DF  eax = [weapon+4]                               ; WeaponTemplate
RW 0x74C6E5  cmp byte ptr [eax+0x161], 0                    ; FinishAttackOnceStarted
RW 0x74C6EC  jne FIRE                                       ; Yes -> the shot goes on
RW 0x74C6F2  ecx = [state+0x18]                             ; the machine
RW 0x74C6F5  eax = [ecx]
RW 0x74C6F7  push 0                                         ; setGoalObject(NULL)
RW 0x74C6F8  call dword ptr [eax+0x38]                      ; vslot 0x38 = RW 0x8DB8CB
RW 0x74C6FB  jmp RW 0x74C8AC                                ; return STATE_FAILURE
```

So the two paths after RW 0x74C6E5 are:

**Yes (1, the constructor's default and RW 0x74C6EC `jne`).** The state continues into the fire
path at RW 0x74C530 with everything it had: the shot that was already started is fired even
though the victim is dead, gone or fleeing.

**No (0, RW 0x74C6F2).** `setGoalObject(NULL)` on the machine — RW 0x8DB8CB is
`if ([machine+0x38] != 0) return;` (a locked machine keeps its goal) otherwise RW 0x8DB809
`and dword ptr [ecx + 0x20], 0` clears the goal object id — and the state returns
STATE_FAILURE (RW 0x74C8AC): the attack ends and the shot is not fired. Unlike the other two
failure returns of update (RW 0x74C4E2 / RW 0x74C72B, which return STATE_CONTINUE), this one
leaves the state.

The field is consulted **only** when the notify says the attack is on an object *and* the
victim is gone in the sense above; a position attack (`isAttackingObject` false), a live
victim, or a missing weapon (RW 0x74C4E2 leaves earlier) never reach RW 0x74C6E5.

attack never reads FinishAttackOnceStarted.

## The other readers of `+0x161`

The linear decode of all of `.text` finds three more accesses. Each is attributed here.

1. **RW 0x5AF4A6 — not this field.** In the constructor that starts at RW 0x5AF2A0:
   `movzx edx, byte ptr [esi+0x162]; movzx ecx, byte ptr [esi+0x161]; movzx edx, byte ptr
   [esi+0x160]` (RW 0x5AF49F .. 0x5AF4B1), all three converted to float and multiplied by
   RW 0xBD1920, then stored as a three-float vector at `[eax] .. [eax+8]` (RW 0x5AF4CC ..
   RW 0x5AF4D5). It is a three-byte colour, `+0x160 .. +0x162` of *another* class: the same
   object has members at `+0x248 .. +0x288`, `+0x2D4` and `+0x2D8` (RW 0x5AF4DE .. 0x5AF4E0),
   `WeaponTemplate` ends at `+0x171` (RW 0x6CE1AA, the constructor's last byte) and its
   `+0x160` is the override byte (field table row 0xC17208, offset 0x160). The class itself is
   not named by the binary; identifying the owner of those colours is not needed — it cannot be
   `WeaponTemplate`. **INFERENCE** only in the class name.
2. **RW 0x741368 — a `WeaponTemplate` getter, no caller.** `mov al, byte ptr [ecx + 0x161];
   ret`, `ecx` is the template. Nothing reads it: no rel32 `call`/`jmp` reaches it, and the
   32-bit value 0x00741368 occurs nowhere in the image (searched every section, so not in a
   vtable or a function-pointer table either). Dead in 2.01.
3. **RW 0x741394 — a `Weapon` getter, no caller.** `mov eax, dword ptr [ecx + 4]; mov al, byte
   ptr [eax + 0x161]; ret`, `ecx` is the `Weapon` (it forwards to its template, the same shape
   as its neighbours RW 0x74136F `mov eax, [ecx+4]; add eax, 8; ret` and RW 0x741376). Also no
   rel32 reference and 0x00741394 occurs nowhere in the image. Dead in 2.01.

So RW 0x74C4A7 **RW 0x74C6E5** is the field's only live reader. Nothing else has to be ported.

## What the port does with it

`engine/src/GameLogic/AI/AIAttack.cpp`, `AIAttackFireState::update` takes the same decision at
its victim test (`if (m_att->isAttackingObject() && victimGone(victim)) return STATE_FAILURE;`)
and never read the field, i.e. it behaved as `FinishAttackOnceStarted = No` for every weapon.
The change adds the RW 0x74C6E5 branch there: the ordinary fire path when the field is Yes (the
port's default, `WeaponTemplate::m_finishAttackOnceStarted = true`, RW 0x6CE164), and the
failure when it is No.

The decision has a precondition in the same update, and the port now keeps it: RW 0x74C50F ..
RW 0x74C52A sends a NoVictimNeeded weapon (`+0x16B`) whose victim is absent (RW 0x74C51C) or
not IMMOBILE (RW 0x74C523, KindOf bit 2 of the victim's template at `+0x108`) straight to
RW 0x74C52C -> RW 0x74C530 with the flag `[ebp-0xd] = 1`, and that flag later chooses the
position fire RW 0x74C88B. So those shots never read the field, and the port's guard
(`positionShot`) is what makes the branch below it equal to RW at all; 13 of Ennorath's 51
weapons with the field set also set NoVictimNeeded.

Not ported, with the reason (stop S-7182): the `setGoalObject(NULL)` of the No path (RW 0x74C6F2
-> RW 0x8DB8CB). The port's `AIAttackState::update` re-derives the sub-machine's goal from the
attack state's own goal every frame (`if (victim->getID() != m_attackMachine->goalObjectID())
m_attackMachine->setGoalObject(...)`) and the attack state's exit clears that goal
(`machine().setGoalObject(INVALID_ID)`), so the sub-machine's own clear cannot be observed by any
test the port can write; a write that no test can tell apart would be unverified code
(PROCESS.md 15.9).

Three behaviours of the same instruction sequence are changed together, because the branch
cannot be correct with only one of them: the field's value (RW 0x74C6E5), the set of cases in
which the field is consulted at all (RW 0x74C6C0 .. RW 0x74C6D9, including the victim's
FLEE_OFF_MAP at RW 0x74C6D0, which the port's fire state was missing) and the exception that
skips the whole block (RW 0x74C50F .. RW 0x74C52C).
